# Приёмник чужих копий на хосте стора (2026-09-23)

По просьбе VibeReel и решению владельца хост стора принимает зашифрованные копии базы соседнего
продукта: `infra/hostBackupDrop.sh --product <имя> --key "<ssh-ed25519 …>"`. Файлы шифрует
отправитель ключом владельца, открыть их на хосте нечем — хост хранит непрозрачное.

## Устройство

- Учётка `<имя>-backup`: оболочка `/bin/sh` — принудительная команда ssh исполняется через оболочку
  пользователя, и под `nologin` rrsync не запустится; без пароля, без sudo, вне групп `vibememory`,
  `vmaccess`
- Каталог `/srv/backups/<имя>` (700, владелец — эта учётка), рядом с `/srv/vibememory`, но не внутри
- `authorized_keys` — ровно одна строка:
  `command="/usr/bin/rrsync -wo -no-del -no-overwrite /srv/backups/<имя>",restrict ssh-ed25519 …`
- Старые копии удаляет root: `/etc/cron.d/<имя>-backup-retention`, ежедневно, старше `--keep-days`
  (по умолчанию 30) — ключ отправителя удалять не может

## Что делают флаги rrsync на деле

Проверено на хосте (rsync 3.4.1) через loopback временным ключом с той же принудительной командой:

| Попытка | Итог |
|---|---|
| Записать новый файл | код 0, файл лёг |
| Перезаписать тот же файл другим содержимым | **код 0**, но файл прежний: `-no-overwrite` — это `--ignore-existing`, отказа нет |
| Прочитать файл обратно | код 12, копии нет |
| `--delete` пустым каталогом | код 12, файл на месте |
| Команда оболочки `ls` | код 1 |

Отсюда следствие для отправителя: успех `rsync` не доказывает, что на хосте именно его новая копия,
если имя файла уже было. Имена копий обязаны быть уникальными — у VibeReel в имени дата и время.

## Грабли проверки: `ssh` съедает скрипт, поданный через stdin

Проверку гоняли как `ssh хост 'bash -s' < скрипт`. Внутри скрипта стоял `ssh … ls` без `-n` — он
прочитал остаток скрипта со stdin как свой ввод, и шаг уборки не выполнился: временный ключ остался
второй строкой `authorized_keys`, проба — в каталоге. Убрали отдельной командой сразу же.

Правило: в скрипте, который сам пришёл через stdin, каждый `ssh` — с `-n` (или `< /dev/null`); `rsync`
канал ssh держит сам и stdin не трогает.
