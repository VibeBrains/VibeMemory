# Удаление памяти воскресало на первом же тике

Найдено 2026-09-13 живой записью с хоста.
Касалось любого `memory_delete`, пришедшего с другой машины, а не только хоста.

## Что было

Хронология по истории стора:

1. `2b9a12af` — сервер на хосте записал `upsert` записи `Probe/host-write-probe`
2. `ed30f134` — тик Mac получил событие и создал проекцию `host-write-probe.md`
3. `c76e26a3` — хост записал `delete` с родителем — версией из шага 1
4. `21ee0f58` — следующий тик Mac дописал новый `upsert` с тем же родителем

Удаление и новая версия стали двумя листьями одного родителя, и по правилу
«удаление уступает правке» запись осталась живой на обеих сторонах.

## Почему

Причин две, и каждая по отдельности безобидна:

- **Синхронизация памяти только пишет файлы.** Проекция забытой записи больше не создаётся, но и старый файл никто не убирает
- **Импорт видит в оставшемся файле новую запись.** Среди живых записей её нет, у файла есть `version`, значит правка от этой версии

Шаг «сначала правки, потом проекция» верен для правок человека.
Для файла, оставшегося от удалённой записи, он превращает удаление в правку.

Гейты этого не видели:
- Фикстура `deleteForgets` проверяла только свёртку журнала, файла на диске в ней нет
- Импорт проверялся только на живых записях

## Как устроено теперь

- Свёртка помнит для забытой записи версию, которую видело удаление (`Forgotten.seen`)
- Импорт сравнивает файл с этой версией:
  - Совпадает и версия, и содержимое — файл попадает в `Import.stale`, событие не пишется
  - Отличается — правка, одновременная с удалением. Пишется с родителем-версией, и запись остаётся, как если бы правка пришла журналом
- Синхронизация удаляет файлы из `stale` и сообщает их в `Synced.removed`

Кейсы: `importForgottenProjectionIsNotAnEdit` (`observed`, этот случай) и
`importEditOfForgottenRecordIsConcurrent`.
Гейты на диске: `a_delete_from_another_machine_removes_the_projection_instead_of_being_undone` и
`an_edit_that_outlived_a_delete_keeps_the_record` в `memory_sync.rs`.
Выключение правила в импорте роняет оба вида гейтов.

## Вторая половина — сторож тика возвращал файл

После правки импорта уборка на живой машине показала то же в другом месте.
Тик сообщил:
_restored: projects/Probe/memory/host-write-probe.md was deleted in the working copy and put back_

Синхронизация памяти убирала файл, а шагом позже `restore_deleted_transcripts` возвращал
всё пропавшее под `projects/` из индекса git.
Удаление так и не коммитилось, и на каждом тике повторялось «убрал → вернул».
Журнал не портился, но файл жил вечно и на всех машинах.

Сторож защищает транскрипты от чужих подметальщиков, и это верно.
Проекции памяти ему защищать незачем:
Файл живой записи проекция перепишет сама
Файл, который проекция убрала, принадлежит записи, забытой журналом

Поэтому сторож пропускает `projects/<имя>/memory/…`.
Журнал `projects/<имя>/memory.jsonl` лежит уровнем выше и остаётся под защитой.
Удаление коммитит обычный шаг общих файлов: `git diff --name-only HEAD` видит удалённые пути.

Гейт `a_memory_delete_from_elsewhere_removes_the_file_everywhere_and_stays_removed` в `tick_cycle.rs`
проходит путь целиком на двух клонах: запись, проекция, удаление с другой машины,
два тика, файл пропадает и у второй машины.
Без фильтра в стороже он падает.

## Правило на будущее

Проекция — производное журнала в обе стороны.
Если событие убирает запись, проекция должна убрать файл, иначе следующий импорт прочитает
остаток как новое слово человека.
Любой новый вид события проверяется гейтом, где файл на диске уже есть, и через полный тик:
у тика несколько шагов, трогающих рабочую копию, и каждый может отменить соседний.
