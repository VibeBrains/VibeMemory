# Первый хост стора: чему научил живой прогон (2026-09-07)

Сервер `vm@vibememory.ru` — чистая Debian 12, 1,3 ГиБ памяти, 2 ядра, диск 9,9 ГиБ (свободно 7,8).
Всё ниже найдено на нём, а не придумано заранее.

## 1. «Server accepts key» и сразу «Permission denied» — это про парольную фразу

Ключ засеян, сервер его принимает (`debug1: Server accepts key`), и следом отказ. Причина не в
ключе и не в сервере: ключ защищён парольной фразой, `ssh-agent` пуст, подписать вход нечем, а
спросить фразу в неинтерактивном режиме не у кого. Сообщение ssh об этом не говорит ничего.

Лечение — один раз: `ssh-add --apple-use-keychain ~/.ssh/id_ed25519_vibememory`. В
`~/.ssh/config` нужны `AddKeysToAgent yes` и `UseKeychain yes`, иначе после перезагрузки всё
повторится; `seedKey.sh` теперь их пишет и сам проверяет агент.

## 2. На свежей Debian нет git

Очевидно задним числом, неочевидно в момент, когда `hostBootstrap.sh` падает на первой команде.
Скрипт теперь говорит прямо и называет команду установки. Ставится `sudo apt-get install -y git`
(на этом сервере `sudo` без пароля).

## 3. Пустой последний аргумент через ssh исчезает

`ssh host 'bash -s' -- "$a" "$b" "$c"` при пустом `$c` доходит до сервера как два аргумента: ssh
склеивает всё в одну командную строку. На той стороне `set -u` и `mirror="$3"` — мгновенная
смерть. Правильно `${3:-}`.

## 4. Большой первый push по домашнему каналу не доезжает, и дробить его по коммитам бесполезно

Первая попытка: 780 МиБ одним потоком, 17 минут, `client_loop: send disconnect: Broken pipe`,
`send-pack: unexpected disconnect`. На сервере остался брошенный временный пакет на 124 МиБ и
**ноль** объектов: git не умеет продолжать прерванный push.

Вторая попытка — порциями по коммитам — не сработала по другой причине: коммитов всего 81, а вся
масса (930 МиБ) лежит **в одном** коммите миграции. Дробление по коммитам помогает, когда объём
размазан по истории; здесь оно не помогло ничем.

**Что работает: перенести пакеты, а не поток.** `git gc` локально (780 → 594 МиБ), затем
`git clone --bare --local` (жёсткие ссылки, мгновенно) и `rsync --partial` файлов `objects/`
плюс `packed-refs` и `HEAD`. `rsync` продолжает с места обрыва — на канале ~0,5 МиБ/с это
разница между «дошло» и «никогда».

Гоча macOS: системный `rsync` — это `openrsync`, он не знает `--info=progress2`. Флаги проверять,
а не копировать из статей про GNU rsync.

## 5. Память сервера: своп нужен, а автосборка мусора — нет

1,3 ГиБ без свопа — мало для `index-pack` большого пакета. Добавлено 2 ГиБ свопа (`/swapfile`,
прописан в `fstab`) и лимиты в репозитории: `pack.threads=1`, `pack.windowMemory=64m`,
`core.bigFileThreshold=8m`.

`gc.auto=0` оставлен намеренно — сборка мусора не должна начинаться на приёме push'а посреди
тика, — но репозиторий, который никогда не пакуют, растёт неограниченно, а диск 10 ГиБ. Поэтому
`hostBootstrap.sh` ставит еженедельный `git gc` в cron (воскресенье, 04:17).

## 6. Мелочь, которая шумит: `sudo: unable to resolve host`

У свежей машины имя хоста не разрешается через `/etc/hosts`, и каждая команда через `sudo` пишет
эту строку в stderr. Одна строка `127.0.1.1 vibememory` — и вывод скриптов становится читаемым.
