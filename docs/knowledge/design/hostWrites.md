# Сервер под `vmgit` пишет в чужой стор: что это стоит (фаза 1, 2026-09-23)

Фаза 1 перевела сервер памяти на хосте с учётки владельца `vm` на `vmgit` без sudo и дала ему снимок
прав вместо одного токена. Код — `crates/vibememory-mcp/src/{access,host,http}.rs`, выкладка —
`infra/hostMcp.sh`. Здесь — то, что выяснилось только на живом хосте и чего не было в плане.

## Git запирает `HEAD`, двигая ветку, на которую `HEAD` указывает

Права личного стора после фазы 0: группе `vibememory` — запись только в `objects/` и `refs/`, корень
`store.git` — `2750`, потому что там `config` и `hooks/`, которые исполняет git владельца с sudo
([hostUsers.md](hostUsers.md)). Гейт фазы 0 проверил запись `vmgit`: объект, дерево, коммит и
`update-ref refs/heads/probe` прошли.

Но `probe` — не та ветка, на которую указывает `HEAD`. Двигая **её**, git (2.54 на Mac, 2.47.3 на
хосте) заодно пишет журнал `HEAD` и для этого берёт замок `HEAD.lock` — рядом с `HEAD`, в корне
репозитория. Под `vmgit`:

```
fatal: update_ref failed for ref 'refs/heads/main': cannot lock ref 'refs/heads/main':
Unable to create '…/store.git/HEAD.lock': Permission denied
```

Ни `update-ref --no-deref`, ни `--stdin` с `option no-deref`, ни `-c core.logAllRefUpdates=false`
замок не снимают: это раздельное обновление `HEAD`, которое git делает всегда. То есть демон под
`vmgit` не сдвинул бы `main` ни одной записью, а гейт фазы 0 этого не увидел, потому что двигал не
ту ветку. Урок для гейтов: проверять ровно ту операцию, которую сделает код, — здесь `main`.

**Открыть корень группе нельзя** — даже со sticky-битом, который защитил бы `config` и `hooks/` от
подмены. В корень можно было бы положить новый файл `commondir`: git читает его у любого каталога
репозитория и берёт `config` и хуки из названного там места — то есть `vmgit` исполнил бы код от
`vm`. Корень остаётся закрытым.

**Решение — свой `HEAD` у пишущего.** Каталог связанного рабочего дерева — `HEAD` и файл
`commondir` с путём к репозиторию — во временной папке процесса. `update-ref` идёт с
`GIT_DIR=<этот каталог>`: замок `HEAD.lock` ложится туда, а сама ветка запирается и сдвигается в
`refs/` стора тем же `refs/heads/main.lock`, что и push владельца, — взаимное исключение с push и
compare-and-swap по старому значению сохранены. Каталог удаляется после записи; git владельца в него
не заглядывает.

Две грабли по дороге:

- **`GIT_COMMON_DIR` вместо файла `commondir` не работает**: `git rev-parse --git-common-dir` называет
  общий каталог, но ни config, ни ссылки из него не читаются — `main` не находится вовсе. Только файл
  `commondir` внутри каталога дерева, как его кладёт `git worktree add`
- **Через дерево репозиторий для git уже не голый**, и он пишет журнал ссылки в `logs/` стора — снова
  в корень. Отсюда `-c core.logAllRefUpdates=false` у этой одной команды. Журнала ссылок у стора нет
  (`logs/` отсутствует — проверено на хосте), а существующий журнал git дописывал бы при любой
  настройке

Временный индекс записи (`GIT_INDEX_FILE`) по той же причине переехал из корня стора во временную
папку. Проверено на git хоста под `vmgit` одноразовым репозиторием с правами как у `store.git`, потом
вживую: запись по HTTPS — коммит с автором `host-tk_legacy`, корень стора без новых файлов, объекты
`0444 vmgit:vibememory`, новые каталоги объектов `drwxrwsr-x`, `refs/heads/main` — `0664
vmgit:vibememory`: push владельца и ночная упаковка от `vm` с ними справляются. Гейт в
`tests/git_memories.rs` пишет в репозиторий с корнем `0555`; мутация «`update-ref` через `--git-dir`»
падает на том же `HEAD.lock`.

## Замеры сервера

- **Память:** RSS процесса 3,6 МиБ в покое, 3,8 МиБ с восемью занятыми соединениями
- **Семафор:** восемь соединений висят на недосланном теле — у процесса 9 потоков (приём и восемь
  соединений); девятый запрос ответ получил через 9,2 с — когда первое место освободилось по
  таймауту чтения 10 с; в одиночку тот же запрос отвечен мгновенно; после — снова один поток
- **Аудит:** на каждый вызов инструмента строка вида
  `memory_save in personal/Probe by borodatych (claude-code, tk_legacy): done`; `grep` по секрету
  токена и по тексту записи в журнале службы — ноль совпадений

## Гейты считаются джейлом

Гейт кодов (`401` без токена, `200`, `403`, `405`, `202`), гейт плохих токенов и гейт отзыва сами
дают `401` с адреса Mac. За десять минут их набралось десять, и джейл `vibememory-mcp` забанил адрес
на час — вместе с HTTPS-клиентами владельца на этой машине. Сняли командой
`fail2ban-client set vibememory-mcp unbanip <адрес>`. Попутно это доказало, что бан доходит до
nftables, но так проверять не надо: считать свои `401` до гейта, отказы гонять с loopback (джейл
игнорирует `127.0.0.0/8`) или снимать бан сразу после.

## `access check` не паникует на закрытой трубе

Скрипт выкладки читает ответ `access check … | head -n 1`. `head` закрывает трубу после первой
строки, `println!` второй строки получал `EPIPE` и паниковал — код выхода 101 вместо вердикта 0, 1
или 2, на который опирается кабинет. Ответ теперь пишется `writeln!` с проглоченной ошибкой записи.

## Миграция токена в снимок

Первый снимок собран из файла токена прежнего сервера: отпечаток — SHA-256 содержимого без
пробельных символов (прежний сервер обрезал то, что читал), строка `tk_legacy` в личном сторе. Файл
удалён только после того, как новый сервер на loopback принял тот же токен (`200`); клиенты владельца
работают тем же значением. Агент строки — `claude-code`: заголовок `VibeMemory-Agent` больше не
читается, и до токенов на агента (фаза 4) всё, что пишется легаси-токеном, подписано так.
