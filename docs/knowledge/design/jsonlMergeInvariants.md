# Инварианты слияния JSONL: что доказано и почему правила такие (2026-09-03)

Обоснования решений `vibememory-core::merge::jsonl`. Факты о читателе и писателе —
[claudeCode/transcriptFormat.md](../claudeCode/transcriptFormat.md), контракт git —
[git/mergeDriverInvocation.md](../git/mergeDriverInvocation.md), правила в виде кейсов —
`fixtures/merge/mergeScenarios.json`.

## Порядок файла влияет ровно на две вещи

Записи читатель кладёт в карту по `uuid`, цепочку восстанавливает по `parentUuid`, сироту чинит
по времени в окне 5 с. Значит перестановка строк не меняет разговор. Порядок решает только:

1. **Состояние** (`custom-title`, `bridge-session`, `mode`, …) — карта `last-wins` по типу:
   побеждает последняя строка файла.
2. **Какую ветвь покажет resume** — лист последнего `last-prompt` (и он же попадает в заголовок).

Отсюда правило вставки: чужие строки чередуются с локальными по `timestamp`, поэтому файл
заканчивается ветвью, на которой работали позже, а состояние и лист согласованы между собой.
Глобальная сортировка запрещена: она переставила бы штатные немонотонные пары одной машины
(`dequeue → system stop_hook_summary` с разрывом до часа) и сломала бы `merge(x,x,x) = x`.

## Якорем может быть только запись с `uuid`

Блок состояния переписывается целиком при каждых ≈32 КиБ дописей, поэтому две ветви одной сессии
содержат десятки **байт-идентичных** строк состояния. Если считать их общими якорями, чужой хвост
пришивается к «своему» якорю и файл заканчивается более старой ветвью: на реальном транскрипте
это давало неверную видимую ветвь в 28–30 случаях из 54 против 0 у правила «якорь — последняя
общая запись с `uuid`».

## Кратность байт-идентичных строк — максимум, а не сумма

Ключ `(байты, номер копии)` сопоставляет k-й экземпляр k-му, поэтому после слияния копий столько,
сколько было на стороне с большим числом. Сумма ломала бы идемпотентность (`merge(x,x,x)` растил
бы файл), а множество — `last-wins` при чередовании `T1, T2, T1`. Читателю кратность безразлична:
он берёт последнюю строку типа.

Отсюда же следствие для базы: **строка без `uuid` никогда не считается удалённой**. Блок
состояния переписывается каждой машиной по своему счётчику байт, поэтому «у theirs копий меньше,
чем в базе» означает «theirs реже переписывала блок», а не «theirs удалила копию». Подчинение
таких ключей правилу удаления давало бы кратность базы вместо максимума и ложный `dropped`
(поймано ревью на 4/5/3 копиях).

## База решает членство, но не порядок; предки неприкосновенны

Git применяет одностороннее удаление **без** драйвера, а Claude Code сам удаляет записи
(tombstone, отзыв продолжения) и может включить компакцию удалённым флагом. Поэтому union,
который никогда не уважает удаление, давал бы разный ответ в зависимости от того, дописывала ли
вторая машина. Исключение — строка, которая по `parentUuid` является предком выжившей записи:
без неё ветвь другой машины осиротеет (воспроизведено на прототипе для tombstone и для GC), и
такие строки возвращаются со счётчиком `resurrected`.

Сторона, не имеющая с базой **ни одного** общего `uuid`, — не «удалила всё», а другой файл: так
выглядит новый транскрипт, созданный CLI по старому пути после перелинковки (он начинается с
блока состояния, поэтому проверка «ноль строк» его не ловит). Такая сторона объявляется
отсутствующей, и слияние идёт как union.

## Законы, которые проверяются на каждом кейсе

- `merge(x, x, x) = x` (до последнего `\n`) — иначе тик переписывал бы файл без причины.
- `merge(∅, x, ∅) = merge(∅, ∅, x) = x` — copy-import не должен зависеть от того, с какой стороны
  пришёл единственный файл.
- Мультимножество ключей не зависит от перестановки сторон (байты зависят: хребет — `ours`).
- **Закон второй машины:** `keys(merge(o, o, r)) = keys(r) = keys(merge(t, t, r))` — машина,
  получившая чужой результат, не приобретает и не теряет строк. **Предусловие:** файл машины и
  результат делят хотя бы одну запись. Форма, в которой закон ложен, найдена и закреплена тестом
  `the_second_machine_law_needs_its_precondition`: обе машины уважили удаления друг друга, в
  результате не осталось ни одной записи с `uuid` (только строки состояния), и при следующем
  слиянии своего файла с этим результатом машина видит файл, с которым у неё нет ничего общего —
  срабатывает правило «сторона отсутствует», и её запись возвращается. Выбор осознанный: слияние
  не отличает «другая машина удалила запись» от «по этому пути лежит новый файл» (реальная форма —
  транскрипт после переименования начинается с блока состояния), и между воскрешением записи и
  тихой потерей движок воскрешает. Без него закон ложен, и это не случайность: если общих
  записей нет, срабатывает правило «сторона отсутствует», база перестаёт арбитрировать, и вместо
  уважения удалений получается объединение. Фаззинг эталонной реализации (9000 случайных троек из
  окон реальных фикстур с удалениями, дублями, правками байтов, битыми строками и обрывами) дал
  181 нарушение — все до единого этой формы, ни одного иного; остальные три закона и постусловие
  нарушений не дали.
- Обычный закон поглощения `merge(r, r, a) = r` **не выполняется** и не требуется: при удалении,
  конфликте байтов или разной кратности он ложен по построению (проверено на прототипе).

## Что осталось риском

- Свежий ход другой машины, не дошедший до своего `last-prompt`, после слияния в разговор не
  попадает: видима ветвь последнего промпта. Ядро сообщает это отдельным полем (`fork.visible`),
  а не выдаёт желаемое за действительное.
- В файле > 5 МиБ строки, легшие раньше последней `compact_boundary`, читатель не загружает —
  счётчик `beforeBoundary` в отчёте существует ровно для того, чтобы CLI не обещал их
  доступность.
- Кратность keep-both растёт при слиянии двух **разошедшихся** результатов keep-both (2 + 2 → 4):
  ключ `(uuid, номер копии)` не знает, что копии описывают одну запись. Самослияние и слияние с
  машиной, у которой пара уже есть, стабильны. Читатель схлопывает копии по `uuid`, поэтому цена
  — байты в файле, а не разговор; источник у такого состояния только ручная правка.
- Лист, названный `last-prompt`, ищется лишь после последней `compact_boundary` результата
  (политика читателя для `last-prompt` — `boundary-cleared`), а если названный лист в результате
  отсутствует, видимая ветвь объявляется неизвестной, а не угадывается по хвосту.
