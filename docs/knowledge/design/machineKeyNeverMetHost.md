# Ключ машины ни разу не встретился с правилом хоста (2026-09-27)

Первое живое подключение машины к команде с сессиями отказало.
Человек ввёл свежий код в `vibememory connect`, CLI ответил:

> the cabinet refused the code: it is unknown, used or expired — make a new one

Код был ни при чём.
В журнале кабинета — настоящая причина:

> Отказ (invalidPublicKey): key mk_…: expected `ssh-ed25519 <base64>` of a 32-byte key, on one line and without a comment

## Причина

Движок делает ключ `ssh-keygen -C vibememory` и отправлял строку `.pub` целиком — с комментарием.
Снимок прав принимает ключ только без комментария: строка становится строкой `authorized_keys`, где лишнее поле — опция.
Кабинет ключ не проверяет, он проверяет кандидата снимка бинарём, и отказ бинаря превращается в общий ответ на код.

## Почему тесты молчали

Каждая сторона проверяла себя своим представлением о другой:

- Тест движка смотрел только на префикс `ssh-ed25519 `
- Тесты кабинета и фикстуры снимка брали ключ, написанный руками, без комментария
- Настоящий вывод `ssh-keygen` с правилом хоста не встречался ни разу

Тот же урок, что в [memoryNeverMetReality.md](memoryNeverMetReality.md): зелёные тесты обеих сторон ничего не говорят о стыке.

## Решение

- Правило ключа — `vibememory_core::ssh_key`: `is_ed25519_line` перенесена из сервера памяти, хост и движок зовут одну функцию
- Движок отправляет `wire_line` файла: тип и ключ, без комментария; файл `.pub` на машине комментарий сохраняет
- Не прошла строка правило — `connect` падает до кабинета со своей ошибкой, а не тратит код
- Тест `connect_keys.rs` прогоняет ключ настоящего `ssh-keygen` через `is_ed25519_line`; без правки он падает

## Второй случай — в обратную сторону, тем же вечером

С исправленным ключом код прошёл, и `connect` отказал уже на ответе:

> the cabinet's answer is not understood: a host key is not ssh-ed25519

Хост отдавал в отчёте все `ssh_host_*_key.pub` — ed25519, ecdsa и rsa, а движок берёт ключи хоста только ed25519.
Фикстуры ответа и спека отчёта показывали один ключ ed25519, и ни один тест не читал настоящий `/etc/ssh`.
Кабинет к этому моменту уже выдал ключ машины `mk_…`; его отзывает следующий `connect` той же машины.

Решение: хост отдаёт `ssh_key::host_key_lines` — только ed25519 в виде провода, той же `wire_line`.
Движок проверяет ключи хоста `is_ed25519_line`, а не префиксом; `ED25519_PREFIX` удалена.
Тест делает ключи трёх типов настоящим `ssh-keygen`, пропускает их через функцию хоста и отдаёт результат разбору ответа движка.

## Правило

Договорённость двух сторон проверяется **настоящим выводом одной стороны против кода правила другой**, а не двумя копиями представления о формате.
