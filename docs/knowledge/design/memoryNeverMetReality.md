# Память как записи ни разу не встретилась с реальным файлом (2026-09-09)

Слой «память — это записи» написан, покрыт двадцатью кейсами фикстур, задокументирован спекой и
подключён к хукам. На машине владельца он **не обработал ни одного настоящего файла памяти** —
и это выяснилось только когда MCP-сервер, читающий журнал, вернул пустоту.

## Измерение

```
журналов memory.jsonl в сторе:            0
файлов памяти в markdown:               135
из них с полем `title` во frontmatter:    0
```

Штатный хук остановки, прогнанный руками для Promed, ответил двадцать одной строкой одного вида:

> VibeMemory could not read the memory document `promed-branch-names.md`: frontmatter has no
> title. The file is left as it is.

## Причина

Реальный файл памяти Claude Code выглядит так:

```yaml
---
name: promed-branch-names
description: "Ветка `d-PROMEDWEB-259846` — это наша `deadborn`, а не соседняя задача"
metadata:
  node_type: memory
  type: project
  originSessionId: e303dd59-ad00-47b4-94a6-76fd3936ad41
  modified: 2026-08-14T07:46:19.118Z
---
```

Поля `title` в нём **нет вовсе**. Человеческое имя живёт не в файле, а в строке индекса
`MEMORY.md`. Её строка устроена так (показано без markdown-разметки, чтобы гейт ссылок не принял
пример за ссылку):

```
- [Заголовок]{имя файла}.md — крючок
```

Наш `Record` требует `title`, `parse_document` делает `required(&top, "title")?` — и отвергает
каждый файл.

Заодно видно, что в `metadata` есть поля, которых наша модель не знает: `node_type`,
`originSessionId`, `modified`.

## Чем это обернулось

Отказ разбора не роняет ничего и не теряет данных — файл остаётся на месте, и это правильно. Но
цепочка следствий длинная и вся тихая:

1. ни один документ не импортируется → журнал не создаётся никогда;
2. память не становится записями → у неё нет ни причинности `parent`, ни соперничающих версий, ни
   событий удаления, ни статуса `stale`, который добавляли накануне;
3. между машинами память ездит **как обычные файлы стора** — это работает, но это ровно та
   модель, от которой уходили: одновременная правка на двух машинах разрешается keep-both по
   файлам, а не по записям;
4. MCP-сервер, читающий журнал, честно отвечает «ничего не найдено» — и выглядит сломанным, хотя
   написан верно.

## Как это прошло мимо всех гейтов

Двадцать кейсов фикстур проверяют разбор, свёртку, проекцию и импорт — и **все двадцать написаны
от нашей модели**, а не от наблюдённого файла. `provenance` у них `computed`, и это честно
проставлено; никто не заметил, что ни одного `observed` среди них нет.

Правило, которое из этого следует, шире памяти и сильнее уже записанного в
[desktopCardsLayout.md](desktopCardsLayout.md) («факт из knowledge обязан появиться в фикстуре»):

> **Формат, который пишет чужая программа, обязан войти в фикстуры своим настоящим файлом.**
> Кейс с `provenance: computed` доказывает, что код соответствует нашему представлению. Ровно
> это здесь и было доказано — двадцать раз подряд.

Дешёвая проверка, которой не было: взять один настоящий файл с диска и прогнать через разбор.
Она заняла бы минуту и сэкономила бы весь слой.

## Что чинить (решение владельца)

`title` не может быть обязательным. Варианты, от менее к более честному:

1. выводить заголовок из `name` (слаг → человеческий вид), когда поля нет;
2. брать его из строки индекса `MEMORY.md`, где он и живёт на самом деле;
3. признать, что заголовка у записи нет, и хранить только `name` + `description`.

Второй ближе всего к реальности, но привязывает разбор одного файла к другому. Кроме того,
неизвестные поля `metadata` (`node_type`, `originSessionId`, `modified`) надо сохранять при
перезаписи проекции, иначе движок будет затирать то, что писал CLI.

До этого решения MCP-сервер работает правильно и показывает пустую память, потому что она пуста
как **записи** — а не потому, что сервер сломан.
