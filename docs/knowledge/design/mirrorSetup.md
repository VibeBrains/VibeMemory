# Бэкап стора в чужой git-хостинг: как он устроен и почему именно так

Стор живёт на своём хосте (bare-репозиторий), а бэкап — зеркало в приватный репозиторий у
провайдера. Сделано вживую 2026-09-08 на GitHub (`VibeBrains/VibeMemoryStore`); всё ниже
написано так, чтобы повторялось на GitLab, Gitea, Codeberg или своём втором сервере — от
провайдера зависит только один шаг из шести.

## Топология: почему пушит хост, а не клиент

```
машина 1 ─┐
машина 2 ─┼─push→ хост (bare, источник правды) ─post-receive→ зеркало (приватный репо)
машина N ─┘
```

Клиент не знает о зеркале ничего и ключа к нему не имеет. Причины:

- **Ключ один и лежит в одном месте.** Дать доступ к бэкапу каждой машине — значит раздать
  ключ на запись во все транскрипты стольким устройствам, сколько их есть, включая те, что
  теряются.
- **Клиент не ждёт зеркало.** Пуш в зеркало происходит после того, как хост уже принял пуш
  клиента; недоступное зеркало пуш **не отклоняет** (`|| echo ... >&2` в хуке) — иначе упавший
  GitHub останавливал бы работу на всех машинах.
- **Порядок гарантирован.** Зеркало повторяет состояние хоста, а не гонку двух машин.

## Шесть шагов

1. **Приватный репозиторий у провайдера, пустой.** Именно пустой: `push --mirror` приводит
   удалённую сторону к состоянию хоста и снесёт всё, чего на хосте нет — README, созданный
   мастером «создать репозиторий», исчезнет при первом же заливе. Приватность проверять
   фактом, а не намерением (`gh repo view --json isPrivate`).
2. **Отдельный ключ на хосте**, `ssh-keygen -t ed25519 -N '' -f ~/.ssh/storeMirror`. Приватная
   часть никогда не покидает хост — наружу отдаётся только `.pub`.
3. **Отдельный ssh-алиас, а не `Host github.com`.** Имя алиаса — `storeMirror`, по назначению, а
   не по провайдеру: первая версия звалась `githubMirror`, и это имя противоречило тому, что
   схема работает с любым хостингом. `mirrorSetup.sh` переносит ключ со старого имени, а не
   заводит новый (новый не был бы зарегистрирован у провайдера) и убирает осиротевший блок из
   `~/.ssh/config`. Проверено переносом живого хоста 2026-09-08. Глобальная запись перехватила бы любой
   другой доступ к тому же хостингу с этого сервера. `IdentitiesOnly yes` обязателен: без него
   ssh сначала переберёт все ключи агента и может быть отвергнут по лимиту попыток, имея
   верный ключ в кармане.
   ```
   Host storeMirror
     HostName github.com
     User git
     IdentityFile ~/.ssh/storeMirror
     IdentitiesOnly yes
   ```
4. **`known_hosts` заранее** (`ssh-keyscan -t ed25519 github.com >> ~/.ssh/known_hosts`). Хук
   `post-receive` работает без терминала: незнакомый хост он не спросит, а молча провалится.
5. **Ключ регистрируется как deploy key с правом записи** — единственный шаг, зависящий от
   провайдера. GitHub: `POST /repos/{owner}/{repo}/keys` с `read_only=false` (в UI —
   Settings → Deploy keys → Allow write access). GitLab: deploy key с `can_push=true`. Gitea:
   deploy key, снять «Read only». Свой сервер: строка в `~/.ssh/authorized_keys`. Deploy key
   лучше личного токена: он привязан к одному репозиторию, а не ко всей учётной записи.
   Проверять фактом: `ssh -T githubMirror` с хоста должен назвать репозиторий.
6. **Хук `post-receive`** ставится `infra/hostBootstrap.sh --mirror <url>`; весь шаг целиком
   (2–6) делает `infra/mirrorSetup.sh --repo owner/name`.

## Пуш в зеркало — фоном, и первый залив тоже

Хук `post-receive` выполняется, пока клиент ещё держит свой push открытым. Синхронный
`git push --mirror` внутри него означает, что **каждая машина ждёт провайдера**, а зависший
провайдер останавливает тик, который этот push и начал. Поэтому хук запускает пуш отделённым
(`&` + `disown`) под `flock -n`: пачка пушей подряд не поднимает стопку заливок одного и того же
репозитория, а пропущенный из-за блокировки запуск ничего не стоит — следующий push везёт те же
ссылки. Лог — `~/vibememory-mirror.log` на хосте. Замер 2026-09-08: push клиента 6.5 с (это
дорога до VPS), зеркало догнало за секунды после.

Цена решения: об ошибке зеркалирования клиент не узнаёт в момент пуша — её ловит суточная
проверка тика и строка `doctor`. Это осознанный размен: бэкап может отставать на секунды и
минуты, а работа машин не может ждать чужой сервис.

## Первый залив — вне хука

Первый `push --mirror` — это весь стор целиком (у нас 619 МБ). Внутри `post-receive` он
выполняется **синхронно**: клиент, чей пуш его вызвал, ждёт эти минуты, а тик на клиенте имеет
таймаут. Поэтому первый залив запускается на хосте отдельно и фоном
(`nohup git push --mirror ... > ~/mirror-seed.log`), а хук потом возит только дельты. Проверено:
залив прошёл за ~40 секунд, последующие пуши доезжают меньше чем за 10.

Своя грабля из этой же серии: пуш стора **с Mac на VPS** в 780 МБ рвался на 17-й минуте и не
возобновлялся — там пришлось везти пак-файлы `rsync --partial`. Пуш **с VPS на GitHub** такой
проблемы не имел: канал у сервера лучше домашнего. Не переносить вывод одного плеча на другое.

## Что проверяет `doctor`

`vibememory doctor` печатает строку зеркала: спрашивает хост одной ssh-командой — есть ли хук,
какой в нём URL, совпадает ли голова хоста с `git ls-remote` зеркала. Расхождение — отказ
(`is_fault`), отсутствие зеркала — не отказ: бэкап необязателен. Смысл в том, что **бэкап,
который никто не проверял, бэкапом не является**: хук молчит по замыслу, и без этой строки
сломанное зеркало не проявилось бы никогда. Чистые части (разбор remote, разбор хука, вердикт
по двум головам) — в `crates/vibememory-cli/src/mirror.rs`, гейт
`tests/mirror_probe.rs` проверен четырьмя мутациями.

## Ограничения, о которых узнают поздно

- **Руками в зеркало не коммитить.** `--mirror` — односторонняя операция: любой коммит,
  сделанный на стороне провайдера, будет стёрт следующим пушем хоста.
- **Размер растёт вместе с транскриптами.** На 2026-09-08: пак 590 МиБ, крупнейший объект
  38 МиБ. Жёсткий предел GitHub — 100 МБ на файл, мягкое предупреждение по репозиторию — около
  1–5 ГБ; у GitLab и Gitea свои. Один транскрипт когда-нибудь упрётся в предел файла, и это
  вопрос не «если», а «когда»: транскрипт растёт монотонно.
- **Еженедельный `gc` на хосте** (`gc.auto=0` + cron) — иначе неупакованный репозиторий
  растёт без предела и зеркалирование дорожает вместе с ним.
- **Ключ — на хосте, а не в репозитории продукта.** В коде нет ни URL зеркала, ни имени
  владельца: URL живёт в тексте хука на хосте, и `mirrorSetup.sh` принимает его аргументом.
  Это же условие делает продукт пригодным к открытому исходному коду: у каждого пользователя
  своё зеркало, и ничьё чужое имя не вкомпилировано.

## Кто читает хук: один парсер, а не два

Первая версия проверки в `doctor` доставала URL из хука `grep`-ом на хосте, а в Rust лежала
функция `url_in_hook`, которую никто не звал: гейт проверял неиспользуемый разбор, а работал
непокрытый шелловый. Формат читается **в одном месте** — хост печатает текст хука целиком,
разбирает Rust. Цена — второй ssh-вызов (ls-remote умеет только хост, ключ у него), и она
того стоит: правило чтения формата под гейтом, а тест прямо запрещает `grep` в этой команде.

## Бэкап проверяет себя сам

`doctor` спрашивает про зеркало только когда его запустил человек, а человек не запускает его
по расписанию. Поэтому тик раз в сутки задаёт тот же вопрос сам; отставшее зеркало он
записывает в те же ожидающие заметки, что и отчёты о слияниях, и следующая сессия слышит это
первой строкой. Недоступный хост ответом не считается — таймер не сдвигается, вопрос повторится
на следующем тике, а не через сутки. Часы, ушедшие назад, делают проверку срочной, а не
отменяют её навсегда.

## Мелочи, которые ломают всё в неудачный день

- **URL из хука уходит обратно на хост внутри shell-команды.** Поэтому он принимается только
  без кавычек, пробелов, `$`, backtick и разделителей команд: хук, отредактированный руками,
  должен падать громко, а не выполняться тихо. Гейт на это — в `mirror_probe.rs`.
- **Скрипт настройки не спрашивает, когда спрашивать некого.** `read -p` в неинтерактивном
  запуске (cron, пайп, чужой скрипт) висел бы вечно; теперь при `! -t 0` скрипт говорит, чего
  не хватает, и выходит с ошибкой.
- **Колонка отчёта и фраза — разные вещи.** `describe()` собирается из `summary()`, а не
  наоборот: заметка сессии, которая срезала бы префикс `mirror   ` строкой, сломалась бы от
  любой правки выравнивания.
