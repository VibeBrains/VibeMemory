# Мутационная проверка гейта: как её проводить, чтобы она что-то значила

Правило проекта — гейт, прошедший с первого раза, ничего не доказывает: тест обязан падать,
если сломать проверяемое поведение. Практика 2026-09-08 добавила к правилу три оговорки,
каждая куплена ошибкой.

## 1. Проверять, что мутация применилась

Мутации вносились `perl -0pi -e 's/…/…/'`. Если регулярка не совпала (экранирование, перенос
строки, `cargo fmt` переформатировал), файл остаётся прежним — и тест, разумеется, проходит.
Это выглядит **точно так же**, как выживший гейт, и толкает «усиливать» тест, который и так
был в порядке. Один такой ложный вывод был сделан и вовремя пойман: тот же случай, переписанный
подстановкой с `assert old in s`, гейт убил.

**Как правильно:** мутация вносится способом, который падает, если цель не найдена
(`assert` на паттерн), или после правки печатается diff. «Тест прошёл» без доказательства, что
код изменился, — не результат.

## 2. Слабая фикстура прячет силу гейта

Первая версия теста про открытые хендоффы пережила мутацию «читать статус из всего файла, а не
из фронтматтера» — потому что в фикстуре строка в теле была `status: open in my head`, а сравнение
шло по точному совпадению строки. Фикстура должна содержать **ровно тот** текст, который ломает
проверку: строку `status: open` в теле, отдельной строкой.

## 3. Не всякое поведение доказуемо на этой машине

Сортировка списка хендоффов мутацию пережила и переживёт: APFS отдаёт `read_dir` уже в
алфавитном порядке, а сортировка нужна для файловых систем, которые возвращают хэш-порядок
(ext4). Такое место честнее назвать в самом тесте комментарием, чем делать вид, что оно под
гейтом, — и не выбрасывать код, который не с чем сравнить.

## Что мутировать

Мутации, которые реально что-то показали: убрать отсев комментария при разборе, посчитать пустое
значение синхронным, снять признак «это отказ», расширить приём входа (https вместо ssh), снять
отступление при недоступном хосте, склеить путь без учёта `~/`. Общее у них одно: каждая —
правдоподобная будущая правка, а не случайная порча синтаксиса.

## Коммит нельзя ставить строкой после гейта (2026-09-09, дважды за день)

Скрипт вида

```
python3 - <<'PY' ... PY          # правка
cargo test -p … --test docs_integrity
git add -A && git commit -m …
git push
```

выполняет коммит и пуш **независимо** от того, упал ли гейт: строки не связаны кодом возврата.
За один день это случилось дважды — в `next` уехали файл без строки в индексе и падающий гейт
документации, оба раза с сообщением коммита, обещавшим сделанное целиком.

Форма, у которой этого не может быть: одна цепочка, где каждое звено зависит от предыдущего.

```
правка && гейт && cargo test && git add -A && git commit -m … && git push
```

Правило шире git: **действие, которое нельзя откатить, не ставится строкой после проверки — оно
ставится за `&&`.** Отдельная строка выглядит как последовательность, но ею не является.

Звено цепочки обязано отвечать **кодом возврата самой проверки**, а не числом, вытащенным из её
вывода. `grep -c` при нуле совпадений печатает `0` и выходит с кодом **1**, поэтому в голом виде
`F=$(cargo test | grep -c FAILED) && git commit` смысл переворачивается целиком: на зелёном прогоне
цепочка обрывается, на красном — коммитит. Попалось 2026-09-11 и сработало в безопасную сторону
только потому, что за присваиванием стояла ещё одна проверка. Звено — это `cargo test && …`, с его
собственным кодом.

## Откат мутации — записью файла, а не `mv` из копии (2026-09-23)

Мутацию откатывали так: `cp файл файл.orig`, правка, прогон, `mv -f файл.orig файл`. Копия получает
время изменения в момент `cp` — раньше, чем правка-мутант. После `mv` у исходника время **старее**
последней сборки, и cargo, сверяющий время изменения, считает сборку свежей: следующий прогон
тестов идёт на бинаре мутанта. Выглядело как настоящий провал исправленного кода — и полчаса ушло бы
на поиск дефекта, которого нет, если бы путь в сообщении об ошибке не выдал старое поведение.

Правило: вернуть исходник **записью** (`open(p, 'w').write(orig)` или `cat копия > файл`) — время
станет новым, и cargo пересоберёт; или `touch` после `mv`. И после отката — один прогон на чистом
коде до того, как верить его результату.
