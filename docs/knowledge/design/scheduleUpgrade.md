# Файл расписания прежней версии

**30.09.2026**, GPD, первый выпуск после смены триггеров Windows.

## Что случилось

`install.ps1` поставил 0.4.0 на GPD, где раньше стояла 0.3.0.
Двоичные файлы встали, а на шаге расписания установка остановилась:
_left alone: scheduled tick — found …\tick-task.xml holds something else_

Файл задания написала 0.3.0: с триггерами входа и разблокировки.
В 0.4.0 задание — один таймер (`windowsReadiness.md`, «Планировщик без администратора»).
Шаг сверял файл с ожидаемым по байтам, находил расхождение и считал файл чужим.
Чужое движок не трогает — и собственный старый файл оказался под той же защитой.

## Почему это общий дефект

Любой выпуск, меняющий описание расписания, упёрся бы в свой же старый файл на каждой машине.
Это касается всех трёх систем: задания Windows, `LaunchAgent` macOS, таймера и сервиса systemd на Linux.
Хуки и драйверы слияния уже различали «наше от прежней установки» и «чужое» — расписание не различало.

## Как теперь

- **Свой файл узнаётся по тому, что пишет только движок:**
  - метка `dev.vibememory.tick` в `.plist`;
  - описание `VibeMemory: keeps this machine's store in step with the others` в задании Windows (UTF-16);
  - строка `Description=VibeMemory` в юнитах systemd.
  Описание — одна константа: одна и та же строка и пишется, и распознаётся.
- **Свой старый файл** шаг показывает как «нужно поставить», и установка заменяет его целиком: временный файл, затем переименование.
- **Чужой файл** остаётся конфликтом.
  Появившийся между планом и установкой тоже не перезаписывается: перед записью файл проверяется ещё раз.
- **macOS:** launchd продолжает исполнять агента, которого загрузил, по старому описанию.
  Поэтому при замене перед `bootstrap` идёт `bootout`.
  На Windows `schtasks /F` заменяет задание сам, на Linux `daemon-reload` уже был.

Гейты — в `install_plan.rs`: распознавание на точном задании 0.3.0 и на чужих файлах трёх систем; замена старого агента и отказ трогать чужой, в том числе появившийся после плана.
Каждый роняется подменой.
