# Стенд своего сервера: что нашёл первый живой прогон (2026-10-07)

Консоль хоста и гранты были проверены тестами, а путь «чистый сервер → машина участника с сессиями» не прошёл никто:
наш хост с кабинетом, и консоль там отказывает.
Стенд — `infra/selfHostLab.sh`: две машины Debian 13 под Lima на Mac владельца, хост без кабинета и машина участника.
Хост поднимается ровно по [selfHosting.md](../../manuals/selfHosting.md), так что проверяется и мануал.
Как прогонять — [selfHostLab.md](../../manuals/selfHostLab.md).

## Находки

В порядке, в котором их встречает человек, идущий по мануалу.
Шаги с пометкой WORKAROUND в скрипте обходят находку, чтобы прогон дошёл до конца; они уходят вместе с исправлением.

1. **`hostBootstrap.sh` требует git и сам его не ставит.** Скрипт останавливается со строкой
   «Установите: sudo apt-get install -y git», а мануал о пакетах молчит.
   Соседние скрипты ставят свои пакеты сами: `caddyApply.sh` — caddy, `backupSetup.sh` — age. WORKAROUND
2. **В облачном образе Debian 13 нет cron.** Ночная упаковка личного стора не ставится, и `hostBootstrap.sh` говорит об
   этом одной строкой. Упаковка сторов команд в `hostMcp.sh` идёт таймером systemd и встаёт
3. **`hostMcp.sh --owner` на чистом сервере падает.** Первый снимок прав он умеет собрать только из файла токена
   прежнего однотокенного сервера (`~/vibememory/mcp-token`), то есть только при переезде.
   Шаг 2 мануала на новом сервере не проходит. WORKAROUND — тестовый файл токена
4. **fail2ban не установлен — джейл `/mcp` пропущен.** Скрипт предупреждает, мануал не говорит его поставить
5. **Машина участника без личного стора не настраивается.** `vibememory install` без `config.json` только кладёт
   программы. `connect --grant` с ключом отказывает: «движок не установлен, запустите `vibememory install`». Круг.
   Ключ машины при отказе выбрасывается, и каждая попытка — это отзыв на хосте и новый `--key-request`.
   Выход только руками: `config.json` с одним `machineId` по [configSpec.md](../../manuals/configSpec.md). WORKAROUND
6. **Отказ хоста не виден, пока машине нечего отправлять.** Тик делает `git fetch` каждый раз, но ошибку fetch
   использует только для проверки «сессии команды выключены»: в `problems` и счётчик неудач она не попадает.
   Отозванный ключ или недоступный хост молчат, машина перестаёт получать чужие сессии, а `doctor` пишет «in step».
   Отказ при push считается: три подряд — пауза цикла и строка `N failing run(s)` в `doctor`
7. **Сессии, начатые после `route add`, остаются только на машине**, если в каталоге проекта уже были сессии.
   Хук `SessionStart` не может сразу перевести такой каталог на стор (`ImportNeeded`) и обещает сессии: «её импортирует
   следующий тик, ничего не потеряется». Тик импортирует каталог и помечает «только на машине» всё скопированное
   (`local_only::keep` по `outcome.copied`), не отличая сессии до маршрута от сессий после.
   Граница «до команды» на деле — первый импорт, а не `route add`
8. **Закончившаяся сессия в настоящем каталоге час числится живой.** `SessionEnd` для транскрипта вне клона стора
   выходит сразу и запись в `live.json`, сделанную `SessionStart`, не снимает. Её снимет только устаревание через
   `HEARTBEAT_STALE_AFTER` — час. Всё это время тик не импортирует проект: каталог с живой сессией не трогается.
   Из-за этого находка 7 на стенде видна не сразу: проверка упирается в восьмую
9. **`seedKey.sh` знает один хост:** алиас прибит к `vibememory`. Второй хост — стенд или переезд — засевается руками

Проверки стенда утверждают обещанное поведение, поэтому находки 5–8 падают в `check` красным, пока их не починят.
Находки 1 и 3 — строки «находка:» в `up` с обходом.

## Что подтвердилось

- `connect --key-request` → `admin key add` → `connect --grant`: ключ делает машина, хост получает только открытую
  половину, грант несёт ключи хоста
- Клон ходит своей командой ssh: свой ключ, `known_hosts` команды из гранта, `StrictHostKeyChecking=yes`, `-F none`
- Сессия, начатая после маршрута в проекте без старых сессий, доезжает до хоста первым же тиком
- Сессия до маршрута остаётся на машине (`.git/info/exclude` клона)
- Отзыв ключа: применение снимка убирает строку из `authorized_keys` `vmgit` за секунды, следующий push отвергнут

## Грабли стенда

- **vzNAT изолирует машины друг от друга:** Mac видит обе, а машина участника хост — нет (`No route to host`).
  Вторая сеть Lima `user-v2` соединяет машины между собой и не требует root.
  Mac ходит на хост по адресу vzNAT, участник — по адресу `user-v2`
- **Сеть, добавленная после первого старта, меняет ключи ssh хоста:** cloud-init принимает изменённую конфигурацию за
  новую машину. Обе сети задаются при создании
- **Lima кладёт образы в `~/Library/Caches/lima`:** на macOS это `os.UserCacheDir`, переменной для него нет.
  Каталог перенесён в `/Volumes/Storage/Caches/lima-cache`, на старом месте — ссылка; скрипт её проверяет
- **Имя хоста без `/etc/hosts`:** `192-168-104-1.sslip.io` отвечает адресом `192.168.104.1`.
  Клиент ходит по имени из гранта с `-F none`, так что алиас ssh ему не помогает
- **Каждый `check` — своя команда:** запись машины в сторе команды переживает машину. Новая машина с тем же
  `machineId` в старой команде наследует `live.json` прошлого прогона
- HTTPS `/mcp` на стенде не проверяется: Caddy не получит сертификат на частный адрес
