# Ужесточение ssh на хосте стора: порядок, при котором нельзя запереться (2026-09-09)

Хост стора — единственная машина, потерять доступ к которой нельзя: на ней лежит общий git всех
машин владельца. Поэтому ценность здесь не в самих настройках (их три строки), а в порядке, при
котором ошибка не стоит хоста.

## Что было и что стало

`sshd -T` до: `permitrootlogin yes`, `passwordauthentication yes`, `maxauthtries 6`. То есть root
по паролю был разрешён.

Стало (drop-in `/etc/ssh/sshd_config.d/10-vibememory-hardening.conf`, главный конфиг не тронут):
`PermitRootLogin prohibit-password`, `PasswordAuthentication yes`, `MaxAuthTries 3`.

**Пароль пользователю оставлен осознанно, решением владельца:** его IP меняется, поэтому
ограничение по адресу не годится, а имя пользователя не типовое. Это защита неизвестностью, и
называть её иначе нечестно — см. цифры ниже.

**`prohibit-password` для root здесь означает «root не зайдёт вообще»,** а не «root по ключу»:
`/root/.ssh/authorized_keys` пуст. Это выяснилось до правки и не изменило решения (владелец ходит
пользователем `vm`, у него два ключа и passwordless sudo), но узнать это следовало заранее — иначе
формулировка «запретить root пароль» звучит мягче, чем её последствие.

## Порядок, при котором нельзя запереться

1. **Сначала доказать, что ключ работает** — до всякой правки. Не «он же работал вчера».
2. **Drop-in, а не правка главного конфига.** Откат — удаление одного файла, а не восстановление
   отредактированного.
3. **`sshd -t` до применения.** Битый конфиг не доедет до живого демона вовсе.
4. **Страховка по таймеру, вооружённая до перезагрузки конфига:** фоновый процесс, который через
   120 секунд удаляет drop-in и перезагружает `ssh`, если не появился файл-маркер. Маркер ставится
   **из нового соединения** — то есть отменить откат может только тот, кто реально смог войти
   после изменений.
5. **`reload`, а не `restart`.** Живые соединения переживают перезагрузку конфига; при `restart`
   единственная работающая сессия рвётся ровно в тот момент, когда она нужнее всего.
6. **Проверка новым соединением**, и только потом объявлять успех.
7. Дождаться закрытия окна страховки и убедиться, что drop-in **на месте** — иначе успех был
   мнимым: откат мог сработать, а проверка — пройти по старому конфигу.

## Проверка фактом: первая попытка ничего не доказала

Проверять «root по паролю теперь нельзя» так:

```
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no -o NumberOfPasswordPrompts=0 root@host
```

бесполезно: ответ `Permission denied (publickey,password)` приходит и для `root`, и для `vm`,
потому что пароль не был предложен вовсе. Список методов в этой строке — глобальный, он не
зависит от пользователя, и по нему политику не прочитать.

Доказательства оказались два, оба на стороне сервера: `sshd -T -C user=root,...` — политика
именно для этого пользователя, и журнал `journalctl -u ssh` — что произошло на самом деле.

## Что показал журнал: перебор идёт непрерывно

За один час на хосте:

| Измерение | Значение |
|---|---|
| Неудачных попыток пароля | 615 |
| из них по `root` | 66 |
| Уникальных атакующих адресов | 290 |
| Входов принято по ключу (наш тик) | 83 |
| Входов принято по паролю | **0** |

Это обычный фон для любого ssh на публичном адресе, и именно поэтому его стоит измерить, а не
представлять: 290 адресов в час непрерывно проверяют, насколько «непопулярное имя пользователя»
— защита. Ноль принятых паролей — сегодняшнее состояние, а не гарантия.

## `fail2ban` поставлен — и чуть не оказался декорацией

Владелец решил ставить, цена названа заранее: бан действует на **весь адрес, включая вход по
ключу**, — пять промахов паролем стоят и ключевого доступа с этого адреса на время бана. Поэтому
`bantime.increment` (первый бан час, повторным растёт) и `mode = normal`, а не `aggressive`:
агрессивный считает нарушением и разрыв соединения до аутентификации, что бывает у законного
клиента.

Свой текущий адрес в `ignoreip` намеренно **не вписан**: он меняется, а вписанный однажды остался
бы исключением навсегда — в том числе для того, кому этот адрес достанется после владельца. Обычный
путь владельца — ключ, а он не даёт неудачных попыток вовсе.

**Главное, что стоит запомнить.** Через минуту после установки джейл показывал
`Currently banned: 2` — и не блокировал ничего. На этом хосте **нет ни `iptables`, ни `nft`**:
минимальный Debian 12. Служба `active`, счётчики растут, список забаненных заполняется — а
действие `iptables-multiport` выполнить нечем, и баны живут только в базе самого fail2ban.

Поймано единственной проверкой, которую стоит делать всегда: сверить список джейла с реальным
набором в firewall.

```
sudo fail2ban-client status sshd                            # что он думает
sudo /usr/sbin/nft list set inet f2b-table addr-set-sshd    # что на самом деле
```

Списки обязаны совпадать. После установки `nftables` и переключения на `banaction =
nftables-multiport` они совпали: `elements = { 67.227.251.15, 176.53.159.198 }`.

Службу `nftables` при этом включать не стали: fail2ban заводит собственную таблицу
`inet f2b-table`, а включённая служба подгрузила бы `/etc/nftables.conf` — это отдельная правка,
и делать её заодно нельзя.

Мелочь, стоившая одного прохода: `nft` лежит в `/usr/sbin`, которого нет в `PATH`
неинтерактивной ssh-сессии, поэтому `command -v nft` вернул пустоту на хосте, где nft стоял.

## Общая форма всех трёх ошибок этого дня

Проверка клиентом вместо сервера; служба `active` вместо «делает то, что обещает»; `command -v`
вместо полного пути. Каждый раз проверялся **признак**, а не **следствие**. Правило, годное шире
ssh: спрашивать не «включено ли», а «произошло ли то, ради чего включали».
