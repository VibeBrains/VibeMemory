# Рост стора: замер для квот и резерва (2026-09-23)

Фаза 0 этапа 6: квоты командных сторов и резерв места хоста выводятся из того, как на самом деле
растёт стор одного человека. Стор владельца — единственная живая выборка.

## Как мерили

Для каждого дня: объекты, достижимые из `main` на конец дня и недостижимые на начало, и их размер
на диске (`git rev-list --objects <конец> ^<начало> | git cat-file --batch-check='%(objectsize:disk)'`).
Считалось на Mac, где стор упакован с дельтами.

**Оговорка, без которой цифры врут:** объекты последних двух дней на Mac ещё лежат отдельными
файлами, без дельт, — `count-objects` показывает 487 отдельных объектов на 188 МиБ. Их «размер на
диске» завышен в разы: 23.09 вышло 214,7 МиБ за день при 147 коммитах. Поэтому для оценки взяты
только упакованные дни, 10–20.09, а сверка — по ночным отчётам упаковки старого хоста, где всё уже в
пакетах.

## Что из этого следует

**Один человек — 6–9 ГБ в год.** Диск нового хоста 50 ГБ: одному владельцу хватит на несколько лет,
и первым кончится именно диск, а не память или процессор.

**Квота `sync`-команды в 10 ГБ (решение 14) у тройки кончится примерно за полгода.** Три активных
участника — 50–75 МиБ в сутки.

**Главное: git-стор только растёт.** История транскриптов не удаляется ни одной операцией движка, и
`forget` снимает файл из дерева, а не из истории. Значит квота, достигнутая один раз, не освободится
никогда: команда навсегда станет «только на чтение» по коду `quota`. Квота без механизма сжатия
истории — не лимит, а таймер. К фазе 5 (`sync`) это решение владельца: архив старой истории в
отдельный репозиторий с новым корнем, срок хранения транскриптов или квота, считающая только
текущее дерево. В плане — раздел 8.

**Резерв места хоста 2 ГиБ** — около 80 суток роста одного человека и четыре-шесть недель роста
команды из трёх. Этого хватает, чтобы письмо о пороге успело дойти.

**Режим `memory` квоты почти не расходует:** в нём живут только журналы памяти — килобайты на проект.
