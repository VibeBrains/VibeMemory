# Стор команды на хосте: от первого коммита до переименования (фаза 2, 2026-09-23)

Сторы команд живут в `/srv/vibememory/teams/<слаг>.git`, и держит их в порядке одна команда —
`vibememory-mcp access-apply` под `vmgit`, при каждой смене снимка прав. Решение — чистый модуль
`crates/vibememory-mcp/src/apply.rs` под фикстурой `fixtures/host/applyPlans.json`, исполнение —
`hostops.rs`. Правила — в плане этапа 6 (2.5), коды проблем —
[hostStatusSpec.md](../../manuals/hostStatusSpec.md).

## Правила каталога

| Снимок | Каталог | Что делается |
|---|---|---|
| команда без `deleted` | `<слаг>.git` есть | настройки и хук заново, `.gitattributes` сверяется |
| команда без `deleted` | нет, и нет `<слаг>.deleted-*` | создать, первый коммит |
| команда без `deleted` | нет, но есть `<слаг>.deleted-*` | ничего; `slugRetired` |
| `deleted: <дата>` | `<слаг>.git` есть | переименовать в `<слаг>.deleted-<дата>.git` |
| `deleted: <дата>` | есть и `<слаг>.git`, и `<слаг>.deleted-<дата>.git` | ничего; `retireBlocked` |
| слага нет | любой | не трогать; в отчёте — `orphans` |

Удаления нет ни в одной строке. Слаг удалённой команды не получает новый пустой стор: он выглядел бы
как пропавшая память. `retireBlocked` в плане не было: переименование каталога поверх непустого
каталога падает, и план сам видит оба имени — лучше назвать проблему, чем получить ошибку `rename`.

## Первый коммит и эволюция `.gitattributes`

Без `main` сервер памяти не запишет ни одной записи, а клон участника увидит пустой репозиторий.
Поэтому применение делает первый коммит само: единственный файл `.gitattributes` с текстом движка
(`vibememory_cli::install::GITATTRIBUTES`) байт в байт.

Одна операция на оба случая — `GitMemories::settle_file`: если `main` уже держит нужный текст —
ничего; иначе коммит поверх `main`, а в репозитории без `main` — первый. Временный индекс вне
репозитория, `read-tree --empty` вместо `read-tree <старый>`, `commit-tree` без родителя и
`update-ref` с пустым старым значением — «ветки ещё быть не должно». Движение `main` — тот же
compare-and-swap, что у записи памяти: push, пришедший между, сохраняет свой коммит, а попытка
повторяется на нём.

Больше `.gitattributes` не меняет никто: `pre-receive` не пускает путь, а `install` для командного
стора его не пишет.

## Негодный снимок не меняет ничего

Снимок, не прошедший `access check`, не применяется ни в какой части: ни сторы, ни ключи машин.
`applied.json` сохраняет хеш, время и `teamCount` последнего годного снимка, а в начало `problems`
встаёт `snapshotRejected` с кодом проверки. Если годного снимка не было ни разу, файл не пишется.

Материал ключей тоже проверяет `access check`, для всего снимка сразу. Поэтому код `keyInvalid` из
первого проекта спеки снят: снимок с негодным ключом отвергается целиком, и строка
`authorized_keys` без `restrict` появиться не может ни при каком снимке.

## Смена снимка во время применения

`.path`-юнит запускает `access-apply` при смене `access.json`. Применение — `Type=oneshot`, и
запуск, который приходит, пока идёт предыдущий, systemd сливает с идущим: вторая публикация ждала
бы третьей. Поэтому `access-apply` после прохода перечитывает файл и, если байты уже другие,
применяет снова — до трёх проходов за запуск.

_Слияние запусков выведено из устройства path- и oneshot-юнитов systemd; вживую не воспроизведено —
окно шириной в один проход применения._

## Что показали живые гейты (2026-09-23)

- Три тестовые команды из снимка — три стора с единственным `.gitattributes`, SHA-256 совпал с
  файлом личного стора на Mac. Подменённый старый текст в `main` вернулся коммитом поверх, а клон на
  Mac получил его обычным fast-forward: подмена сделана коммитом поверх, а не новым корнем, иначе
  fetch был бы вынужденным.
- Снимок без команды не тронул каталог — тот же inode, в отчёте сирота с `projects` и `machines`.
  Удалённая команда переименована с тем же inode, повтор ничего не меняет; слаг, возвращённый в
  снимок, получил `slugRetired` и нового стора не получил.
- `host.json` после применения и после таймера `status` различаются только `generatedAt`.
- Упаковка под записью: 60 записей по HTTPS, пока `storeRepack.sh --teams` шёл 26 раз подряд —
  объектов в пакетах от 13 до 208, потерянных версий ноль, `fsck --strict` чистый.

Две грабли самих гейтов:

- HTTP 200 — не успех записи. `seq -w` дал id `01`…`09`, а `"id":01` — невалидный JSON: сервер
  ответил ошибкой разбора с кодом 200, и девять «записей» не случились. Успех проверяется по
  `isError` ответа и по журналу стора, а не по коду HTTP.
- Шесть `systemctl start` одного `oneshot` подряд — отказ «start … attempted too often»: у юнита
  лимит запусков systemd (по умолчанию пять за десять секунд), и после него юнит в `failed`, пока
  не сделан `reset-failed`. Нагрузочный цикл гоняет сам скрипт под `vmgit`, а юнит — один раз.

## Упаковка и бэкап

Ночную упаковку сторов команд делает та же `storeRepack.sh`, что пакует личный стор, в режиме
`--teams`: каждый живой `<слаг>.git`, переименованные удалённые не трогаются. Отдельной подкоманды
`gc` у сервера нет — один скрипт на обе упаковки. Упаковка идёт в 04:47, после бэкапа в 03:47.

Бэкап — только `memory`-команды: у их участников клона нет. `git bundle --all` каждого стора,
шифрование age открытым ключом владельца, один коммит без истории и `push --force` деплой-ключом —
репозиторий бэкапа не растёт. Закрытый ключ создаётся на Mac и хост не покидает. Ключи GitHub для
`known_hosts` у `vmgit` берутся из `gh api meta` по каналу Mac, а не `ssh-keyscan` с хоста, который
поверил бы первому ответившему.

Вживую: ключ age создан на Mac, репозиторий `VibeBrains/VibeMemoryBackup` — приватный, от учётки
`VibeBrains` (это учётная запись GitHub, не организация: API организаций отвечает 404).
Бэкап тестовой `memory`-команды расшифрован на Mac, склонирован, и локальный сервер прочитал её
записи. В репозитории бэкапа после второго прогона — один коммит: `push --force` заменил первый.
