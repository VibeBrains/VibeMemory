# Готовность движка к Windows: что проверено на Mac и что осталось GPD (2026-09-11)

Этап 4 стоял с пометкой «заблокирован железом». Часть его заблокирована по-настоящему: всё, что
исполняется только на Windows. Другая часть проверяется на Mac — компиляция под
`x86_64-pc-windows-msvc` и чистые функции, которые строят для Windows строки, пути и файлы.

## Замер компиляции

Зависимости чисто Rust (в lock нет ни `cc`, ни `libc`, ни `windows-sys`), поэтому
`cargo check --target x86_64-pc-windows-msvc` работает на Mac целиком. Нужна только цель
(`rustup target add x86_64-pc-windows-msvc`), линкер не нужен.

- Продуктовый код (lib и bin всех трёх крейтов) собирается и проходит `clippy -D warnings`.
- Тесты не собирались: 14 прямых вызовов `std::os::unix::fs::symlink` в пяти файлах. Компилятор
  показывает их по очереди — после починки первых трёх файлов всплыли ещё два, — поэтому искать
  надо поиском по тексту, а не по ошибкам сборки.
- `clippy.toml` даёт под Windows-целью три предупреждения конфигурации: пути `std::os::unix::…` из
  списка гейта чистоты там не существуют. Windows-пути туда добавлять нельзя — они дали бы такие же
  предупреждения в основном гейте на Mac. Оставлено как есть.

## Как std видит junction — прочитано в исходнике, а не запущено

`library/std/src/sys/fs/windows.rs` в 1.97.1, `rust-src`:

- `FileType::new`: `is_symlink = FILE_ATTRIBUTE_REPARSE_POINT && (тег & 0x20000000)` — бит
  name-surrogate. У junction тег `IO_REPARSE_TAG_MOUNT_POINT = 0xA0000003`, бит есть, значит
  `is_symlink()` — да, `is_dir()` — нет.
- `readlink` разбирает и `IO_REPARSE_TAG_SYMLINK`, и `IO_REPARSE_TAG_MOUNT_POINT`.
- `rmdir` — это `RemoveDirectoryW`.
- `remove_dir_all` открывает путь с `FILE_FLAG_OPEN_REPARSE_POINT` — внутрь ссылки не заходит.

Следствие: все шесть проверок «ссылка или настоящий каталог» в движке верны для junction без
правок, и импорт «настоящего каталога», который кончается `remove_dir_all`, junction не возьмёт.
Это важнее, чем выглядит: ошибись std здесь — и импорт стёр бы содержимое стора сквозь ссылку.
Поэтому прочитано в коде, а не взято из памяти.

## Что осталось — только GPD

Сборка под Windows теперь в проверках проекта (`CLAUDE.md`): `cargo clippy --workspace
--all-targets --target x86_64-pc-windows-msvc -- -D warnings`.

Всё, что на Windows **исполняется**, на Mac не проверяется ничем:

- junction под живым CLI и Desktop;
- какой из двух путей Desktop на GPD стоит на самом деле;
- ~~примет ли `schtasks` файл в UTF-16~~ — принимает, без администратора: 30.09 на GPD 0.4.1 зарегистрировала задание
  из `/XML`, `schtasks /Query` — `Ready`, последний запуск с результатом 0, следующий через две минуты;
- **консольное окно**: `vibememory.exe` — консольное приложение, и задание с `InteractiveToken`
  может открывать окно каждые две минуты. Нужен замер, и если окно есть — решение (отдельный
  бинарь без консоли или запуск через скрытый хост);
- строка хука с Windows-путём вживую под Git Bash и git-алиас пробы драйвера под `sh` из Git for
  Windows;
- resume в обе стороны.

## Планировщик без администратора (GPD, 27.09.2026)

Первый `connect` на GPD: всё встало, кроме тика
`schtasks` ответил:
_ERROR: Access is denied._

Замеры на GPD, PowerShell без повышения:
- `schtasks /SC ONLOGON` — отказ, даже с явным `/RU` владельца; от администратора — создаётся
- Триггер разблокировки (`MSFT_TaskSessionStateChangeTrigger`) — отказ
- `schtasks /SC MINUTE /MO 2` — создаётся

**Вывод:** пользователь без повышения регистрирует задание по времени, но не на вход и не на разблокировку.
Дело не в пустом `<UserId>` — эта гипотеза проверена и отвергнута.

**Стало:** в задании один `TimeTrigger` с повтором каждые 2 минуты от давно прошедшей даты, без конца.
`StartWhenAvailable` запускает пропущенный тик сразу после сна, поэтому отдельный триггер разблокировки не нужен.
Гейт в `install_plan.rs` падает на любом триггере, требующем администратора.
Проверено 30.09 на GPD: 0.4.1 зарегистрировала этот файл через `/XML` без администратора, тик идёт каждые две минуты с результатом 0.
`doctor` при этом сверяет только файл задания, а не регистрацию в Планировщике: «ok» о расписании пока значит «файл верный», а не «задание есть».
