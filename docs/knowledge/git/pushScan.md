# Чтение push на токены и каналы git (2026-09-25)

Четвёртый круг ревью нашёл в `pre-receive` три ошибки сразу, и все три — про то, как говорить с git.

## Запись всего ввода до чтения ответа запирает обоих

`cat-file --batch` отвечает, пока читает вопросы.
Хелпер писал весь ввод, а ответ читал потом: когда ответы заполняли канал (64 КиБ на Linux), git переставал читать, а хук ждал записи.
Ревьюер воспроизвёл на 3000 файлах; обычная первая синхронизация машины столько и даёт.
Теперь ввод пишет отдельный поток, а ответ читается сразу, в `git_memories::run` и в скане.
Мутация «писать весь ввод до чтения» вешает тесты — гонка ловится таймаутом прогона, а не падением.

## Скан по объектам, а не по итоговому дереву

Разница деревьев до и после push не видит токен, добавленный одним коммитом push и убранный следующим: дерево чистое, история — нет.
Скан берёт `rev-list <new> --not --all` — в `pre-receive` ссылки ещё не сдвинуты, так что это ровно коммиты push — и читает каждый коммит (с сообщением) и каждый блоб, который коммит добавляет.
`diff-tree` без `-m` на слиянии молчит, а блоб, который написало разрешение конфликта, есть только в слиянии: флаг обязателен.
Вопросы задаются по id объекта, не по пути: имя с переводом строки делило вопрос по пути надвое и сдвигало все ответы, а имя не в UTF-8 после `from_utf8_lossy` не находилось вовсе.
Такие имена теперь отвергаются в `paths_allowed`.

## Сколько push может заставить прочитать

Блоб из нулей сжимается почти в ничто, и `receive.maxInputSize` (1 ГиБ сжатых) его не остановит.
Размеры берутся заранее `cat-file --batch-check=%(objectsize)`; больше потолка (4 ГиБ, флаг `--max-content-bytes`) — отказ `contentTooLarge`.
Сам скан идёт кусками по 64 КиБ с хвостом в длину признака токена минус один байт: память не растёт с размером блоба.
Объекты читаются только у push, который прошёл все прочие проверки, поэтому `tokenInPush` — последний код таблицы.
