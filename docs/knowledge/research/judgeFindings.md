# Фатальные находки судей 2026-09-02

> 27 судейских вердиктов (3 дизайна × 3 линзы × 3 судьи). Дистиллят — [design/engineConstraints.md](../design/engineConstraints.md).

## Дизайн: native-or-different-transport

- Resume на машине B не получает свежую версию сессии, которую только что вёл A. SessionStart(resume) срабатывает ПОСЛЕ того, как CLI загрузил транскрипт в память, а дизайн при source=resume добавляет текущий session_id в список живых и ОТКЛАДЫВАЕТ merge, если входящий diff трогает этот файл — то есть ровно в целевом сценарии («закрыл крышку A, открыл B, нажал resume») B продолжает устаревшую копию. Для Desktop нет pre-launch хука вообще: корректность зависит от того, успел ли tick (10 мин / RunAtLoad; на Mac нет триггера «при разблокировке») до клика пользователя. Результат — вилка транскрипта; union сохранит строки, но при resume CLI выбирает лист с максимальным timestamp (проверено в 2.1.255: fAr перебирает leafUuids и берёт max(timestamp)), поэтому ветка одной из машин исчезает из видимого разговора — данные есть, обещание «продолжить» нарушено, и решает это часы двух машин.

- Git LFS несовместим с union-драйвером и с квотой GitHub. Файлы ≥40 МБ переводятся в LFS поимённо; при этом merge-драйвер получает от git содержимое блобов, то есть pointer-файлы, а не JSONL — union двух указателей даёт мусор вместо транскрипта; сбой smudge (сеть, квота) оставляет в рабочей копии 130-байтный pointer, который CLI прочитает как пустой транскрипт, а Desktop пометит transcriptUnavailable и сбросит cliSessionId. Stop-хук коммитит каждые 30 с, LFS хранит каждую версию целиком без дельт — активная сессия с транскриптом 45 МБ исчерпает 1 ГБ бесплатного LFS за ~20 ходов, после чего GitHub блокирует push ВСЕГО репо: полная остановка синка, о которой узнаёшь только из additionalContext на следующем старте. Под LFS попадают именно самые длинные и ценные сессии.

- Нет политики на неразрешённый конфликт и нет драйверов для половины JSON под projects/. Покрыты только *.jsonl, *.md, desktop/**, tasks/**, config/settings.json; для projects/<name>/.project.json (обе машины дописывают свой корень — конфликт гарантирован), <sid>/custom-title.json, workflows/*.json, tool-results/*.txt действует дефолтный 3-way → маркеры <<<<<<< в рабочей копии; следующий Stop-хук делает `git add -A && git commit` и ПУШИТ маркеры на другую машину. Конфликтный .project.json ломает разрешение идентичности проекта на обеих машинах. Также не описано поведение при modify/delete (forget на A, продолжение на B) и при «local changes would be overwritten» (memory/MEMORY.md, дописанный CLI между commit и merge).

- Порча дескрипторов Desktop распространяется через fast-forward. Экспорт локального стора дескрипторов в repo не имеет защиты: когда Desktop на B не находит транскрипт (ссылка ещё не создана, merge отложен, LFS pointer), он навсегда стирает cliSessionId (clearStaleResumeHandle), хук экспортирует и пушит испорченный дескриптор, A забирает его fast-forward — драйвер claudesync-newest с coalesce не вызывается вовсе (он работает только при конфликте). Более того, унификация CLAUDE_CONFIG_DIR во всех источниках, которую дизайн требует, как раз ВКЛЮЧАЕТ доверие Desktop к вердикту «транскрипта нет» (canTrustTranscriptMissingVerdict) — сегодня расхождение случайно защищает.

- Модель «живой сессии» построена на неверной и неполной посылке. Проверено lsof на двух живых Desktop-сессиях (pid 6278, 11657): открытого дескриптора транскрипта НЕТ — CLI пишет через open/append/close по пути, значит замена inode git-ом сама по себе записи не теряет, а прецедент 08.08 объясняется иначе (и остаётся необъяснённым). Реальная опасность другая: загруженный в память разговор нельзя обновить никаким способом, а git откажет в merge на dirty-файле — значит отложенный merge под открытой вкладкой Desktop висит ДНЯМИ (вкладки живут неделями), а ввод в такую вкладку после работы на другой машине даёт вилку без предупреждения (нет UserPromptSubmit-проверки свежести). Список «кто жив» неполон: `claude -p` прогоны (VibeDub, 109 сессий в сторе root) защищены только рекомендованной, не принудительной переменной; Windows переиспользует pid — kill -0/tasklist даст ложное «жив» или ложное «мёртв».

- Окно потери и порядок шагов хука. Stop-хук: дебаунс 30 с, потом commit+push — закрыл крышку внутри окна → последние ходы остаются на A (SessionEnd не срабатывает при сне, tick не идёт), B начинает со старой копии. Синхронный commit дёшев (сотни мс), откладывать надо только push. В SessionStart единственное действие, обязанное успеть до рождения транскрипта (ensure-link), стоит ПЯТЫМ — после ожидания лока (до 20 с), fetch (до 15 с), merge и push — внутри таймаута 45 с; по таймауту CLI отбрасывает хук и создаёт реальный каталог. Проверено (racetest): CLI ждёт завершения SessionStart перед первой записью, т.е. гарантия достижима, но только если ссылка создаётся первой и без сети.

- Union-переписанный транскрипт — синтетический файл, который ни одна версия CLI не писала: сортировка по timestamp двух машин с расходящимися часами (GPD vs Mac) ломает причинный порядок относительно parentUuid; снимок `git add` живого append-only файла может захватить оборванную строку, а byte-дедуп для строк без uuid сохранит обрывок при двустороннем изменении (CLI 2.1.255 парсит строки в try/catch и молча пропускает мусор — не фатально, но накопление). Формат объявлен внутренним и меняется каждый релиз — драйвер обязан иметь тест-гейт против каждой новой версии CLI.

- Идентичность по `git rev-parse --show-toplevel` даёт ЛОЖНОЕ имя для git-worktree: в linked worktree toplevel — сам worktree, basename = имя ветки/папки, а не репо. Desktop-режим «изолированный worktree» (4 дескриптора уже с cwd .claude/worktrees/<name>) молча создаст отдельные сторы `<name>`, и после удаления worktree сессии станут сиротами. Нужен `--git-common-dir`.

- Resume-on-machine-B race breaks the core promise: merge is (correctly) forbidden under a live or resuming session, so if the fetch has not completed before the user clicks resume, B loads a stale transcript, the merge is deferred and A's last turns never enter B's context. Bytes survive on disk (union merge), but the resumed chain follows parentUuid from the leaf, so the other branch is invisible — a silent conversation fork in exactly the 'close lid, open other machine' flow. Mac has no wake/unlock trigger (only RunAtLoad + StartInterval 600), so the fetch-before-click guarantee is a timing bet, not a mechanism.

- SessionStart ordering: ensure-link is step (e), after fetch (15 s) + merge + push, under a 45 s timeout. Any timeout, hung remote or merge failure before (e) means no link is created, the CLI materialises a real ~/.claude/projects/<enc> directory ~4 s later, and the session forks until it ends and tick merges it. Link creation must be the first, network-free step; network work belongs after it or in the background.

- Desktop descriptor poisoning propagates linearly: Desktop strips cliSessionId and sets transcriptUnavailable on not-found (20 cards already damaged). The design's coalesce lives in the claudesync-newest merge driver, which git only invokes on conflicts; a one-sided change on B (e.g. user clicks a card before the transcript arrived) fast-forwards and overwrites A's good copy. The guard must be at export time (never publish a descriptor that lost cliSessionId or gained transcriptUnavailable relative to the repo copy), not in the merge driver.

- Failed merge driver + 'git add -A && git commit' at the next hook start finalises a half-merged state: if claudesync-jsonl/md/newest crashes (Python missing, format change, torn line), git leaves MERGE_HEAD with the local version in the worktree; step (b) of the next hook commits it as a merge, so the remote side's lines are considered merged and never come back. Need 'git merge --abort' on any driver failure and a hard rule: never auto-commit while MERGE_HEAD exists.

- Last-turn loss window when Desktop kills the CLI: no SessionEnd, Stop hook is async with a 30 s debounce, and a sleeping machine's tick does not run. Closing the lid within the debounce leaves the final turn(s) unpushed; opening B then produces flaw #1. Commit should be immediate on Stop (debounce only the push), and tick must fire on wake/unlock on both OSes.

- gitleaks as a push gate on projects/** converts a security nicety into a silent-desync mechanism: transcripts are full of high-entropy strings (JWTs and tokens in tool results, base64 blobs, env dumps), so false positives are routine; each one blocks push with no visible signal until the next session start, while the user believes the machines are in sync. Scan and warn (or gate config/ only); never block replication of transcripts on heuristics.

- Snapshotting a live transcript with 'git add' can capture a torn last JSONL line (O_APPEND writes of multi-MB tool results are not atomic). That partial line then becomes a 'unique non-uuid line' for the union driver and can be interleaved into the merged file mid-stream, corrupting a transcript that B continues to append to. Snapshots must be truncated to the last newline (or the driver must drop lines that fail JSON parse).

- Интерлок «живая сессия» — единственная защита от повторения 08.08 (git подменяет inode под открытым дескриптором, записи уходят в никуда) — построен на недокументированном sessions/<pid>.json + kill -0. При смене формата/каталога в очередном апдейте CLI он отказывает «в открытую»: все сессии выглядят мёртвыми, merge проходит под живой записью. Нужен fail-closed (реестра нет/не парсится → merge откладывать) и второй независимый сигнал: mtime транскрипта < N мин, lsof/handle.exe по файлу, список процессов claude.

- `git add -A && git commit` в каждом хуке после неудачного или прерванного merge (драйвер упал на новом формате JSONL, delete/modify-конфликт от `forget`, хук убит по таймауту с MERGE_HEAD) тихо фиксирует «ours» как разрешение: `git add` снимает unmerged-статус, «theirs» выпадает из линии слияния — восстановимо только из origin/reflog и незаметно. Коммит обязан отказываться при `git ls-files -u`/MERGE_HEAD. Стейл index.lock и стейл mkdir-лок (в дизайне нет pid-владельца) должны сниматься по проверке живости процесса — иначе один убитый хук останавливает синк навсегда, а сигнал — только additionalContext «после N стартов».

- Pull не гарантирован ДО resume. Merge в SessionStart бесполезен для той самой сессии: CLI читает транскрипт до хука, а текущий session_id живой → merge откладывается. Реально «продолжение на B» держится на таймере (10 мин) и триггерах логона; на Mac LaunchAgent по пробуждению не срабатывает — окно до 10 мин, когда `--resume`/Desktop на B поднимает устаревший транскрипт, пользователь работает поверх, затем union даёт перемешанную по timestamp историю, которой ни одна модель не видела. Нужен «pull перед resume» (обёртка/тик по wake через WatchPaths или sleepwatcher, Windows — unlock есть) и явный сигнал «транскрипт изменён на другой машине».

- Та же сессия живая на A (открытая вкладка Desktop держит процесс CLI — проверено: сегодня два живых pid с entrypoint claude-desktop) и продолженная на B: на A merge отложен, при возврате пользователь пишет в старый процесс со старым контекстом → расхождение растёт до закрытия вкладки, потом union склеивает ветви. Плюс bridge-record Remote Control внутри транскрипта: resume на B отбирает RC у A. Дизайн декларирует «одна машина за раз», но ничего не принуждает и не предупреждает — нужна детекция «сессия изменена на другой машине» с блоком/предупреждением при resume, а не молчаливая склейка.

- Идентичность стора = basename(git toplevel). В linked-worktree `--show-toplevel` возвращает каталог worktree (сегодня 6 Desktop-дескрипторов с cwd под .claude/worktrees/*) → отдельные сторы projects/<имя-worktree>, невидимые с другой машины; одноимённые репо под РАЗНЫМИ корнями коллизией не считаются (проверка только «тот же корень, другой rel») и сливаются в один стор; переименование каталога репо = новая идентичность → старые сессии не находятся (фолбэк-скан слеп к ссылкам). Ключ должен быть `--git-common-dir` + хеш первого коммита/remote, basename — только для отображения.

- SessionStart делает fetch+merge+push синхронно под 45 с (хук блокирует старт — подтверждено доками): первый ssh к хосту без known_hosts, Defender на 500-МБ дереве, LFS smudge — хук убивается посреди git-операции (см. п.2), а каждый старт офлайн ждёт 15 с fetch-таймаута. Сетевые операции — только в tick/async-хуках; SessionStart — link-only + быстрый локальный коммит.
## Дизайн: local-hot-auto-durable

- Слепое пятно межмашинной живости. Все опасные операции (uuid-слияние с перезаписью канонического <sid>.jsonl, перелинковка, слияние конфликт-копий) гейтятся ТОЛЬКО по локальному sessions/*.json, а этот реестр не покидает машину по построению. Сессия, живая на другой машине, для вотчера невидима: он видит конфликт-копию, «живых pid нет» — и переписывает канонический транскрипт tmp+rename, пока вторая машина в него дописывает. Проверено lsof на живом pid 6278: CLI не держит fd транскрипта (append по пути), т.е. дописи между «вотчер прочитал» и «OneDrive доставил переписанный файл» остаются в живых только если OneDrive сделает конфликт-копию, — и цикл повторяется (ping-pong слияний). Нужен heartbeat живых sid в outbox (SessionStart/Stop/SessionEnd) и правило «sid с heartbeat моложе 30–60 мин на ЛЮБОЙ машине неприкосновенен» — с большим TTL, потому что и heartbeat едет лениво.

- Гейт приёмки слияния в описанном виде неудовлетворим на реальных данных → слияния никогда не фиксируются. Проверено на чистых одномашинных транскриптах: VibeSweep e3bbbf16 — 13 немонотонных пар timestamp из 304 и 1 осиротевший parentUuid (tool_result user-записи, строка 148); VibeShot 7bad7d59 — 75 немонотонных пар из 1785. Правило «timestamp монотонны, нет осиротевших parentUuid» отклонит почти каждое слияние, источники «останутся», а каноническим навсегда будет та версия, которой OneDrive отдал имя в гонке загрузок — нередко устаревшая. Это тихая потеря продолжения при формально сохранённых байтах. Валидировать только парсимость и покрытие всех uuid всех источников; сироты и немонотонность считать нормой, если они есть уже в базе.

- Устаревший resume не детектируется. Ленивый синк (крышка закрыта → загрузка OneDrive остановлена) означает, что машина B возобновляет <sid> без последних ходов A и ветвит разговор; после слияния хвост A попадает в файл как боковая ветка, которую resume по цепочке parentUuid от последнего листа не показывает. Данные есть, «продолжить на другой машине» — нет, и пользователь этого не узнает. Нужен маркер хвоста per-sid в outbox на Stop/SessionEnd ({lastUuid, lines, bytes, at}); SessionStart(resume) сравнивает с локальным файлом и через additionalContext предупреждает «транскрипт отстаёт на N записей, дождитесь синхронизации», перелинковку/слияние откладывает.

- Desktop-половина обещания ломается ровно в окне ленивого синка. (а) Импорт дескрипторов «только при закрытом Desktop» на машине, где Desktop живёт постоянно (на этом Mac все сессии после 14.08 идут через Desktop), не происходит никогда — сессии другой машины не появятся в списке без ритуала «выйти из Desktop, дождаться tick, запустить». (б) Когда пользователь жмёт resume до прибытия транскрипта, Desktop ЛОКАЛЬНО ставит transcriptUnavailable и навсегда обнуляет cliSessionId (clearStaleResumeHandle); экспорт это не выпускает наружу, но локальный дескриптор на этой машине никто не чинит из архива/outbox — сессия для этой машины потеряна как возобновляемая. Нужны: восстановление локальных дескрипторов из outbox/archive (cliSessionId «не понижается» и локально), и проверка, перечитывает ли Desktop стор без перезапуска (открытый вопрос №2 — критичен, а не косметичен).

- Windows-половина не проверена и несёт два известных блокера, которые дизайн не закрывает. (а) OneDrive ставит +R на синхронизируемые каталоги и файлы; дизайн пинит (`attrib +P -U`), но не снимает +R → Bun mkdir recursive даёт EEXIST на каталогах стора через junction (per-site фиксы 2.1.163/2.1.181 не общие; sidecar-каталоги <sid>/tool-results не покрыты), а запись settings.json сквозь символическую ссылку упирается в rename поверх read-only файла. (б) С Files On-Demand каждый файл стора — reparse point (CldFlt); проверка идентичности транскрипта в Desktop (lstat/fstat, ETRANSCRIPTNOTREGULAR) на таких файлах не проверялась. (в) Doctor проверяет валидность settings.json, но не то, что settings.json/CLAUDE.md всё ещё ссылки: атомарная запись CLI может подменить ссылку обычным файлом (#78162) → hooks и cleanupPeriodDays тихо расходятся между машинами.

- Движок продолжает писать .claude.json (seedTrust по умолчанию включён) — в файл с худшей историей порчи (#28847/#29153, каскад 35KB→77B), ради поля, которое сегодня пусто и для Desktop не нужно (сессии на /Volumes/Storage/* работают при hasTrustDialogAccepted=false). Гейт «нет живых сессий и Desktop закрыт» опирается на тот же локальный реестр и на детект процесса; писатели мимо реестра (VS Code extension host, вспомогательные запуски) возможны. Правильное решение — не гейтить, а убрать запись целиком: одна нативная кнопка «доверять» на путь дешевле любого риска.

- Структурная хрупкость: Desktop-слой private-file прямо объявляет ссылки под корнем конфига неподдерживаемыми («components under the config root may not be symlinks»; запись → PlantDetectedError, чтение → warnAndRead). Сегодня это лишь пропуск .desktop-released-маркеров, но любая будущая запись Desktop под projects/<enc>/ (состояние сессии, заголовки, релиз-маркеры) на этой раскладке молча провалится. Дизайн опирается на недокументированную терпимость, а не на поддерживаемый путь; нужен мониторинг PlantDetectedError в логах Desktop как штатная проверка doctor, а не «посмотреть через неделю».

- Ключ стора — basename репо (или basename cwd для не-git). Два разных репо с одинаковым именем папки (web, server, api) и любые не-git каталоги (Downloads на обеих машинах) сливаются в один стор: пикер сессий текущего cwd показывает чужие сессии, память MEMORY.md смешивается. Не потеря байтов, но тихое загрязнение контекста; ключевать по хешу git remote или <parent>/<name>, non-git — по машине.

- Импорт Desktop-дескрипторов только при закрытом Desktop. Проверено сейчас: Desktop у владельца живёт постоянно (два процесса claude-desktop, аптайм 1ч09 и 36 мин, реестр ~/.claude/sessions/). Значит для основного рабочего пути «сессия Desktop → другая машина» ритуал остаётся: выйти из Desktop → дождаться tick (до 5 мин, поллинг процесса) → перезапустить; а вопрос «перечитывает ли Desktop стор во время работы» оставлен открытым вместо того, чтобы быть решённым. Минимум: импортировать НОВЫЕ дескрипторы в любое время (Desktop не перепишет то, чего не загружал), откладывать только обновления известных; проверить перечитывание на folder-picker.

- Liveness проверяется только локально (sessions/<pid>.json), кросс-машинной живости нет. Типовой сценарий владельца — вкладка Desktop на машине A остаётся открытой часами, на B тот же sid возобновляют: либо OneDrive делает конфликт-копию, которая НЕ сливается, пока sid жив на A (правило «живые не трогаем» блокирует навсегда), либо после последовательных дозаписей получается транскрипт с двумя листьями parentUuid — при resume CLI идёт по одной цепочке, ходы второй машины лежат в файле, но невидимы модели. Байты не теряются, разговор тихо форкается — это ровно нарушение обещания. Нужен outbox machines/<id>/live.json (sid + heartbeat со Stop/SessionStart) и предупреждение/отказ в additionalContext при resume sid, живого на другой машине.

- Пин стора — ручной шаг Finder без CLI и без API проверки, и он до сих пор не сделан: прямо сейчас 5 из 14 сторов (EventHub, Undercut, VSCodeSync, VibeReel, VibeReviewer) дегидрированы (blocks=0). Дегидрированный транскрипт на warm_preflight → Desktop ставит transcriptUnavailable и НАВСЕГДА обнуляет cliSessionId (подтверждённое поведение), офлайн resume падает. Doctor лишь «сигналит», а движок отказывается сливать — т.е. первый же машинный переход с непропинённым стором ломает дескрипторы. Пин должен быть гейтом bootstrap с проверкой факта (blocks по всем jsonl), а не рекомендацией.

- Проигранная гонка хука не покрыта на протяжении жизни сессии: если транскрипт родился в реальном каталоге (интерактивный TTY не проверен; в -p и stream-json хук выигрывает — проверено сегодня), сессия пишет локально до конца жизни, а Stop-хук зеркалит только history/tasks, но не сам транскрипт. Вкладки Desktop живут днями → сессия невидима другой машине днями. Дешёвое закрытие: Stop-хук копирует D/<sid>.jsonl → S (tmp+rename), когда D — реальный каталог.

- seedTrust пишет в .claude.json — файл с задокументированной историей порчи (#28847/#29153), который Desktop и CLI переписывают целиком по 5 раз за полчаса; выигрыш — один нативный вопрос на новый путь, причём Desktop-сессиям флаг вообще не нужен (работают при false). Риск ненулевой, польза ~0; включён по умолчанию. Убрать, а не оставлять флагом.

- memory/ по правилу «новее побеждает»: авто-память — единственный общий артефакт, который обе машины легитимно правят в каждой сессии; проигравший MEMORY.md уезжает в .conflicts, куда модель не смотрит. Для модели это тихая потеря памяти другой машины. Нужно слияние по строкам/секциям (append + dedupe), LWW здесь недопустим.

- Именование стора расходится между машинами на краях и даёт тихий сплит/слияние: (а) не-git cwd → basename — VibeSweep на /Volumes/Storage/… НЕ git-репо (проверено), т.е. уже сегодня ключуется basename'ом, и любой второй каталог с тем же именем на любой машине сольёт транскрипты И память; (б) `git rev-parse --git-common-dir` без --path-format=absolute отдаёт относительный `.git` → для cwd VibeDub/server родитель = «server» на одной машине и «VibeDub» на другой; (в) сабмодуль → `.git/modules/<x>` → родитель «modules». Без фикстурного теста на worktree/сабдир/сабмодуль/не-git это гарантированный тихий форк.

Дизайн к тому же излишне консервативен: перезапись из памяти грозит только известным приложению дескрипторам — новые (чужие) файлы можно класть и при запущенном Desktop.

- [ломает обещание] Ловушка преждевременного resume в Desktop: если транскрипт ещё не доехал по OneDrive или дегидрирован, приложение само ставит transcriptUnavailable и стирает cliSessionId локально (clearStaleResumeHandle) — а CLAUDE_CONFIG_DIR в дизайне везде единый, значит canTrustTranscriptMissingVerdict сработает и вердикту поверят. Правило «cliSessionId никогда не понижается до null» описано для слияния outbox-ов, но не как обязательный локальный ремонт независимо от lastActivityAt; без него сессия осиротеет на этой машине навсегда (сегодня уже 16 дескрипторов без cliSessionId).

Транскрипты с другой машины приезжают именно дегидрированными: первый --resume на новой машине = блокирующая загрузка, офлайн = отказ. Единственный барьер — ручной.

- [потеря данных, коррелированная] Ни одной копии стора вне OneDrive. Любое удаление (retention-свип при невалидном settings.json, claude project purge, удаление сессии в Desktop, баг слияния, сбой аккаунта OneDrive, шифровальщик на любой из машин) уезжает на вторую машину за секунды; откат — только корзина/версии OneDrive, 30 дней, вручную. Окно «проверил живых → CLI стартовал → записал» не закрыто локом CLI. Это единственный компонент, способный сломать сам вход в Claude Code на машине; ценность — нулевая (allowedTools/mcp везде пусты).

Косвенный сигнал: у Windows-сессии 78dcced4 (2.1.227/229, транскрипт 1.5 МБ) в сторе нет сайдкар-каталога. Оба пункта в дизайне не названы как «проверить до миграции Windows».

- [ломает обещание, честность] Слияние разошедшихся транскриптов гарантирует сохранность записей, но не их видимость: после uuid-слияния двух веток CLI показывает только цепочку от последнего листа по parentUuid — ход второй машины остаётся в файле, но исчезает из разговора. Для владельца это неотличимо от потери. «Проверка покрытия» продаётся как решение, тогда как это архив, а не продолжение; нужна явная оговорка и подсказка (fork/rewind) в additionalContext.

Риск существует уже сегодня (settings.json общий), дизайн его не добавляет, но и не называет; в OneDrive при этом до сих пор лежит .credentials.json с MCP-токенами.

## Дизайн: cloud-first

- Защита живой сессии по построению одномашинная (pid жив на ЭТОЙ машине И pidDomain совпадает), а Desktop держит CLI-процесс живым для каждой открытой карточки часами (pid 6278 с 07:24). Проверено: транскрипт пишется по пути, а не через открытый fd (lsof pid 6278 не показывает .jsonl) — после `activate` на машине B, переименовавшего файл живой сессии A, следующий append на A создаст новый файл по старому пути: транскрипт форкается. B при этом продолжил со stale-копии, и uuid-merge «объединение + сортировка по timestamp» даёт DAG, где хвост A становится невидимой мёртвой веткой parentUuid. Вдобавок CLI на B при старте удалит `sessions/<pid>.json`+`.key` машины A как «crash leftover» (pid не жив локально) — метаданные защиты исчезают раньше, чем reconciler успеет ими воспользоваться. Это ровно сценарий «перекрытие на минуты» — обещание «продолжить» ломается, контент выживает только через merge/карантин.

- Сам механизм: каждое переключение машин массово переименовывает ВСЮ историю репо (сотни транскриптов, сайдкары, memory/) между двумя enc-каталогами внутри sync-корня, а rmdir-свип CLI (#86952) через минуты сносит опустевший источник, пока клиент другой машины ещё может дозаливать изменения по старому пути. Move+modify одного элемента с двух клиентов в окне лага — канонический генератор конфликт-копий; дизайн превращает редкий случай (8 копий за 3 месяца, включая проверенную `VibeIDE/78dcced4-…-MacMini.jsonl`) в штатное событие на каждом переключении. Единственная защита — привычка «дождаться up to date», которую гейты не проверяют: гейт свежести опирается на Desktop-дескрипторы (для терминальных сессий их нет), гейт дегидрации не видит stale-но-гидрированную копию.

- Бэкап — зеркало, а не поколения: `rsync -a --delete` / `robocopy /MIR` реплицируют удаление и порчу в «бэкап» в течение суток; на macOS источник — File Provider-дерево, где любой недокачанный файл — 0-байтный стаб, который rsync запишет поверх хорошей копии (дизайн отмечает это только для миграции, не для ежедневного прогона). На Windows второго поколения нет вообще. Time Machine включает CloudStorage (проверено `tmutil isexcluded` → Included), но dataless-файлы не гарантированно попадают. Карантин лежит внутри синк-дерева и самоудаляется через 30 дней — ошибка merge, замеченная на 31-й день, невосстановима штатными средствами дизайна; корзина/версии OneDrive в дизайне не задействованы.

- Безнадзорный uuid-merge над форматом, объявленным внутренним и меняющимся в каждом релизе, запускается на каждом SessionStart обеих машин. Проверено на текущем транскрипте: 142 из 423 записей без uuid (queue-operation 24, custom-title 20, bridge-session 19, last-prompt 18, ai-title 17, atis-latch 17, agent-name 16, mode 11) — это восстанавливаемое состояние (режим прав, имя агента, заголовок, запись переподключения Remote Control), для которого правила слияния нет; skill sync-repo их явно не покрывает («свежий перекрывает старый»). Нет спецификации атомарной записи/журнала операций: хук с таймаутом 60 с, убитый посреди merge/пакета rename (гидрация через File Provider), оставляет полуперенесённую историю. Баг merge применяется ко всему парку до того, как его заметят.

- Секреты — обнаружение после выгрузки, а не предотвращение: `CLAUDE_SECURESTORAGE_CONFIG_DIR` недокументирована (проверено в 2.1.232: `ine()` возвращает env-каталог, Keychain ключуется sha256 этого пути — работает), на Windows-сборке не проверена; гейт «нет .credentials.json в облаке» срабатывает после того, как OneDrive уже выгрузил файл. `sessions/*.key` (peer-токены) и `session-env/` остаются в облаке осознанно. При исчезновении переменной в будущем релизе plaintext-токены Windows снова уедут в облако до первого старта гейта.

- «Продолжить в Desktop на Windows (MSIX)» держится на самодельном двустороннем mtime-зеркале горячих файлов: Desktop переписывает lastFocusedAt при каждом фокусе, reconciler переписывает cwd/originCwd, агент копирует «новее побеждает» между двумя машинами с разными часами — победитель выбирается тихо и неверно при расхождении часов; `clearStaleResumeHandle` всё равно срабатывает в окне лага, а descriptor-shadow — восстановление best-effort. Открытый Desktop на машине A перезапишет переписанные агентом дескрипторы своей копией из памяти (пинг-понг записей → конфликт-копии).

- Правило «ровно одна копия в настоящем каталоге» превращает любую гонку в потерю привязки: как только один sessionId оказывается в двух enc-каталогах (лаг OneDrive, Desktop bring-home-копия при resume, конфликт-копия), projectsScan возвращает null → Desktop получает cli_resume_not_found → clearStaleResumeHandle стирает cliSessionId навсегда; descriptor-shadow чинит это только если reconcile успел раньше пользователя. Сегодня симлинки делали сканы слепыми, но primary-lookup работал; дизайн меняет «невидимо» на «неоднозначно → не найдено». Проверено: VibeDub/server и VibeDub/web — подкаталоги одного toplevel VibeDub → repoKey совпадает → каждый запуск в другом подкаталоге (даже на одной машине, две Desktop-вкладки server+web) гоняет 105 MB стора между тремя enc-каталогами внутри OneDrive; каждый такой rename во время недосинка другой машины порождает дубль.

- Retention-свип (unlink мимо корзины) впервые взводится на общем сторе (17 транскриптов >30 дней уже есть), а единственная защита — cleanupPeriodDays=3650 + гейт в SessionStart-хуке — живёт в том же settings.json, чью невалидность она должна ловить: при провале zod-валидации хуки не грузятся, гейт не срабатывает, действует дефолт 30 дней, удаление уезжает по OneDrive на обе машины. Дизайн сам вносит в этот файл самый рискованный блок (hooks). Восстановление — только из бэкапа, вручную.

- Оставленный открытым Desktop на машине A (сессии подключены к Remote Control) при работе на B: любое сообщение с телефона или служебная запись CLI на A воссоздаёт транскрипт по старому пути после того, как B его переименовала → форк; `--resume` на B дополнительно перехватывает bridge → два живых CLI на один sessionId на двух машинах. Гард живости в reconciler видит только pid своей машины и этот случай не покрывает; владелец «работает по очереди», но Desktop он не закрывает.

- .claude.json возвращается в облако — ровно тот вектор, который 21.07 пересоздал конфиг с нуля (каскад #29153, +R-stall до 2.1.234). Idle Desktop-CLI переписывает его ≥5 раз/30 мин, значит каждое пробуждение второй машины даёт конфликт-копию и очередную зависимость от reconciler; replBridgePlaceholders/pid чужой машины и sessions/<pid>.<sha>.key (peerToken) едут в облако. Пользовательского контента там нет, но это постоянный источник «тихих» расхождений, которые должен разгребать код, парсящий приватный формат.

- Корректность держится на парсинге форматов, которые Anthropic объявила внутренними и ломающимися в любом релизе (JSONL транскриптов, дескрипторы Desktop, journal.jsonl побайтово). Политика «не парсится — не трогаю» означает, что при первом изменении формата дубли не сливаются, неоднозначность остаётся, и срабатывает флаг №1. Плюс на Windows секреты зависят от недокументированной CLAUDE_SECURESTORAGE_CONFIG_DIR (в 2.1.255 она есть — xw()/_0 проверены), но гейт ловит регрессию уже после того, как .credentials.json лёг в облако.

- Windows: OneDrive перештамповывает +R на каждом досинканном каталоге; почасовой attrib оставляет окна, в которых Bun mkdir на read-only каталогах (EEXIST) бьёт по ещё не починенным путям (сайдкары projects/<enc>/<sid>/, installer #81004). Зеркало стора Desktop для MSIX — LWW по mtime с надгробиями в обе стороны — классическая схема тихой потери; в дескрипторах лежит cliSessionId, т.е. это не только метаданные.

- Liveness marker lives inside the synced tree and is destroyed by the other machine. The CLI's own session-registry sweep probes pid/procStart and removes entries it judges 'dead-owner' (verified in 2.1.232 strings: isProcessProvablyGone / dead-owner / sweepPermitted; 2.1.232 has no pidDomain at all). Typical case: Mac Desktop left open, user starts Claude on Windows -> Windows CLI deletes sessions/6278.json -> Mac's WatchPaths agent fires on the incoming files -> reconcile (б)/(в) sees the Mac's open transcript as not-live and renames/uuid-merge-rewrites it while a live process appends -> the 2026-08-08 split, now automated and unattended. Tail of the live session is lost or forked; this breaks both data safety and 'continue on another machine'.

- Real directories + Desktop 'bring-home' manufacture duplicate sessionIds on every OS switch. Verified in the Desktop bundle: on resume it copies a transcript found in another project dir into enc(cwd) (sourceDir 'shared-cli-project', keepSource:true). Until the reconciler runs, the id exists in two real dirs, so cross-project --resume returns null (uniqueness rule) and Desktop's own lookup is ambiguous -> transcriptUnavailable / clearStaleResumeHandle on cli_resume_not_found_* (verified) permanently drops cliSessionId. descriptor-shadow.json heals only after the next reconcile and only if the user has not already continued the card from scratch. The design fights the app on the app's own turf and the race is inherent.

- Retention sweep is now armed on the shared store. With real dirs the unlink sweep (no trash) covers projects/*.jsonl, tasks/, shell-snapshots/, backups/ across BOTH machines; protection is one key in a cloud-synced settings.json plus a version mandate with no enforcement (terminal CLI autoUpdates=false; Windows still on 2.1.227/229). 2.1.232 verifiably fails closed on unparsable/invalid settings ('Skipping cleanup: a settings file could not be read or parsed'), but older Windows builds run on the same tree first. The 'backup' is rsync --delete / robocopy /MIR: it mirrors the deletion within 24 h, so it is not a backup against this failure; the real recovery paths (OneDrive online recycle bin, Time Machine on hydrated files) are not part of the design.

- Default-open cloud tree = secrets and machine state in OneDrive by construction. Today already by design: sessions/<pid>.<sha>.key peerTokens, session-env/*/sessionstart-hook-*.sh (CLAUDE_ENV_FILE exports), .claude.json oauthAccount + replBridgePlaceholders, mcp-needs-auth-cache; on Windows plaintext OAuth/mcpOAuth tokens stay out only because of an undocumented variable (CLAUDE_SECURESTORAGE_CONFIG_DIR — verified real in 2.1.232 ine()/DZ() and 2.1.255, unverified on 2.1.227/229), and the gate fires only after OneDrive has already uploaded the file (server-side version history keeps it). Anything Anthropic adds to the config dir next lands in the cloud automatically — the split scheme fails closed, this one fails open.

- MSIX Desktop store mirror is a hand-rolled LWW sync inside a sync. Hourly/at-logon mtime mirror with tombstones in both directions between the virtualized AppData store and OneDrive: a Windows-side descriptor with cliSessionId cleared, or a deleted_* tombstone, beats the Mac's good descriptor purely by mtime, and Desktop rewrites descriptors on every focus. The GUI list — the 'list + resume' half of the promise on Windows — is reconstructed from whichever side wrote last.

- repoKey = basename of `git rev-parse --show-toplevel` (or basename of cwd outside git). Two clones/forks with the same folder name, Desktop isolated worktrees (.claude/worktrees/<name> is its own toplevel, so 'feature-x' collides across repos), or any non-git folder named like a repo -> 'store follows the user' silently renames unrelated histories and memory/ into one enc dir and uuid-merges MEMORY.md across projects. Corruption without loss, but irreversible by the quarantine model because nothing was quarantined.
