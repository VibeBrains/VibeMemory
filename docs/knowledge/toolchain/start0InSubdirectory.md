# start0 в подкаталоге `cabinet/`: спайки фазы 0 (2026-09-23)

Стенд — scratch-репозиторий с корнем-заглушкой и паком start0 v0.1.29 в `cabinet/`, свой Postgres 17
с настройками хоста из плана (`shared_buffers=64MB`, `max_connections=20`); macOS arm64, bun 1.3.14
системный и 1.4.0 из пака, git 2.54.0. Здесь — то, на чём держатся решения фазы 3, и то, в чём спайк
поправил план. Сырой отчёт и логи лежат на одноразовом стенде
`/Volumes/Storage/Caches/VibeMemory/start0Spike/` (`REPORT.md`). Грабли пака, общие для любого проекта,
дописаны в навык `start0`.

## Обновление пака работает из подкаталога, но `git apply` там молчит

`bunx 1gr14@latest update` запускается в `cabinet/`: маркер `start0.version` читается из
`cabinet/package.json`, дифф `start0-<от>..<до>.diff` ложится туда же; из корня репозитория команда
отказывает («No package.json here»). Дифф она не применяет — пишет файл и печатает промпт для агента.
Нужны git в PATH и ключ 1gr14 (`~/.config/1gr14/auth.json` или `S_1GR14_API_KEY`): обновления идут, пока
жив Support Pack, без него — только ручной перенос.

Пути в диффе — от корня пака (`a/src/lib/slug.ts`). **`git apply` из подкаталога пропускает всё и
возвращает 0:** пути патча git считает от корня репозитория, а всё вне текущего каталога игнорирует — так
и написано в `git help apply`. Без `-v` не печатается ничего; с `-v` — «Skipped patch». Повторено руками.
Применять `git apply --directory=cabinet` или `patch -p1` из `cabinet/`: чистый v0.1.28 после
`--directory=cabinet` совпал с чистым v0.1.29 до байта (`diff -rq` пуст, 23 файла).

Атомарно дифф на наш кабинет не ляжет никогда: в нём хунки на файлы, которых у нас нет по построению.
`CHANGELOG.md` удаляет сам `init.ts` v0.1.29, демо `idea` и `init/` вырезаем мы — на копии «как после
init» `git apply --check --directory=cabinet` отказывает ровно на пяти «No such file or directory».
Штатный путь тот, что задумал пак: агент идёт по диффу и перечисляет пропуски с причиной; `--check` с
`--directory` показывает, какие хунки ложатся чисто.

## `init.ts` в подкаталоге сделал бы второй репозиторий

По коду, не запускался: `setupGit` проверяет только `cabinet/.git` и при его отсутствии делает
`git init` — внутри нашего репозитория вырос бы вложенный. Флага «без git» нет. Значит вендоринг руками
(так и было в плане), и работа `init.ts` повторяется руками: замена `my-app` / `My App` / `myapp`,
`.env` из `env.example` со сгенерированным `BETTER_AUTH_SECRET`, удаление `init/`, `dev/`,
`install-point0.js`, `CHANGELOG.md`, блоков `<!-- dev-only -->` и скрипта `init`.

## `prepare` в подкаталоге: husky молчит, `agents:link` пишет

План снимал `prepare` потому, что husky «перехватил бы `core.hooksPath` репозитория». Факт другой: в
подкаталоге husky печатает «.git can't be found» и не ставит ничего. Решение то же, причина другая —
pre-commit пака (`eslint --fix`, `prettier`, типы) в нашем репозитории не сработает никогда, и проверки
кабинета держит правило `CLAUDE.md` (`bun run check && bun run test`), как у Rust-части держит
`cargo test`. `agents:link` отработал и создал `cabinet/.claude/skills` — второй довод за снятие
`prepare`.

## Плагин `organization` на Prisma 7 работает — после правки генерата

better-auth 1.6.25 и Prisma 7.9.1 с `@prisma/adapter-pg`: плагин подключается строкой в
`auth/server.ts` и строкой в `auth/client.ts`, `bun run check` зелёный, типы API выводятся и не
ломают типы admin-плагина, интеграционный тест (создать организацию, добавить участника, пригласить,
выбрать активную, проверить строки в базе) проходит. Риск плана «совместимость не подтверждена» снят.

Генератор схемы для 1.6 — пакет `auth` (`bunx auth@<версия better-auth из lock> generate`):
`@better-auth/cli` на npm остановился на 1.4. Генератор ищет экспорт с именем `auth`, а пак
экспортирует `authServer` — нужен шим в одну строку.

**Генерат расходится с конвенцией пака и ломает миграцию.** У пака `generateId: 'uuid'`, и генератор
пишет новым моделям и внешним ключам `@db.Uuid`, а `User.id` пака — `String @default(uuid())`, колонка
`text`. `prisma generate` это пропускает; `migrate dev` падает (P3018, 42804: «incompatible types: uuid
and text») и **остаётся применённой наполовину** — таблицы созданы, незавершённая запись в
`_prisma_migrations` блокирует следующие. Правка — привести модели к конвенции пака до миграции. Урок
для прода: Prisma упавшую миграцию не откатывает, поэтому любая миграция сначала идёт на копии базы.

`migrate dev --name <имя>` без терминала создаёт и применяет миграцию, если нет предупреждений о
потере данных; миграция с потерей данных не проверялась.

## Лицензии: ограничение даёт только сам пак

Открытые зависимости — MIT (`@point0/*`, `@1gr14/*`, better-auth), Apache-2.0 (Prisma), ISC
(`@prisma/dev`), copyleft нет. У всех девяти `@point0/*` нет файла лицензии — MIT заявлен только полем
`license`, атрибуцию брать оттуда.

start0 — source-available: делать на нём свои приложения, в том числе коммерческие, можно, а
публиковать или распространять код пака и его существенную часть — нельзя. Для нас это значит: кабинет
живёт только в закрытом репозитории. `VibeBrains/VibeMemory` приватный, решение «`cabinet/` в этом
репозитории» ограничению не противоречит; если репозиторий когда-нибудь откроют, `cabinet/` уезжает из
него первым. Раздачу бинарей это не задевает — кода пака в архивах нет.

## Память и соединения (macOS arm64, ориентир порядка)

- Сервер кабинета на bun 1.4.0 (phys_footprint — RSS на macOS шумит из-за сжатия памяти): 190–200 МБ
  после прогрева и на плато, пик 239–254 МБ; 400 запросов с сессией по 50 параллельно — 293 МБ, пик
  328 МБ. `--smol` ничего не даёт, bun 1.3.14 тяжелее примерно на 40 МБ.
- Postgres: 11–21 МБ без приложения; с приложением 8 соединений на старте, 3–5 в покое, до 14 под
  нагрузкой.
- **Бюджет соединений по умолчанию не сходится:** `PrismaPg` без `max` — пул `pg` на 10, pg-boss отдаёт
  свой конфиг в `pg.Pool` без `max` — ещё 10, бэкплейн — 3 и отдельное соединение LISTEN. До 24 при 17
  доступных (20 минус 3 резерва суперпользователя), а рядом ещё мигратор и `pg_dump` бэкапа. На стенде
  пик 14 — предел не достигнут случайно, а не по построению.
- Сборка 4,6 с, `dist` 88 МБ, из них 55 МБ — серверные source maps.
- Серверу хватает `dist` и **существующего** `node_modules` — пустой годится, без каталога старт падает
  «No node_modules found». Prod-зависимости — 1,2 ГБ (855 пакетов, из них `next` 171 МБ, который
  притягивает `react-email` из `dependencies` пака); из них живёт только мигратор
  (`prisma migrate deploy` прошёл за 1,8 с).
- На первом старте приложение само создаёт схемы `pgboss` и `point0` — роли кабинета нужен CREATE на
  базе.

На Linux x86_64 цифры не мерились: другой учёт RSS, другие бинари. Перемер на хосте той же методикой —
в фазе 3.

## Холодная установка

Первая установка на пустом кэше заняла 24 минуты (1167 пакетов), первая попытка встала на «Fail
extracting tarball for "prisma"». Прерванная установка оставляет `node_modules/.bin/bun` заглушкой без
postinstall, и каждый вложенный `bun` в скриптах падает «Bun's postinstall script was not run» —
лечится только `rm -rf node_modules && bun install` (с тёплым кэшем 3,8 с). Пак держит `bun@^1.4.0` в
devDependencies, и скрипты зовут его, а не системный bun.
