# Кабинет на хосте

Кабинет — сайт `app.vibememory.ru`: команды, коды-подарки, приглашения, выдача токенов агентам и
страница владельца хоста. Он живёт на том же хосте, что и сторы, под учёткой `vmcab`, и говорит с
сервером памяти только двумя файлами в `/srv/vibememory/access/`: сам пишет снимок прав
`access.json` ([спека](accessSnapshotSpec.md)), читает отчёт хоста `host.json`
([спека](hostStatusSpec.md)).

Все скрипты запускаются на Mac владельца из корня репозитория. Работа на сервере в каждом — один
ssh-сеанс; повторный запуск безопасен и печатает «без изменений».

## Порядок

1. `./infra/hostBootstrap.sh` — учётки `vmgit`, `vmcab`, каталоги `/srv/vibememory`, sshd
   ([hostSetup.md](hostSetup.md)).
2. `./infra/hostMcp.sh --binary …` — сервер памяти, первый снимок прав, команды хоста.
3. `./infra/backupSetup.sh` — ночной бэкап; повторите его после обновления `infra/hostBackup.sh`,
   он же доставляет скрипт на хост.
4. `./infra/hostCabinet.sh --owner-email <адрес>` — кабинет.
5. `./infra/cabinetPassword.sh` — пароль владельца, вводит сам владелец.
6. `./infra/cabinetSecrets.sh` — ключ Resend, бот Telegram, ссылка «поддержать», вводит сам владелец.
7. Релиз: `./infra/releaseBuild.sh` на Mac, `infra\releaseBuild.ps1` на GPD, затем
   `./infra/hostRelease.sh <версия>`.

## Выкладка: `hostCabinet.sh`

Скрипт собирает кабинет на Mac (`bun run build:code` в `cabinet/`) — на хосте нет ни сборки, ни
проверки типов. На хост едут только `dist/`, манифесты, схема Prisma и миграции; передача
возобновляется после обрыва.

На хосте, по шагам:

- Postgres 17 из PGDG, только `localhost`, `shared_buffers = 64MB`, `max_connections = 20`
- `.env` кабинета — `/home/vmcab/cabinet/.env`, 0600, `vmcab`; секреты (`BETTER_AUTH_SECRET`,
  пароль базы, `OPENAPI_CREDENTIALS`) генерируются на хосте один раз и не печатаются
- Роль `vmcab` — владелец базы `cabinet`; роль `vmgit` — `pg_read_all_data` и вход по peer, без
  пароля: ею ночью снимается дамп
- Bun той версии, на которой кабинет тестируется, под `vmcab`
- Зависимости только production, затем `prisma migrate deploy`
- Импорт владельца из `/srv/vibememory/access/access.json` — снимка, на котором хост уже работает
- Юнит `vibememory-cabinet` на `127.0.0.1:3000` — и скрипт проверяет, что порт слушает только
  loopback, джейл fail2ban `vibememory-cabinet`, журнал не больше 200 МБ, в конце Caddy из
  [шаблона](../../infra/Caddyfile.tmpl) — два сайта, один файл

Джейл считает строки, которые кабинет пишет в stderr отдельно от JSON-журнала:
`vibememory-cabinet: <что> refused from <адрес>`, где «что» — `sign-in`, `claim`, `code` (код-подарок)
или `invitation`. Адрес — последний `X-Forwarded-For`, то есть тот, что видел Caddy, и только IP:
строка с именем не пишется вовсе. Фильтр привязан к концу строки, а `usedns = no`: строка журнала, в
которую запрос вписал бы что-то своё (user-agent, путь), не банит никого.

**Первый запуск без `--owner-email` не запускает кабинет — так задумано.** Юнит спрашивает
`access:seeded` перед стартом и не поднимается на базе без владельца: кабинет на пустой базе
опубликовал бы пустой снимок поверх настоящего. Импорт берёт владельца (`handle`), личный стор и
строку `tk_legacy` из снимка хоста, адрес — из `--owner-email`; пароля импорт не ставит.

Импорт принимает только снимок, на котором хост работает: `teamCount: 1`, одна команда — личный стор,
и `applied.snapshotHash` в `host.json` равен хешу файла. И только если база после импорта отрисовывает
то же самое: поле, которое кабинет опубликовал бы иначе (например, личный стор без записи), отменяет
импорт, а не меняет хост первой же публикацией. Файл становится первой строкой журнала публикаций.

## Пароль владельца

```bash
./infra/cabinetPassword.sh
```

Пароль вводится на терминале хоста дважды, без эха, и не проходит ни через аргументы, ни через
файлы. Повторный запуск меняет пароль и закрывает сессии владельца.

## Письма и тревоги

Письма уходят через Resend, срочные тревоги хоста — ещё и в Telegram.

1. Аккаунт Resend, домен `vibememory.ru` подтверждён записями SPF и DKIM, которые Resend покажет.
2. Бот у @BotFather; в его чат владелец пишет `/start`, номер чата — из
   `https://api.telegram.org/bot<токен>/getUpdates` (открыть в браузере самому).
3. Внести всё в кабинет:

```bash
./infra/cabinetSecrets.sh
```

Секреты вводятся без эха и едут на хост через stdin ssh. Пустой ответ оставляет прежнее значение.

4. На странице владельца `Admin → Dashboard` кнопка «Send a test message» отвечает, что сделал
   каждый канал: `sent`, `skipped` или `failed`.

Тревоги: диск ниже 1 ГиБ или 10 %, служба не `active`, бэкап старше 25 часов, команда у 90 % квоты,
проблемы применения снимка, отчёт хоста старше двух часов, снимок не применён 15 минут, снимок не
опубликован сторожем. Одна и та же тревога повторяется не чаще раза в сутки; ушедшая забывается.

## Снимок и сторож

Кабинет публикует снимок после каждого изменения прав, при старте и раз в пять минут. Каждая
публикация — строка журнала в базе: сначала строка, потом файл, потом отметка «записан». Поэтому
снимок на хосте всегда либо последний записанный, либо тот, что в пути.

Каждый снимок кабинета несёт номер `serial` — на единицу больше всех номеров журнала. Хост к меньшему
номеру не возвращается: применив снимок, он кладёт рядом копию `applied-snapshot.json` и держится её,
пока не придёт снимок новее ([accessSnapshotSpec.md](accessSnapshotSpec.md)). Публикация, проигравшая
очередь, или старый файл, возвращённый руками, хост назад не откатывают.

Кабинет **не** публикует — и не меняет ничего, от команды до бана, — если база не может говорить за
хост:

- В базе нет владельца
- На хосте снимок, которого эта база не писала: `access.json`, копия применённого
  `applied-snapshot.json` или тот, что хост называет применённым в отчёте. Так выглядит база,
  восстановленная из дампа: она потеряла строки всего, что публиковалось после дампа, а с ними — отзывы.
  Число команд тут не показатель: дамп теряет отозванный токен и удалённого участника, не теряя команд
- На хосте нет ни `access.json`, ни копии применённого, а база уже публиковала: что хост потерял,
  не сказать
- `host.json` есть, но не читается

Свой старый файл на хосте — не повод: хост к нему не возвращается, а следующая публикация пишет файл
заново под новым номером. Пропавший `access.json` рядом со своей копией — тоже: хост закрыл дверь и
ждёт файла, следующая публикация его пишет.

Отдельно: снимок, который отвергает `access check`, не публикуется никогда. Хост во всех случаях
работает на последнем своём снимке, владелец получает тревогу, а участники видят на странице команды
«on the host: changes held back».

Осознанный выход — например, после восстановления базы из дампа — сначала посмотреть, что будет:

```bash
ssh vibememory "sudo -u vmcab -H bash -c 'cd /home/vmcab/cabinet && NODE_ENV=production /home/vmcab/.bun/bin/bun run access:publish --force --reason \"база восстановлена из дампа 2026-09-22\" --dry-run'"
```

Затем то же без `--dry-run`. Принудительная публикация сначала переносит в базу отзывы и баны из
снимка, по которому живёт хост, — из новейшего из `access.json` и копии применённого. Всё, что база
разрешила бы, а хост уже не разрешает, отзывается и в базе — токены, ключи, участники, понижения,
архивные проекты, удалённые и убранные команды. Id и слаги не переиспользуются, поэтому отсутствие на
хосте всегда означает отзыв. Личный стор и владельцы команд так не трогаются — кабинет и сам не может
их отнять. То, что есть у хоста сверх базы (команды, люди и токены после дампа), не возвращается:
команды станут сиротами, люди — приглашениями заново.

Токены и ключи сравниваются по живым строкам базы, а не по тому, что база опубликовала бы. Токен
забаненного, ключ участника без живой команды спят вне снимка и проснулись бы со снятием бана или
вступлением в команду. Отзывали ли их за это время, хост не скажет, поэтому живая строка, которой нет
на хосте, отзывается: человек подключится заново, а потерянный с дампом отзыв не проснётся. Баны хоста
возвращаются в базу, сессии забаненных закрываются; бан, который хост держит дольше, продлевается до
его срока. Бан, который есть только в базе, остаётся: перенос отнимает, но не даёт. Номер
принудительного снимка — выше всего, что было у хоста.

Причина попадает в журнал и в строку публикации, перенесённое печатается по видам. Владельца и бинарь
не обходит ничто. `access.json`, который не читается, останавливает и принудительную публикацию: его
отзывы не перенести, и отложить файл в сторону — решение владельца; тогда перенос идёт из копии
применённого. Если на хосте нет ни файла, ни копии, переносить не из чего, и публикация требует ещё
`--without-carrying`: владелец подтверждает, что знает об этом.

## Восстановление базы из дампа

Дамп лежит в ночном бэкапе (`cabinet.pgdump.age`, [hostSetup.md](hostSetup.md)).

1. На Mac: `age -d -i ~/.vibememory/keys/backup.age cabinet.pgdump.age > cabinet.pgdump`,
   скопировать на хост.
2. На хосте: `sudo systemctl stop vibememory-cabinet`, затем
   `sudo -u vmcab pg_restore --clean --if-exists --no-owner --dbname=cabinet cabinet.pgdump`.
3. `sudo systemctl start vibememory-cabinet` — сторож откажет публиковать и менять что-либо
   (`behindHost`). Это правильно: без отказа кабинет вернул бы на хост всё, что отозвали после дампа.
4. `access:publish --force --reason … --dry-run` — посмотреть, что перенесётся из снимка хоста; затем
   то же без `--dry-run` (раздел выше). Каталоги команд, которых нет в базе, хост не трогает и
   показывает как сирот.

`access.json` и `applied-snapshot.json` из бэкапа не восстанавливают никогда: их пишут кабинет и
применятель. Старый файл хост и так не применит, а удалённая копия ослабила бы защиту от старых
файлов.
5. На странице владельца, раздел «Orphaned directories»: «Take it back» с владельцем команды и
   причиной. Члены, токены и ключи после дампа не возвращаются: участников приглашают заново, и они
   делают `vibememory connect` снова; старые токены отвечают `401`.

## Бан пользователя

Страница пользователя в разделе владельца, карточка «Ban»: причина и, по желанию, срок. Пока бан
действует, пользователь не входит, его сессии закрыты, а все его токены и ключи машин уходят из снимка —
хост их не пускает. Строки не отзываются: снятие бана или конец срока возвращают их в следующем снимке.
Админа кабинета и самого себя не банят. Эндпоинты admin-плагина better-auth, меняющие пользователей
(`ban-user`, `set-role`, `update-user`, `remove-user` и прочие), на запросы отвечают `403`: это делает
кабинет, в своей транзакции; открыта только имперсонация. Имперсонация — только просмотр: админ видит
кабинет глазами пользователя, но ни одна мутация и ни одно действие кабинета, ни смена пароля, адреса или
учётки better-auth от имени пользователя не проходят (`403`); остаются чтение, выход из имперсонации и
выход из учётки. Начинается она только кнопкой на странице пользователя.

## Удалённые команды

Удаление в кабинете мягкое: хост переименовывает стор в `teams/<слаг>.deleted-<дата>.git` и ничего не
стирает. Убрать каталог — решение владельца хоста:

```bash
ssh vibememory "sudo -u vmgit rm -rf /srv/vibememory/teams/<слаг>.deleted-<дата>.git"
```

Следующий отчёт хоста его не покажет, и кабинет уберёт маркер из снимка сам — если каталога команды
нет нигде: ни переименованного, ни ждущего переименования (`retiring` в `host.json`), и последнее
применение не назвало проблемы с этой командой. Слаг не освобождается никогда.

## Восстановление стора команды

- **`memory`-стор** — из ночного бэкапа: `age -d` бандла и `git clone --bare`, как в
  [hostSetup.md](hostSetup.md); на хост кладётся копией под `vmgit` в `/srv/vibememory/teams/<слаг>.git`.
- **`sync`-стор** — из клона любого участника, **копией, не push'ем**: `pre-receive` отвергнет push
  чужих `machines/*`. У участника `git clone --bare ~/.vibememory/stores/<id>/store /tmp/<слаг>.git`,
  копия на хост под `vm`, затем `sudo install -d -o vmgit -g vibememory -m 2770
  /srv/vibememory/teams/<слаг>.git`, `sudo rsync -a --chown=vmgit:vibememory` содержимого туда же и
  `sudo -u vmgit /srv/vibememory/bin/storeInit.sh /srv/vibememory/teams/<слаг>.git` — хуки клона не
  переносятся. Если строки команды в базе нет — «Take it back» на странице владельца.

## Релизы

```bash
./infra/releaseBuild.sh              # macOS arm64 и x86_64, Linux x86_64 в контейнере
./infra/hostRelease.sh 0.1.0         # проверка сумм и состава, выкладка, index.json
```

На GPD: `powershell -ExecutionPolicy Bypass -File infra\releaseBuild.ps1` — архив Windows и сумма
уходят в тот же `~/releases/incoming/<версия>/`. `hostRelease.sh` отвергает версию целиком, если
сумма не сходится или в архиве не ровно два бинаря (`vibememory`, `vibememory-mcp`, для Windows —
с `.exe`). Опубликованное раздаётся с `https://app.vibememory.ru/dl/<версия>/`, страница «Скачать»
читает `index.json`. Копия сборок Mac — в `/Volumes/Storage/Caches/VibeMemory/releases/<версия>/`.

## Локальная среда тестов

В `cabinet/`: Postgres в Docker — `docker compose up -d db` (порт 5433, базы `cabinet` и
`cabinet-test`); `.env` и `.env.test` задают `VIBEMEMORY_MCP_BIN` — абсолютный путь к
`target/debug/vibememory-mcp` после `cargo build -p vibememory-mcp`, и `ACCESS_DIR` в
`/Volumes/Storage/Caches/VibeMemory/`. Проверка перед коммитом: `bun run check && bun run test`.
