# Кабинет на хосте

Кабинет — сайт `app.vibememory.ru`: команды, коды-подарки, приглашения, выдача токенов агентам и
страница владельца хоста. Он живёт на том же хосте, что и сторы, под учёткой `vmcab`, и говорит с
сервером памяти только двумя файлами в `/srv/vibememory/access/`: сам пишет снимок прав
`access.json` ([спека](accessSnapshotSpec.md)), читает отчёт хоста `host.json`
([спека](hostStatusSpec.md)).

Все скрипты запускаются на Mac владельца из корня репозитория. Работа на сервере в каждом — один
ssh-сеанс; повторный запуск безопасен и печатает «без изменений».

## Порядок

1. `./infra/hostBootstrap.sh` — учётки `vmgit`, `vmcab`, каталоги `/srv/vibememory`, sshd
   ([hostSetup.md](hostSetup.md)).
2. `./infra/hostMcp.sh --binary …` — сервер памяти, первый снимок прав, команды хоста.
3. `./infra/backupSetup.sh` — ночной бэкап; повторите его после обновления `infra/hostBackup.sh`,
   он же доставляет скрипт на хост.
4. `./infra/hostCabinet.sh --owner-email <адрес>` — кабинет и дамп его базы в бэкап. Роль `vmgit`
   в базе, если она осталась от прежней схемы, скрипт снимает, только когда скрипт бэкапа на хосте уже
   берёт готовый дамп: иначе бэкап молча остался бы без базы. Тогда он так и пишет — запустите
   `backupSetup.sh`, затем этот скрипт ещё раз.
5. `./infra/cabinetPassword.sh` — пароль владельца, вводит сам владелец.
6. `./infra/cabinetSecrets.sh` — ключ Resend и бот Telegram, вводит сам владелец; ключ и домен отправителя скрипт сперва проверяет в Resend.
7. Релиз: `./infra/releaseBuild.sh` на Mac — macOS, Linux и Windows, затем
   `./infra/hostRelease.sh <версия>`.

## Выкладка: `hostCabinet.sh`

Скрипт собирает кабинет на Mac (`bun run build:code` в `cabinet/`) — на хосте нет ни сборки, ни
проверки типов. На хост едут только `dist/`, манифесты, схема Prisma и миграции; передача
возобновляется после обрыва.

На хосте, по шагам:

- Postgres 17 из PGDG, только `localhost`, `shared_buffers = 64MB`, `max_connections = 20`
- `.env` кабинета — `/home/vmcab/cabinet/.env`, 0600, `vmcab`; секреты (`BETTER_AUTH_SECRET`,
  пароль базы, `OPENAPI_CREDENTIALS`) генерируются на хосте один раз и не печатаются
- Роль `vmcab` — владелец базы `cabinet`; учётка и роль `vmdump` — `pg_read_all_data` и вход по
  peer, без пароля: ею перед каждым бэкапом юнит `vibememory-dump` снимает дамп и сразу шифрует его
  открытым ключом владельца (`infra/cabinetDump.sh`) в `/srv/vibememory/backup/dump/`. Бэкап под `vmgit`
  ждёт этот юнит и берёт готовый шифротекст; своей роли в базе у `vmgit` нет, и подключаться к базе
  может только владелец и `vmdump`
- better-auth хранит ссылки сброса пароля и подтверждения адреса хешем, а токены Google — шифром
  под `BETTER_AUTH_SECRET`: дамп базы сам по себе ни ссылки, ни доступа к Google не даёт
- Bun той версии, на которой кабинет тестируется, под `vmcab`
- Зависимости только production, затем `prisma migrate deploy`
- Импорт владельца из `/srv/vibememory/access/access.json` — снимка, на котором хост уже работает
- Юнит `vibememory-cabinet` на `127.0.0.1:3000` — и скрипт проверяет, что порт слушает только
  loopback, джейл fail2ban `vibememory-cabinet`, журнал не больше 200 МБ, в конце Caddy из
  [шаблона](../../infra/Caddyfile.tmpl) — все сайты хоста, один файл

Джейл считает строки, которые кабинет пишет в stderr отдельно от JSON-журнала:
`vibememory-cabinet: <что> refused from <адрес>`, где «что» — `sign-in`, `password` (неверный текущий
пароль при его смене), `claim`, `code` (код-подарок) или `invitation`. Адрес — последний
`X-Forwarded-For`, то есть тот, что видел Caddy, и только IP: строка с именем не пишется вовсе. Фильтр
привязан к концу строки, а `usedns = no`: строка журнала, в которую запрос вписал бы что-то своё
(user-agent, путь), не банит никого. Новое слово в фильтре приезжает с `hostCabinet.sh`.

Джейл считает по адресу, и перебор паролей с многих адресов он не видит. Поэтому кабинет считает и по
учётке: 10 неверных паролей за 15 минут — при входе или при смене пароля — ставят вход в эту учётку на
паузу, пока окно не очистится, с любого адреса и с любым паролем, верным тоже (`429`). Адрес без учётки
встаёт на паузу так же — ответ не говорит, есть ли учётка. Попытки, посланные разом, считаются все:
место в счёте занимается до проверки пароля, под замком на учётку, так что мимо паузы не проходит
больше 10 паролей. Вход считается и в теле-форме
(`application/x-www-form-urlencoded`), которое better-auth тоже принимает; иное тело better-auth
отвергает (`415`) до проверки пароля. Владелец получает письмо и сообщение в Telegram один раз на паузу; письмо уходит
в фоне, и ответ по существующей учётке не медленнее ответа по чужому адресу. Учётка хранится
HMAC-SHA256 адреса под `BETTER_AUTH_SECRET`: по дампу не узнать, кого подбирали, перебором списка
адресов.

Пароль и сессии:

- Новый пароль закрывает все остальные сессии учётки, даже если запрос об этом не просил; сброс по
  письму закрывает все
- На странице профиля «Sign out everywhere else» закрывает все сессии, кроме текущей
- Адрес меняется только с подтверждённого: подтверждение изменения приходит на текущий адрес, а
  неподтверждённый ничего не доказывает. Сначала — «Send verification email»
- Пароль проверяется только входом и сменой пароля, которые считает пауза. Эндпоинты better-auth, которыми
  кабинет не пользуется, — `/verify-password`, `/delete-user` — отвечают `404`
- ID-токен Google не хранится: кабинет его не читает, и дамп его не несёт

**Условие для IPv6.** Джейл банит адрес целиком. Сейчас у хоста нет глобального IPv6, и клиент
приходит одним адресом IPv4. Если хост получит IPv6, у одного клиента окажется /64 — миллиарды адресов,
и бан по одному ничего не даст: тогда либо Caddy слушает только IPv4, либо джейл банит /64. Пауза по
учётке работает при любом числе адресов.

**Первый запуск без `--owner-email` не запускает кабинет — так задумано.** Юнит спрашивает
`access:seeded` перед стартом и не поднимается на базе без владельца: кабинет на пустой базе
опубликовал бы пустой снимок поверх настоящего. Импорт берёт владельца (`handle`), личный стор и
строку `tk_legacy` из снимка хоста, адрес — из `--owner-email`; пароля импорт не ставит.

Импорт принимает только снимок, на котором хост работает: `teamCount: 1`, одна команда — личный стор,
и `applied.snapshotHash` в `host.json` равен хешу файла. И только если база после импорта отрисовывает
то же самое: поле, которое кабинет опубликовал бы иначе (например, личный стор без записи), отменяет
импорт, а не меняет хост первой же публикацией. Файл становится первой строкой журнала публикаций.

## Пароль владельца

```bash
./infra/cabinetPassword.sh
```

Пароль вводится на терминале хоста дважды, без эха, и не проходит ни через аргументы, ни через
файлы. Повторный запуск меняет пароль и закрывает сессии владельца.

## Письма и тревоги

Письма уходят через Resend, срочные тревоги хоста — ещё и в Telegram.

1. Аккаунт Resend, домен `vibememory.ru` подтверждён записями SPF и DKIM, которые Resend покажет.
2. Бот у @BotFather; в его чат владелец пишет `/start`, номер чата — из
   `https://api.telegram.org/bot<токен>/getUpdates` (открыть в браузере самому).
3. Внести всё в кабинет:

```bash
./infra/cabinetSecrets.sh
```

Секреты вводятся без эха и едут на хост через stdin ssh. Пустой ответ оставляет прежнее значение.

4. На странице владельца `Admin → Dashboard` кнопка «Send a test message» отвечает, что сделал
   каждый канал: `sent`, `skipped` или `failed`.

Тревоги: диск ниже 1 ГиБ или 10 %, служба не `active`, бэкап старше 25 часов, команда у 90 % квоты,
проблемы применения снимка, отчёт хоста старше двух часов, снимок не применён 15 минут, снимок не
опубликован сторожем. Одна и та же тревога повторяется не чаще раза в сутки; ушедшая забывается.

## Снимок и сторож

Кабинет публикует снимок после каждого изменения прав, при старте и раз в пять минут. Каждая
публикация — строка журнала в базе: сначала строка, потом файл, потом отметка «записан». Поэтому
снимок на хосте всегда либо последний записанный, либо тот, что в пути.

Каждый снимок кабинета несёт номер `serial` — на единицу больше всех номеров журнала. Хост к меньшему
номеру не возвращается: применив снимок, он кладёт рядом копию `applied-snapshot.json` и держится её,
пока не придёт снимок новее ([accessSnapshotSpec.md](accessSnapshotSpec.md)). Публикация, проигравшая
очередь, или старый файл, возвращённый руками, хост назад не откатывают.

Кабинет **не** публикует — и не меняет ничего, от команды до бана, — если база не может говорить за
хост:

- В базе нет владельца
- На хосте снимок, которого эта база не писала: `access.json`, копия применённого
  `applied-snapshot.json` или тот, что хост называет применённым в отчёте. Так выглядит база,
  восстановленная из дампа: она потеряла строки всего, что публиковалось после дампа, а с ними — отзывы.
  Число команд тут не показатель: дамп теряет отозванный токен и удалённого участника, не теряя команд
- На хосте нет ни `access.json`, ни копии применённого, а база уже публиковала: что хост потерял,
  не сказать
- `host.json` есть, но не читается

Свой старый файл на хосте — не повод: хост к нему не возвращается, а следующая публикация пишет файл
заново под новым номером. Пропавший `access.json` рядом со своей копией — тоже: хост закрыл дверь и
ждёт файла, следующая публикация его пишет.

Отдельно: снимок, который отвергает `access check`, не публикуется никогда. Хост во всех случаях
работает на последнем своём снимке, владелец получает тревогу, а участники видят на странице команды
«on the host: changes held back».

Осознанный выход — принудительная публикация. После восстановления базы из дампа это команда
`access:restored` (раздел «Восстановление базы из дампа»), в остальных случаях — например, хост
потерял файлы снимков — `access:publish --force`. Сначала посмотреть, что будет:

```bash
ssh vibememory "sudo -u vmcab -H bash -c 'cd /home/vmcab/cabinet && NODE_ENV=production /home/vmcab/.bun/bin/bun run access:publish --force --reason \"хост переставлен\" --dry-run'"
```

Затем то же без `--dry-run`. Принудительная публикация сначала переносит в базу отзывы и баны из
снимка, по которому живёт хост, — из новейшего из `access.json` и копии применённого, и только если
он проходит проверку бинаря, как его проходит хост. Всё, что база
разрешила бы, а хост уже не разрешает, отзывается и в базе — токены, ключи, участники, понижения,
архивные проекты, удалённые и убранные команды. Id и слаги не переиспользуются, поэтому отсутствие на
хосте всегда означает отзыв. Личный стор и владельцы команд так не трогаются — кабинет и сам не может
их отнять. То, что есть у хоста сверх базы (команды, люди и токены после дампа), не возвращается:
команды станут сиротами, люди — приглашениями заново.

Токены и ключи сравниваются по живым строкам базы, а не по тому, что база опубликовала бы. Токен
забаненного, ключ участника без живой команды спят вне снимка и проснулись бы со снятием бана или
вступлением в команду. Отзывали ли их за это время, хост не скажет, поэтому живая строка, которой нет
на хосте, отзывается: человек подключится заново, а потерянный с дампом отзыв не проснётся. Баны хоста
возвращаются в базу, сессии забаненных закрываются; бан, который хост держит дольше, продлевается до
его срока. Бан, который есть только в базе, остаётся: перенос отнимает, но не даёт. Номер
принудительного снимка — выше всего, что было у хоста.

Причина попадает в журнал и в строку публикации; перенесённое печатается по видам. Владельца и
бинарь не обходит ничто. `access.json`, который не читается или не проходит проверку, останавливает
и принудительную публикацию: хост по нему не живёт, а перенос из копии — решение владельца, потому что
копия старше базы отняла бы то, что база сделала после неё. Владелец откладывает файл в сторону, и
перенос идёт из копии; копия, которая не читается или не проходит проверку, так же останавливает
публикацию. Если на хосте нет ни файла, ни копии, переносить не из чего, и публикация требует ещё
`--without-carrying`: владелец подтверждает, что знает об этом.

`access:publish --force` ничего не сбрасывает: база, отставшая от хоста, не обязательно восстановлена
из дампа — хост мог просто потерять свои файлы, и стирать пароли здоровой базе незачем.

### Сброс после восстановления: `access:restored`

Восстановление из дампа распознать по базе нельзя. Дамп, снятый после последнего изменения прав,
не оставляет на хосте ни одного незнакомого снимка, но возвращает всё, что закрыли после него:
вышедшую сессию, отозванное приглашение, использованный или остановленный код, пароль, сменённый
после утечки. Поэтому сброс — слово владельца, отдельная команда:

```bash
ssh vibememory "sudo -u vmcab -H bash -c 'cd /home/vmcab/cabinet && NODE_ENV=production /home/vmcab/.bun/bin/bun run access:restored --reason \"база восстановлена из дампа 2026-09-22\" --dry-run'"
```

Затем то же без `--dry-run`. Команда переносит отзывы хоста, если база от него отстала (как
`--force`, с теми же отказами и `--without-carrying`), и всегда сбрасывает:

- Закрываются все сессии и все ссылки сброса пароля и подтверждения адреса
- Отзываются все непринятые приглашения, истекают все неиспользованные коды подключения,
  останавливаются коды-подарки, у которых остались активации
- Стираются все пароли. После коммита каждой учётке без бана, у которой пароль был, уходит письмо со
  ссылкой сброса; вход — только через неё. Свой пароль владелец задаёт заново
  `./infra/cabinetPassword.sh` — письма могут и не ходить, если почта ещё не настроена
- Имена, которые хост знал, а база нет, занимаются навсегда: хэндлы участников из команд, токенов,
  ключей и банов снимков хоста и каталоги машин `machines/<storeName>/`. Под ними на хосте лежат
  записи и каталоги потерянных людей и машин, и новый человек под тем же именем писал бы в чужое.
  Бан такого хэндла на хосте остаётся в снимке до своего срока. Хэндл отвечает при регистрации
  «This handle is taken», имя машины — «This machine name is taken on the host». Каталог машины
  помнит своего участника: участник, переживший восстановление, подключает ту же машину под её
  прежним именем

Сброшенное печатается по видам; `--dry-run` показывает его и откатывает, писем не уходит.

## Восстановление базы из дампа

Дамп лежит в ночном бэкапе (`cabinet.pgdump.age`, [hostSetup.md](hostSetup.md)).

1. На Mac: `age -d -i ~/.vibememory/keys/backup.age cabinet.pgdump.age > cabinet.pgdump`,
   скопировать на хост.
2. На хосте: `sudo systemctl stop vibememory-cabinet`, затем
   `sudo -u vmcab pg_restore --clean --if-exists --no-owner --dbname=cabinet cabinet.pgdump`.
3. `sudo systemctl start vibememory-cabinet` — если после дампа права менялись, сторож откажет
   публиковать и менять что-либо (`behindHost`). Это правильно: без отказа кабинет вернул бы на хост всё,
   что отозвали после дампа.
4. `access:restored --reason … --dry-run` — посмотреть, что перенесётся из снимка хоста и что
   сбросится; затем то же без `--dry-run` (раздел выше). Делается всегда, даже если сторож не отказал:
   дамп, снятый после последнего изменения прав, сторож не замечает. Каталоги команд, которых нет в
   базе, хост не трогает и показывает как сирот.
5. `./infra/cabinetPassword.sh` — пароль владельца: команда стёрла все пароли.
6. На странице владельца, раздел «Orphaned directories»: «Take it back» с владельцем команды и
   причиной. Члены, токены и ключи после дампа не возвращаются: участников приглашают заново, и они
   делают `vibememory connect` снова; старые токены отвечают `401`. Остальные входят по письму сброса.

`access.json` и `applied-snapshot.json` из бэкапа не восстанавливают никогда: их пишут кабинет и
применятель. Старый файл хост и так не применит, а удалённая копия ослабила бы защиту от старых
файлов.

## Бан пользователя

Страница пользователя в разделе владельца, карточка «Ban»: причина и, по желанию, срок. Пока бан
действует, пользователь не входит, его сессии закрыты, а все его токены и ключи машин уходят из снимка —
хост их не пускает. Строки не отзываются: снятие бана или конец срока возвращают их в следующем снимке.
Админа кабинета и самого себя не банят. Эндпоинты admin-плагина better-auth, меняющие пользователей
(`ban-user`, `set-role`, `update-user`, `remove-user` и прочие), на запросы отвечают `403`: это делает
кабинет, в своей транзакции; открыта только имперсонация. Имперсонация — только просмотр: админ видит
кабинет глазами пользователя, но ни одна мутация и ни одно действие кабинета, ни смена пароля, адреса или
учётки better-auth от имени пользователя не проходят (`403`); остаются чтение, выход из имперсонации и
выход из учётки. Начинается она только кнопкой на странице пользователя.

## Тарифы

Команда платит за место на хосте, а не за людей: людей в ней сколько угодно, в снимке прав нет
`seats`. Квота команды — место её идущего гранта, а без гранта — бесплатное место. Кончился грант —
команда не закрывается, а возвращается на бесплатное место: пишет в его пределах, сверх него хост
отвечает `quota_exceeded`, чтение и «забыть» работают.

Цены и размеры — в `.env` кабинета, без выпуска:

| Ключ | По умолчанию | Что задаёт |
|---|---|---|
| `FREE_QUOTA_BYTES` | 52428800 (50 МБ) | место бесплатной команды |
| `TRIAL_QUOTA_BYTES` | 314572800 (300 МБ) | пробное место сессий: команда получает его один раз, когда впервые включает сессии |
| `TRIAL_DAYS` | 14 | сколько дней длится пробный период сессий |
| `TRIAL_WARN_DAYS` | 3 | за сколько дней до конца пробного периода уходит письмо: потом сессии выключаются и удаляются с сервера |
| `PRICING_TIERS` | 200 МБ — 100 ₽, 300 МБ — 150 ₽, 500 МБ — 200 ₽, 1 ГБ — 350 ₽ | тарифы: JSON `[{"quotaBytes":…,"priceRub":…}]`, размер в байтах, цена в рублях за месяц |
| `FREE_POOL_BYTES` | 10737418240 (10 ГБ) | сколько места хоста отдано бесплатным командам |
| `PAID_POOL_BYTES` | 16106127360 (15 ГБ) | сколько — платным |

Грант хранит место и цену, по которым куплен: новая цена в конфиге не трогает оплаченный период.
Код-подарок и ручной грант дают место только тарифа из этого списка. Второй грант встаёт в очередь
после идущего; из идущих одновременно действует больший.

## Регистрация и очередь

Страница `/start` заводит учётку и бесплатную команду одной формой; вход — сразу, ссылка подтверждения почты уходит
тут же. Регистрация открыта, только когда почта настроена (`RESEND_API_KEY` не плейсхолдер пака): без писем не работают
ни подтверждение, ни очередь, и страница честно говорит «откроется скоро». Бесплатный пул кончился — вместо формы
очередь: адрес подтверждается письмом, раз в час задача пишет всем подтверждённым, когда место освободилось, — одному
адресу не чаще раза в неделю. С одного адреса — не больше трёх регистраций в сутки и пяти писем очереди в час.
Очередь и роздано места — в админке, «Очередь». Команда без подтверждённой почты владельца отдаёт место через
`UNVERIFIED_TEAM_DAYS` дней.

## Жизнь бесплатной команды и архивы

Раз в сутки задача решает судьбу команд, которые не платят (правила — `features/lifecycle/rules.ts`):
- активность — последний запрос агента (хост пишет время в `/srv/vibememory/activity/<слаг>`, отчёт отдаёт его как
  `lastAccessAt`), последний коммит, последний вход участника
- 30 дней без активности — письмо владельцу и админам, на 53-й — последнее, на 60-й — архив памяти письмом и удаление;
  без письма, которому хотя бы неделя, команда не удаляется
- кончилась оплата, а память больше бесплатного места — только чтение: письмо раз в неделю, через `READ_ONLY_DAYS`
  удаление
- владелец не подтвердил почту — через `UNVERIFIED_TEAM_DAYS` команда отдаёт место

Архив собирает хост: кабинет кладёт `<id>.request` в `/srv/vibememory/exports` (группа `vmaccess`, sticky), юнит
`vibememory-export.path` строит `<id>.zip`, кабинет раз в минуту его замечает и убирает свой запрос. Ссылка
`/api/export/<секрет>` отдаёт архив, пока хост его держит — 30 дней. В админке у бесплатной команды — «Отключить»:
архив письмом, потом удаление.

## Оплата и сообщения

Перевод по QR применяется в админке «Платежи»: короткое имя и месяцы — из комментария к переводу, сумма — из банка.
Сумма не равна цене тарифа, умноженной на месяцы, — платёж отвергается, пока не отмечено «принять сумму».
Команде уходит письмо «оплата получена».

Сообщения команд — в админке «Сообщения», ответ — там же, в переписке команды.

| Ключ | По умолчанию | Что задаёт |
|---|---|---|
| `TEAM_MESSAGES_PER_DAY` | 5 | сколько сообщений команда может отправить за сутки |
| `MESSAGE_NOTICE_MINUTES` | 60 | как часто, самое частое, новые сообщения команды будят владельца письмом |

## Удалённые команды

Удаление в кабинете мягкое: хост переименовывает стор в `teams/<слаг>.deleted-<дата>.git` и ничего не
стирает. Убрать каталог — решение владельца хоста:

```bash
ssh vibememory "sudo -u vmgit rm -rf /srv/vibememory/teams/<слаг>.deleted-<дата>.git"
```

Следующий отчёт хоста его не покажет, и кабинет уберёт маркер из снимка сам — если каталога команды
нет нигде: ни переименованного, ни ждущего переименования (`retiring` в `host.json`), и последнее
применение не назвало проблемы с этой командой. Слаг не освобождается никогда.

## Восстановление стора команды

- **`memory`-стор** — из ночного бэкапа: `age -d` бандла и `git clone --bare`, как в
  [hostSetup.md](hostSetup.md); на хост кладётся копией под `vmgit` в `/srv/vibememory/teams/<слаг>.git`.
- **`sync`-стор** — из клона любого участника, **копией, не push'ем**: `pre-receive` отвергнет push
  чужих `machines/*`. У участника `git clone --bare ~/.vibememory/stores/<id>/store /tmp/<слаг>.git`,
  копия на хост под `vm`, затем `sudo install -d -o vmgit -g vibememory -m 2770
  /srv/vibememory/teams/<слаг>.git`, `sudo rsync -a --chown=vmgit:vibememory` содержимого туда же и
  `sudo -u vmgit /srv/vibememory/bin/storeInit.sh /srv/vibememory/teams/<слаг>.git` — хуки клона не
  переносятся. Если строки команды в базе нет — «Take it back» на странице владельца.

## Релизы

```bash
./infra/releaseBuild.sh              # macOS arm64 и x86_64, Linux x86_64 в контейнере
./infra/hostRelease.sh 0.1.0         # проверка сумм и состава, выкладка, index.json
```

На GPD: `powershell -ExecutionPolicy Bypass -File infra\releaseBuild.ps1` — архив Windows и сумма
уходят в тот же `~/releases/incoming/<версия>/`. `hostRelease.sh` отвергает версию целиком, если
сумма не сходится или в архиве не ровно два бинаря (`vibememory`, `vibememory-mcp`, для Windows —
с `.exe`). Опубликованное раздаётся с `https://app.vibememory.ru/dl/<версия>/`, страница «Скачать»
читает `index.json`. Копия сборок Mac — в `/Volumes/Storage/Caches/VibeMemory/releases/<версия>/`.

## Статистика: `hostStats.sh`

`./infra/hostStats.sh` — отчёт по продукту и серверу, только чтение.
Продукт: пользователи, команды и их тарифы (бесплатный, пробный с датой конца, платный), проекты с памятью и сессиями,
агенты по участникам, машины.
Сервер: нагрузка CPU, память, диск, службы.
Данные — из базы кабинета ролью `postgres` по peer и из отчёта хоста `host.json`, секреты наружу не уходят.

## Демо-сайт: `demoDeploy.sh`

`demo.vibememory.ru` — статические страницы для людей вне продукта: презентация, демо.
Сайт описан в том же [шаблоне](../../infra/Caddyfile.tmpl), что и остальные, и ставится `caddyApply.sh`.
Страницы живут вне этого репозитория и выкладываются одной командой:

```bash
./infra/demoDeploy.sh <каталог с index.html>
```

Сборка ложится в `/srv/vibememory/demo/<сборка>`, ссылка `current` переключается одним переименованием.
Имя сборки — хеш имён и содержимого страниц: те же страницы дают ту же сборку.
Три последние сборки остаются для отката руками.

## Лендинг VibeIDE: vibeide.ru

Сайты семейства живут на одном хосте, поэтому `vibeide.ru` описан в том же [шаблоне](../../infra/Caddyfile.tmpl).
Страницы отдаются с `no-cache`: в них ссылки на свежие сборки VibeIDE.
Ассеты Astro (`/_astro/`) именованы по содержимому и кэшируются навсегда.
`www.vibeide.ru` перенаправляет на основной адрес.
Сборку кладёт `deploy.sh` репозитория сайта в `/srv/vibeide/site/<коммит>`, по той же схеме с `current`.
