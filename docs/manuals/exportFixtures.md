# Как добавить кейс в `fixtures/export/`

Гейт экспорта решает единственный вопрос: **уходит ли путь `~/.claude` в стор**. Стор — git с
remote, поэтому ошибка гейта — это утечка на все машины и в зеркало, а не локальная опечатка.
Правила живут в `crates/vibememory-core/src/export.rs` двумя списками, ожидания — в
`fixtures/export/exportScenarios.json`, драйвер — `crates/vibememory-core/tests/export_fixtures.rs`.

## Формат кейса

```json
{
  "id": "sessions-registry",
  "provenance": "observed",
  "note": "Реестр живых сессий с peer-токенами.",
  "path": "sessions/11111111-1111-4111-8111-111111111111.json",
  "size": 12,
  "expect": { "decision": "refuse", "refusal": "secret" }
}
```

- `id` — уникальный в файле, kebab-case; драйвер падает на дубле.
- `provenance` — `observed` (путь снят с реальной описи `~/.claude`), `computed` (путь построен
  по правилу: порог размера, оборона в глубину, незнакомый файл), `unverified` (каталог заводит
  другая платформа или Desktop, на этой машине его нет).
- `note` — зачем кейс; пустая строка роняет драйвер.
- `path` — относительно каталога конфигурации, разделитель `/`.
- `size` — необязателен: только там, где решает порог. У каталога размера нет.
- `expect.decision` — `export` или `refuse`; у `refuse` обязателен `refusal`
  (`secret` | `machineLocal` | `notListed` | `tooLarge`), у `export` его быть не должно.

## Порядок добавления

1. Кейс в JSON — **ожидание пишется руками из описи или правила, никогда из вывода модуля**.
2. `cargo test --test export_fixtures` — падение до правки списка и есть смысл кейса.
3. Правило в `export.rs`, если его там ещё нет; отказ несёт человеческую причину — её показывает
   `doctor`, поэтому «нельзя» без объяснения не проходит.
4. Мутационная проверка **в копии файла, не через `git checkout`**: снять правило (или
   перевернуть дефолт на «разрешено») — тест обязан упасть с внятным различием.

## Чего кейсом не проверить

Добавление пути в белый список ничего не меняет для того, что уже в чёрном: чёрный список
проверяется первым, и это намеренно. Поэтому мутация «разрешим `sessions/`» проходит зелёной —
она не опровергает гейт. Опровергают её две другие: **снять** запись из чёрного списка и
**перевернуть дефолт** на «разрешено, пока не запрещено». Обе прогнаны 2026-09-03 и обе падают.


## Урок 2026-09-05: `sessions` внутри `projects/`

Кейс `sessions-inside-allowed` ожидал отказ — это была моя гипотеза «оборона в глубину». Первый
dry-run миграции по реальному архиву показал `memory/sessions/*.md` — хендоффы `save-session`,
39 файлов. Реестр живых сессий живёт только в корне конфига, поэтому правило сужено до
`TopLevel("sessions")`, а ключи `.key` запрещены везде как и раньше. Кейс переписан по факту и
добавлен `observed`-кейс с реальным путём. Правило для будущих правок: `computed`-ожидание —
гипотеза, `observed` — факт, и второй бьёт первое.
