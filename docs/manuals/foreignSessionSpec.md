# Спека сессии чужого агента

> Скопируйте этот файл целиком своей LLM и попросите собрать обёртку, которая отдаёт сессии вашего
> агента в VibeMemory: здесь описан весь формат и команда, читать исходники не нужно.

Claude Code отдаёт свои сессии в стор сам, хуками.
Любой другой агент отдаёт сессию готовым файлом командой `vibememory session put`.
После неё сессия лежит в сторе так же, как сессия Claude Code после хука `Stop`:
- закоммичена;
- уезжает на другие машины;
- находится инструментом `history_search` сервера памяти.

Свой формат лога агент приводит к формату ниже сам.
Движок чужих форматов не читает: формат принадлежит агенту и меняется вместе с ним.
Исключение — агенты с пресетом: их лог движок читает сам, обёртка не нужна (раздел «Пресеты»).

## Команда

```bash
vibememory session put --agent <имя> --id <сессия> --cwd <каталог> --from <файл.jsonl> [--end]
```

| Флаг | Что это |
|---|---|
| `--agent` | имя агента, то же, что в `--agent` сервера памяти этого агента |
| `--id` | идентификатор сессии, он же имя файла в сторе |
| `--cwd` | рабочий каталог сессии: по нему выбираются стор и проект, как у Claude Code |
| `--from` | файл сессии целиком, в формате ниже |
| `--end` | сессия закончилась: машина перестаёт считать её живой |

**Имя агента и идентификатор сессии** — строчные латинские буквы, цифры и дефис.
Дефис не может стоять первым или последним, длина — не больше 63.
`dsh-desktop` и `session-2edc4cef-d6c8-4144-95f0-31baddbec318` годятся.
`DSH`, `dsh_desktop` и `../x` — нет.

**Когда звать:** после каждого хода агента и в конце сессии с `--end`.
Каждый раз передаётся файл сессии **целиком**, а не приращение.
Неизменившийся файл второго коммита не делает, поэтому звать часто — дёшево.
Без `--end` сессия перестаёт считаться живой сама, через час после последнего вызова.

**Звать некому** — у агента нет своих хуков или событий хода: зарегистрируйте агента, и обёртку будет звать тик движка.
Свой планировщик для этого не нужен — раздел «Агент без своих хуков» ниже.

**Ответ при успехе** — одна строка в stdout и код выхода 0:
```
put: 3 record(s), 2 searchable, into project Promed of the personal store (projects/Promed/agents/dsh-desktop/session-….jsonl) — committed
```

**Отказ** — строка в stderr и код выхода 1, в сторе ничего не меняется.
Причины отказа:
- имя не подходит под правило выше;
- файл нарушает формат — отказ называет номер строки и правило;
- каталог исключён правилом `ignoreCwd` владельца;
- каталог принадлежит команде, которая на этой машине не подключена.

Код 2 — неверный вызов: не хватает флага.

## Агент без своих хуков: обёртку зовёт тик

```bash
vibememory session agent add --agent <имя> --dir <каталог логов> --run <обёртка> [--backfill]
vibememory session agent remove --agent <имя>
```

После регистрации тик движка — он и так идёт раз в две минуты на каждой системе — смотрит каталог логов агента.
Каждый лог, записанный с прошлого раза, тик отдаёт обёртке.

**Регистрация и есть переключатель.** До неё движок об этом агенте не знает: логи лежат на машине, в стор не уезжает
ничего. Узнать о каталоге движку неоткуда — его называет человек, поэтому у агента с обёрткой нет и строки-подсказки,
какая есть у пресета. `remove` возвращает агента в то же состояние, а прошлое после повторной регистрации догоняет
только `--backfill`.

**У вопроса есть и второй ответ.** `vibememory session agent decline --agent dsh-desktop` пишет решение «сессии этого
агента остаются на этой машине»: `doctor` перестаёт предлагать регистрацию и печатает `unwatched` с датой решения, а
`add` решение отменяет. `remove` пишет то же самое — иначе движок спорил бы с человеком после каждого `remove`.
`vibememory session agent list [--json]` показывает всё одним ответом: кто зарегистрирован, кто ждёт решения, кому
отказано и сколько сессий от кого дошло.

Договор с обёрткой:
- вызов — `<обёртка> <путь лога>`: один изменившийся лог на запуск, путь абсолютный;
- в окружении `VIBEMEMORY_BIN` — путь к `vibememory`, `VIBEMEMORY_AGENT` — имя агента: под планировщиком `PATH` не тот, что в терминале;
- обёртка сама читает лог, приводит его к формату ниже и зовёт `"$VIBEMEMORY_BIN" session put …`;
- код 0 — лог отдан; любой другой — сбой: тик запишет код и последние пять строк вывода и попробует тот же лог в следующий раз;
- на один запуск — 60 секунд, потом обёртку останавливают;
- за один проход тика — не больше 20 логов агента, остальные ждут следующего.

Что ещё нужно знать:
- **Логи, которые были в каталоге до регистрации**, тик не трогает: это история.
  С `--backfill` тик отдаёт и их, не больше 20 за проход.
- **`--end` такому агенту звать не нужно**: сессия перестаёт считаться живой сама, через час после последнего `put`.
- **Каталог** — именно каталог логов сессий.
  Любой файл, изменившийся внутри, считается логом, и обёртка, которая его пропустит, будет выглядеть молчащей.
- **На Windows** обёртка — `.exe` или `.cmd`: скрипт PowerShell напрямую не запускается, его зовут из `.cmd`.
- Регистрация хранится на этой машине (`~/.vibememory/agents.json`): каталог и обёртка у каждой машины свои.

## Пресеты: лог читает движок

Для DeepSeek Harness обёртка не нужна:

```bash
vibememory session agent add --agent dsh-desktop --preset dsh [--dir <каталог логов>] [--backfill]
```

- **Каталог** по умолчанию — `~/.dsh/sessions`.
- **`--backfill`** — отдать и сессии, которые уже лежат в каталоге, не больше 20 за проход тика.
  Без него, как и у обёртки, тик берёт только логи, записанные после регистрации.
- **`--run` и `--preset` вместе не бывают.**
- **Логом считается только** `session.v<цифры>.jsonl.zstd`; `session.lock` и прочее рядом не трогается.
- **Формат лога, который знает движок**, — `v4`.
  Лог другой версии останавливает агента с отказом «формат DSH vN неизвестен этому движку: vibememory update», и `doctor` краснеет.
- **Сбой одного лога не останавливает остальные.**
  Если сессию нельзя положить — например, папки её проекта больше нет, — лог откладывается до своей следующей записи.
  Тик и `doctor` называют его и причину строкой «not delivered»; это не поломка связки, `doctor` не краснеет.
- Только что начатая сессия, где кроме заголовка ничего нет, — не сбой: её возьмёт следующий проход.
- **Пока регистрации нет, `doctor` и `status` печатают блок `waiting`** — команду регистрации и, если логи уже
  лежат в каталоге, их число:
  ```
  waiting  DeepSeek Harness: 22 session(s) in /Users/me/.dsh/sessions are not in history — nobody watched this agent: vibememory session agent add --agent dsh-desktop --preset dsh --backfill
  waiting  DeepSeek Harness keeps sessions in /Users/me/.dsh/sessions and they do not go to history — nobody watched this agent: vibememory session agent add --agent dsh-desktop --preset dsh --backfill
  ```
  Это не ошибка: выгрузка сессий — решение человека, и `doctor` на `waiting` не падает.
  В `--json` то же состояние лежит полем `waiting`, а `install` и `update` печатают ту же строку слово в слово —
  там, где человек читает вывод.

Перевод записей — тот же, что в разделе «Перевод из лога DeepSeek Harness» ниже: сессия, отданная движком, и сессия, отданная прежней обёрткой, совпадают запись в запись.

## Файл

JSONL в UTF-8: одна запись — одна строка, каждая строка кончается переводом строки.
Отказ получает файл, у которого:
- последняя строка без перевода строки — файл оборван посреди записи;
- есть пустая строка между записями.

`\r\n` допустим.

Каждая строка — JSON-объект с тремя обязательными полями:

| Поле | Тип | Зачем |
|---|---|---|
| `type` | непустая строка | вид записи; в поиск идут только `user` и `assistant` |
| `uuid` | непустая строка, уникальная в файле | слияние между машинами опознаёт запись по нему; без него исправленная строка оказалась бы на другой машине рядом со старой |
| `timestamp` | строка UTC вида `2026-09-30T12:00:00Z`, дробная часть секунд допустима | слияние расставляет по нему строки двух машин |

У записей `user` и `assistant` есть четвёртое обязательное поле — `message.content`:
- либо строка;
- либо массив блоков, из которых поиск читает `text` блоков с `"type": "text"`.

Блоки других типов допустимы, поиск их пропускает, даже если в них есть поле `text`: вызовы инструментов, размышления (`thinking` у Claude Code, `reasoning` у DSH).

Все остальные поля и записи других типов хранятся как есть, но не ищутся.
Среди них вызовы инструментов, их результаты, служебные события.

Время только в UTC с `Z`.
Смещение вида `+03:00` сравнивалось бы как текст, а не как время.
Число миллисекунд — не строка.

## Пример

```json
{"type":"user","uuid":"6f1d0c1e-0000-4000-8000-000000000001","timestamp":"2026-09-30T08:00:01Z","message":{"role":"user","content":"почини экспорт отчёта"}}
{"type":"tool/call","uuid":"6f1d0c1e-0000-4000-8000-000000000002","timestamp":"2026-09-30T08:00:02Z","data":{"name":"bash","arguments":"{}"}}
{"type":"assistant","uuid":"6f1d0c1e-0000-4000-8000-000000000003","timestamp":"2026-09-30T08:00:03.125Z","message":{"role":"assistant","content":[{"type":"text","text":"Экспорт починен"}]}}
```

## Перевод из лога DeepSeek Harness

Лог сессии DSH лежит здесь:
`~/.dsh/sessions/<кодированный-cwd>/session-<uuid>/session.v4.jsonl.zstd`

Это последовательность zstd-кадров, внутри каждого — строки JSON.
Первая строка — заголовок `{"type":"session","id":"session-<uuid>","cwd":…}`, у остальных есть `type`, `seq`, `time` (мс эпохи) и `data`.

| Поле нашей записи | Откуда в DSH |
|---|---|
| `type` | `user/message` → `user`, `assistant/message` → `assistant`, остальное — как есть |
| `uuid` | `data.message.id` у `assistant/message`, `data.id` у `user/message`; у записей без id — `<id сессии>-<seq>` |
| `timestamp` | `time` (мс эпохи) → UTC со `Z` |
| `message.content` | `data.message.content` у `assistant/message`, `data.content` у `user/message` |

`--id` — это `id` из заголовка, `--cwd` — его `cwd`.

Писать этот перевод самому не нужно: `--preset dsh` делает его в движке.
Таблица остаётся для тех, кто разбирает, как сессия DSH выглядит в сторе.

## Где сессия лежит и как её видно

В сторе: `projects/<проект>/agents/<агент>/<сессия>.jsonl`.
Среди сессий Claude Code её нет, и в этом смысл: Claude Code считает своими все `*.jsonl` верхнего уровня проекта, и чужая запись попала бы в его `/resume`.

`history_search` отдаёт у каждого результата поле `agent`: имя агента или `claude-code`.
Параметр `agent` сужает поиск до сессий одного агента: `{"query": "…", "agent": "dsh-desktop"}`.

`vibememory status` показывает строку на агента:
```
agent    dsh-desktop — 12 session(s) in the personal store, newest written 2026-09-30T09:00:00Z
```
Дата, которая перестала двигаться, — обёртка, которая перестала отдавать сессии.

У зарегистрированного агента `vibememory doctor` пишет строку `watch` и сам говорит, что не так:
```
watch    dsh-desktop — logs in …/.dsh/sessions, wrapper …/dsh-put.sh; last put 2026-09-30T09:00:00Z
         the wrapper failed at 2026-09-30T09:02:00Z on …/session.v4.jsonl.zstd — exit code 1
           zstd: frame is cut
         silent: logs written at 2026-09-30T09:30:00Z and no session put since; the wrapper runs but does not deliver
```
- **the wrapper failed** — последний запуск обёртки упал: код и последние строки её вывода;
- **silent** — логи в каталоге обогнали последний `put` больше чем на 15 минут: обёртка запускается, но сессии не доходят;
- **the log directory is not there** — каталог логов пропал.

Каждая из трёх строк — ошибка `doctor`: он выходит с кодом 1.

## Имя агента у сервера памяти

Сервер памяти запускается с `--agent <имя>` по тому же правилу, что выше.
Имя не по правилу — сервер не стартует и пишет почему.
Имя должно совпадать с тем, под которое выдан токен агента.
`vibememory doctor` у каждого токена пишет, запускался ли на этой машине сервер памяти под его именем:
```
token    personal/deepseek tk_… from https://app.vibememory.ru
         client: no memory server has started as --agent deepseek on this machine; …
```
Такая строка значит одно из двух:
- клиент ещё не настроен;
- клиент зовёт сервер под другим именем.

Третье состояние — **клиент подключён, а сессий от него нет**: под строкой `client …` стоит ещё одна.
```
token    personal/vibeide tk_… from https://app.vibememory.ru
         client: a memory server started as --agent vibeide at 2026-10-03T06:49:18Z (version 0.7.0)
         sessions: none in any store — only memory comes from this client; the engine reads the logs of a watched agent or a known preset
```
Сервер памяти под этим именем запускался, память он пишет, а сессий от него в сторе нет ни одной.
Для клиента, чьи логи движок читать не умеет (Cursor, Codex, Gemini, VibeIDE, VibeIDEA), это норма: он приносит
только память. Для того, чьи логи движок читает по пресету, — нет: там об этом говорит блок `waiting`
в разделе «Пресеты», и лечится он регистрацией.

Регистрацию клиента агент подхватывает при своём перезапуске.

Когда сервер запускался, `doctor` пишет и его версию.
Сервер, запущенный до `vibememory update`, работает старым бинарём, пока клиент не перезапустит его:
```
         client: a memory server started as --agent dsh-desktop at 2026-09-30T07:00:00Z (version 0.4.2) — older than vibememory 0.5.0 on this disk: restart the client so it starts the new server
```
Старый сервер отвечает так, будто нового в выпуске нет: например, не видит сессий других агентов.

## Подключить нового агента: чеклист

1. **Найдите лог.** Где агент пишет сессию, как в имени файла или пути найти её id и рабочий каталог.
2. **Напишите обёртку** по формату ниже: лог → JSONL → `"$VIBEMEMORY_BIN" session put --agent … --id … --cwd … --from …`.
   Проверьте её руками на одном логе: ответ `put: … committed`.
3. **Подключите сервер памяти** агенту: `vibememory mcp-config <клиент>` печатает, что вставить.
   Имя в `--agent` у сервера и у `session put` — одно.
4. **Зарегистрируйте агента**, если звать обёртку ему нечем: `vibememory session agent add …`.
   Это и есть переключатель: без регистрации сессии агента не уезжают в историю вовсе, а `--backfill` догоняет
   прошлое. У агента, которого движок знает по пресету (DSH), `doctor` и `status` печатают `waiting`, пока
   регистрации нет; у агента с обёрткой движок о каталоге логов просто не знает. Не выгружать — тоже ответ:
   `session agent decline --agent <имя>`, и `doctor` перестанет предлагать. Сессия Claude узнаёт о ждущем агенте
   сама, на своём старте (раз в сутки и когда логов стало больше), — чтобы человеку не нужно было читать `doctor`.
5. **Проверьте:** поговорите с агентом, через две-три минуты `vibememory doctor` — строка `watch` без `failed` и `silent`, у `agent` свежая дата.
6. **Найдите сказанное:** `history_search` с параметром `agent` находит слова из этой сессии.

Ловушки, на которые уже наступили:
- **Токен в логе.** Агент, которому показали токен, сохраняет его в логе.
  Такой файл `session put` целиком оставляет на машине и пишет «held on this machine»: отзовите токен в кабинете, следующий `put` без токена уйдёт.
- **Размышления агента.** У DSH они лежат блоком `reasoning` с полем `text`.
  Поиск читает только блоки `"type": "text"`, поэтому размышления в найденное не попадают — так и задумано.
- **Конца сессии нет.** У агента без событий конца сессии `--end` звать не по чему, и не нужно: живость гаснет сама через час.
- **Старый сервер памяти.** После `vibememory update` клиента нужно перезапустить, иначе работает прежняя версия — `doctor` об этом скажет.

## Добавить кейс проверки формата

Кейсы лежат в `fixtures/foreign/foreignSessions.json`, тест — `crates/vibememory-core/tests/foreign_fixtures.rs`.
Кейс — `{id, provenance: "computed", note, text, expect}`:
- `text` — файл байт в байт;
- `expect` — либо `{"lines": N, "spoken": M}`, либо `{"refused": {"line": N, "problem": "<код>"}}`.

Коды:
- `empty`, `noFinalNewline`, `notText` — про файл целиком, `line` 0;
- `blankLine`, `notAnObject`, `timestamp`, `duplicateUuid`, `content`;
- `missing:<поле>`.

Правила наблюдения за агентом — в `fixtures/foreign/agentWatch.json`, тест — `crates/vibememory-core/tests/agent_watch_fixtures.rs`:
- `changed` — `{id, note, seen, found, expect}`: имена логов и их время на прошлом и на этом проходе, `expect` — новые логи по порядку;
- `silent` — `{id, note, newestLog, lastPut, registered, expect}`: время в секундах эпохи, `lastPut` может быть `null`, `expect` — молчит ли агент.
