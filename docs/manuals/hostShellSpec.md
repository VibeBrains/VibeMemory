# Спека входа ключом машины: принудительная команда и `pre-receive`

> Скопируйте этот файл целиком своей LLM, если пишете клиент хоста VibeMemory: что может ssh-ключ
> машины участника на хосте, как выглядит отказ и что означает каждый его код. Права ключа приходят
> из снимка — [accessSnapshotSpec.md](accessSnapshotSpec.md), ответ `status` —
> [hostStatusSpec.md](hostStatusSpec.md).

## Назначение

Машина участника ходит на хост по ssh своим ключом из снимка прав (`keys[]`). Оболочки у неё нет:
ключ открывает ровно четыре команды, и каждая проверяется по снимку на момент входа. Снимок
перечитывается при каждом входе — отзыв ключа действует со следующего соединения. Открытая сессия
`mcp` перечитывает его ещё и перед каждым запросом: отзыв ключа, бан, выход из команды или
закрытие проекта обрывают её на следующем же запросе (раздел «Сессия `mcp`»).

Вход — учётка `vmgit`. Строку каждого ключа в `~vmgit/.ssh/authorized_keys` пишет только применятель
прав на хосте (`vibememory-mcp access-apply`), руками её не правят:

```
restrict,command="/srv/vibememory/bin/vibememory-mcp shell mk_3f8k1p0z" ssh-ed25519 AAAAC3Nza… mk_3f8k1p0z
```

`restrict` снимает терминал, проброс портов, агента и X11; `command` подменяет всё, что просит
клиент, запуском `shell` с id ключа. Что клиент просил на самом деле, `shell` читает из
`SSH_ORIGINAL_COMMAND`.

## Четыре команды

| Команда, как её шлёт клиент | Что делает | Кому можно |
|---|---|---|
| `git-upload-pack 'teams/<слаг>.git'` | clone и fetch стора команды | члену команды из `teams` ключа; у `memory`-команды — только `owner` и `admin`: у её участников клона нет, и выгрузка — это экспорт |
| `git-receive-pack 'teams/<слаг>.git'` | push | члену `sync`-команды из `teams` ключа; пути, запись и место проверяет `pre-receive` |
| `mcp --team <слаг> --agent <агент>` | сервер памяти команды по stdio | члену команды из `teams` ключа; версии подписаны `storeName` ключа, `member` — из ключа, агент — со слов клиента; запись — пока у команды `writable: true`, поиск по прошлым сессиям — только `owner` и `admin` |
| `status` | JSON о командах ключа: [hostStatusSpec.md](hostStatusSpec.md) | любому ключу из снимка |

Путь стора — `teams/<слаг>.git` или `/srv/vibememory/teams/<слаг>.git`, в одинарных кавычках (так
его шлёт git) или без них. Ничего другого: ни `..`, ни `;`, ни пробела внутри пути, ни личного стора
владельца — тот ходит собственным ключом владельца, не ключом машины. Имя агента — по правилу имён
снимка: строчные латинские буквы, цифры и дефис, до 63 знаков.

## Отказ `shell`

Снимок здесь и в `pre-receive` — тот, что в силе: `access.json`, если он не старше снимка, применённого
последним ([accessSnapshotSpec.md](accessSnapshotSpec.md)).

Код выхода 1, в stderr первой строкой `vibememory: <код>`, второй — что именно не так; хост пишет
строку в свой журнал. git показывает stderr как есть, поэтому код читается и из вывода `git fetch`.

Проверки идут в порядке таблицы, называется первая сработавшая.

| Код | Когда |
|---|---|
| `snapshotUnusable` | Снимок прав не читается или не проходит проверку — хост закрыт для всех |
| `unknownKey` | Ключа нет в снимке — он отозван, — или его владелец забанен (`bans` снимка) |
| `commandDenied` | Команда не из четырёх или её аргументы не проходят правила выше |
| `teamGone` | Команды с таким слагом нет в снимке или она удалена |
| `unknownTeam` | Команда есть, но её нет среди `teams` ключа — в том числе личный стор владельца |
| `exportDenied` | `git-upload-pack` `memory`-команды не владельцем и не админом |
| `pushDenied` | `git-receive-pack` в `memory`-команду: её стор пишет только сервер памяти |

## Сессия `mcp`

Права берутся из снимка в силе перед каждым запросом, а не один раз при входе: соединение живёт часами,
а права за это время меняются. Пока ключ в снимке, его владелец не забанен и команда среди `teams`
ключа, запрос обслуживается с правами на этот момент — роль, проекты, запись, поиск по прошлым
сессиям. Иначе ответ на запрос — ошибка JSON-RPC с кодом `-32001` и текстом, что изменилось: ключа
больше нет в снимке (отозван или владелец забанен), ключ больше не открывает команду (вышел из неё,
команда удалена) или снимок не читается. После этого ответа сессия закрывается. Клиенту остаётся
соединиться заново — и получить отказ уже на входе, кодом из таблицы выше.

## Сбои хоста

Эти отказы — не правило снимка, а состояние самого хоста: запрос верный, ответить хост не смог.
Формат тот же — код первой строкой stderr, код выхода 1.

| Код | Когда |
|---|---|
| `statusUnavailable` | Отчёт хоста `host.json` ещё не собран или не читается: `status` ответить нечем. Хост собирает отчёт раз в час и после каждого применения снимка |
| `hostFailure` | Хост не смог сделать то, что правила разрешили: не запустился git, не прочитались строки push |

## `pre-receive`: что проверяется при push

Хук стоит в каждом репозитории команды (в личном сторе владельца его нет). `shell` передаёт ему id
ключа переменной `VIBEMEMORY_KEY`. Хук читает все строки `старое новое ссылка`, и если хоть одна не
проходит, push отвергается **целиком**. Первая строка отказа — `vibememory: <код>`. Если код про пути,
следующие строки — пути по алфавиту, по одному в строке; иначе — одна строка о том, что именно не так.
git показывает их с приставкой `remote: `. Изменённые пути — это разница деревьев `main` до и после
push (`git diff-tree`), а не всё дерево: не тронутый push'ем файл не мешает.

Проверки идут в порядке таблицы, называется первая сработавшая.

| Код | Когда |
|---|---|
| `snapshotUnusable` | Снимок прав сломался, пока шло соединение: не принимается ничего |
| `unknownKey` | Push не через ключ снимка: переменной нет, ключ отозван или его владелец забанен |
| `teamGone` | Команды нет в снимке или она удалена |
| `notAMember` | Команда не среди `teams` ключа |
| `pushDenied` | Команда в режиме `memory` |
| `readOnly` | У команды `writable: false` — грант истёк |
| `refDenied` | Любая ссылка кроме `refs/heads/main` — ветка, тег, заметка — или удаление `main` |
| `configDenied` | Изменён путь под `config/`: общий `settings.json` с хуками стал бы исполнением команд на машинах участников |
| `pathDenied` | Изменён путь вне `projects/` и `machines/<storeName ключа>/` — в том числе `.gitattributes`, чужая машина (и машина, чьё имя лишь начинается с `storeName` ключа), `history.jsonl` |
| `tokenInPush` | Изменённый файл несёт токен агента `vmt_…`: движок держит такие файлы на машине сам, а это push без него или руками. Пути — следующими строками |
| `diskReserve` | После push на хосте осталось бы меньше резерва свободного места (по умолчанию 2 ГиБ) |
| `quota` | Размер стора вместе с входящим пакетом больше `quotaBytes` команды |

## Что клиент делает с кодами

Тик участника по коду переводит стор в паузу с названной причиной — в `tick-state.json` **этого
стора**, остальные сторы машины работают дальше:

- `readOnly` — fetch идёт, push не пробуется; выход из паузы, когда `status` снова скажет
  `writable: true`
- `notAMember`, `teamGone`, `unknownKey` — стор не трогается вовсе; `doctor` называет причину и адрес
  кабинета
- `pathDenied`, `configDenied` — fetch идёт, push не пробуется; `doctor` называет пути и
  `vibememory store reclone <store-id>`: движок историю не переписывает, а отвергнутый коммит остался бы
  в ней навсегда
- `refDenied` — дефект клиента: тик пушит только `main`
- `quota`, `diskReserve`, `snapshotUnusable`, `statusUnavailable`, `hostFailure` — обычный провал цикла
  с сообщением хоста

Отказ без строки `vibememory: <код>` — сетевой или иной сбой, как раньше.
