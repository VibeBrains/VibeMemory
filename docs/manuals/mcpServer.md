# Как подключить память VibeMemory к любому агенту

> Мануал «как сделать». Что именно умеет сервер и почему устроен так — в
> [functional.md](../functional.md) и [knowledge/design](../knowledge/README.md).

Сервер `vibememory-mcp` отдаёт по MCP ту же память, которую ведёт движок: он читает журнал
записей в сторе и дописывает в него события. Своей модели у него нет, поэтому память остаётся
одна на всех агентов и на все машины.

## Что нужно заранее

Установленный движок (`vibememory doctor` — все шаги ok). Сервер берёт стор из
`~/.vibememory/config.json`, как и всё остальное; переменная `VIBEMEMORY_DIR` переопределяет
каталог движка, если он лежит не там.

## Сборка и установка

```bash
cargo build --release
vibememory install
```

`install` кладёт сервер рядом с движком, подписывает его тем же сертификатом и проверяет, что
установленное **запускается**.

**Не копируйте бинарь руками.** Перезапись файла, который уже запускали, делает его
недействительным для ядра: macOS убивает каждый следующий запуск сигналом SIGKILL без единого
сообщения, а `codesign --verify` при этом продолжает называть файл валидным. Замер и способ
повторить — [knowledge/design/binaryReplacement.md](../knowledge/design/binaryReplacement.md).

## Подключить агента: зачем и на каждой ли машине

Без подключения сессии и файлы памяти всё равно ездят между машинами: их переносят хуки и тик.
Подключение даёт агенту инструменты: искать в памяти и в истории сессий, записывать и править записи.

Подключать нужно **на каждой машине и в каждом клиенте**.
Регистрация сервера живёт в файле настроек самого клиента, а это машинный файл: он между машинами не ездит.
Движок в чужие файлы настроек не пишет — у каждого клиента свой формат, и он меняется с версиями.
Поэтому движок печатает готовый фрагмент, а вставляет его человек.

```bash
vibememory mcp-config            # список клиентов и имён агентов
vibememory mcp-config codex      # фрагмент для Codex на этой машине
```

Фрагмент собран под эту машину:
- путь к серверу под эту систему (`vibememory-mcp.exe` на Windows);
- имя агента, которым клиент подписывает записи; токен для команды берётся под тем же именем;
- файл клиента и его формат: TOML у Codex, JSON у Cursor и Claude Desktop, YAML у DSH, команда у Claude Code и Gemini CLI;
- `VIBEMEMORY_DIR`, если движок лежит не в `~/.vibememory`.

| Клиент | `mcp-config` | Агент | Куда | После |
|---|---|---|---|---|
| Claude Code | `claude-code` | `claude-code` | `claude mcp add -s user …` | новая сессия |
| Claude Desktop | `claude-desktop` | `claude-desktop` | `claude_desktop_config.json` | полностью закрыть и открыть |
| Codex (CLI, расширение IDE, приложение ChatGPT) | `codex` | `codex` | `~/.codex/config.toml` или `codex mcp add` | новая сессия, в приложении — Restart |
| ChatGPT | `chatgpt` | `codex` | приложение на компьютере — та же запись Codex | — |
| Gemini CLI | `gemini` | `gemini` | `gemini mcp add -s user …` | `/mcp reload` |
| Cursor | `cursor` | `cursor` | `~/.cursor/mcp.json` | перезапуск |
| DeepSeek Harness | `dsh` | `dsh-desktop` | `~/.dsh/profiles/<профиль>/cordis.patch.yml` | перезапуск DSH |
| VibeIDE | `vibeide` | `vibeide` | подключает сам | перезагрузить окно после установки |
| VibeIDEA | `vibeidea` | `vibeidea` | подключает сама | ничего |

**ChatGPT в браузере** этот сервер использовать не может.
Локальных серверов он не запускает, а удалённый принимает только с OAuth, тогда как сервер памяти ждёт токен.

**Проверить**, какие клиенты подключены: `vibememory doctor`.
Сервер памяти при старте отмечает имя агента, и `doctor` перечисляет каждое имя со временем последнего запуска.
У каждого токена он пишет, запускался ли сервер под именем этого токена.
Строка «no memory server has started as --agent X» после перезапуска клиента значит одно из двух: клиент не подключён или зовёт сервер под другим именем.

`connect` в конце печатает строку для Claude Code, если сервер там не зарегистрирован, и напоминает про `mcp-config`.

## Claude Code

```bash
claude mcp add -s user vibememory ~/.vibememory/bin/vibememory-mcp -- --agent claude-code
```

**`-s user` обязателен.** Без него Claude Code регистрирует сервер только для каталога, в котором
запущена команда, и в остальных проектах памяти нет — в том числе у агента, которого запускает IDE.

Проверить: `claude mcp list` покажет `vibememory`, а в сессии станут доступны инструменты
`memory_search`, `memory_get`, `memory_save`, `memory_update`, `memory_delete`.

## VibeIDE и VibeIDEA

Оба подключают сервер сами, как только он установлен; регистрировать ничего не нужно.

- **VibeIDE** добавляет `vibememory` с `--agent vibeide` и запускает его в домашнем каталоге: там нет проекта, и запись без `project` отказывает, а не уходит не туда.
  Проект каждой открытой папки IDE спрашивает у сервера сама (`project_resolve`).
  Своя запись `vibememory` в `~/.vibeide/mcp.json` заменяет найденную; выключить можно в панели MCP.
  Сервер, поставленный после запуска IDE, подхватывается после перезагрузки окна.
- **VibeIDEA** отдаёт сервер ACP-агентам в каждой сессии и прямому чату, с `--agent vibeidea`, без перезапуска.
  Добавлять `vibememory` в `.vibe/mcp.json` проекта не нужно: агент получит его дважды.
  Для ACP-агентов выключается ключом `use_custom_mcp: false` в `~/.jetbrains/acp.json`.

## Проект по рабочему каталогу

Сервер смотрит, в каком каталоге его запустили, и называет проект стора по тем же правилам, что
хук `SessionStart`. Проект объявляется агенту в ответе на `initialize` (поле `instructions`).
`memory_save`, `memory_update` и `memory_delete` без `project` пишут в него.

Только проект, который в сторе **уже есть**. Каталог, для которого проекта нет (`/tmp`, домашний),
проекта не даёт — тогда запись требует `project` явно. Иначе клиент, запускающий серверы где
попало, плодил бы мусорные проекты.

## Один сервер на несколько проектов

Если клиент держит один процесс сервера на все окна (так делает VibeIDE), рабочий каталог
проекта не называет. Запускайте сервер из каталога вне проектов стора (домашний подходит) —
тогда запись без `project` отказывает, а не уходит в чужой проект.

Имя проекта агент берёт вызовом `project_resolve` с путём открытой папки и передаёт его в
`project`. **Угадывать имя по названию папки нельзя**: репозиторий называется по корню git,
а владелец может переименовать папку правилом или исключить её.

## Память с хоста — для машины без своего стора

На хосте стора нет рабочей копии, только голый репозиторий. Сервер читает память прямо из
`main` и пишет событие коммитом поверх `main`; машины получают его обычным fetch.

### Поставить на хост

Бинарь нужен под x86_64 Linux. На Mac с Apple Silicon — кросс-сборкой в родном arm64-контейнере
(эмуляции amd64 в Docker может не быть):

```bash
docker run --rm --platform linux/arm64 -v "$PWD":/src -v "$PWD/target/linux":/build \
  -e CARGO_TARGET_DIR=/build -e CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_LINKER=x86_64-linux-gnu-gcc \
  -w /src rust:1.97-bookworm sh -c 'apt-get update -qq && apt-get install -y -qq gcc-x86-64-linux-gnu libc6-dev-amd64-cross \
  && rustup target add x86_64-unknown-linux-gnu && cargo build --release -p vibememory-mcp --target x86_64-unknown-linux-gnu'
./infra/hostMcp.sh --binary target/linux/x86_64-unknown-linux-gnu/release/vibememory-mcp
```

Хост должен быть подготовлен `infra/hostBootstrap.sh` (пользователи `vmgit` и `vmcab`,
`/srv/vibememory`). Скрипт кладёт бинарь в `/srv/vibememory/bin/` (владелец root — сервер не может
его подменить), а `~/vibememory/bin/vibememory-mcp` делает ссылкой на него: команда владельца по ssh
не меняется. Сервис на `127.0.0.1:8787` работает под `vmgit`, права берёт из снимка
`/srv/vibememory/access/access.json` ([accessSnapshotSpec.md](accessSnapshotSpec.md)) и пишет
только в стор и в `/srv/vibememory/teams/`; перед ним Caddy с сертификатом для `vibememory.ru`,
снаружи отдаётся только `/mcp`.

Первый запуск на хосте, где снимка ещё нет, — с `--owner <handle владельца>`: из файла токена
прежнего сервера `~/vibememory/mcp-token` скрипт собирает снимок (личный стор, владелец —
единственный член, строка `tk_legacy` с отпечатком токена), проверяет его `access check`, а файл
удаляет только после того, как новый сервер принял тот же токен. Клиенты работают без перерыва тем
же значением; на хосте от него остаётся только отпечаток.

Проверить снимок руками — тем же бинарём: `vibememory-mcp access check <файл>`, первая строка
`ok` или код правила. Снимок перечитывается при каждой смене файла (время, размер, inode), без
рестарта; пропавший или сломанный снимок закрывает дверь всем (`503`) с громкой строкой в журнале.

Каталог сборки — внутри репозитория, а не в `/tmp`: Docker на Mac монтирует `/tmp` своей
виртуальной машины, сборка проходит, а бинаря на диске Mac нет.

С сервером скрипт ставит и команды хоста под `vmgit`: применение снимка прав при каждой его
смене, отчёт хоста раз в час и ночную упаковку сторов команд — [hostSetup.md](hostSetup.md),
раздел 7.

Если на хосте стоит fail2ban, скрипт ставит джейл `vibememory-mcp`:
десять отказов по токену за десять минут — бан адреса на портах 80 и 443.
Адрес берётся из строки журнала сервера, куда он попадает из `X-Forwarded-For`, записанного
Caddy. ssh этот бан не закрывает: неверный токен ничего не говорит о входе по ключу.
Разблокировать себя, если после смены токена клиент успел набрать десять отказов:

```bash
ssh vibememory 'sudo fail2ban-client set vibememory-mcp unbanip <адрес>'
```

### По ssh — без открытых портов

Любой клиент, умеющий stdio-серверы, на машине с ключом к хосту:

```json
{
  "mcpServers": {
    "vibememory": {
      "command": "ssh",
      "args": ["-o", "BatchMode=yes", "vibememory",
               "vibememory/bin/vibememory-mcp", "--git-store", "vibememory/store.git",
               "--machine", "host", "--agent", "<кто вы>"]
    }
  }
}
```

### По HTTPS — когда ssh нет

```
POST https://vibememory.ru/mcp
Authorization: Bearer <токен>
Content-Type: application/json
```

Одно JSON-RPC сообщение на запрос, ответ — JSON; уведомление получает `202` без тела. `GET` и
`DELETE` — `405`: потоков и сессий нет. Запрос с заголовком `Origin` (страница из браузера) —
`403`. Неизвестный, отозванный и просроченный токен получают один и тот же `401`.

**Кто пишет — говорит только токен.** Токен из снимка прав называет команду, участника и агента;
по ним подписана каждая запись (`agent`, `member`, префикс версии `host-tk_<id>`). Заголовка
`VibeMemory-Agent` больше нет: имя, которое клиент выбирает сам, по HTTPS ничем не подкреплено.
Токены выдаёт кабинет; до него действует прежний токен владельца `tk_legacy` — он уже стоит в его
клиентах, а на хосте от него остался только отпечаток.

**Claude Code регистрируется с `headersHelper`**: заголовок `Authorization` при каждом соединении
печатает движок из файла токена, и токена нет нигде, кроме этого файла, — ни в конфигурации Claude
Code, ни в аргументах процесса, ни в истории оболочки. Строку регистрации печатает
`vibememory connect` ([functional.md](../functional.md)):

```bash
claude mcp add-json --scope user vibememory-acme '{"headersHelper":"'\''/Users/me/.vibememory/bin/vibememory'\'' mcp-headers acme claude-code","type":"http","url":"https://vibememory.ru/mcp"}'
```

`vibememory mcp-headers <команда> <агент>` читает `~/.vibememory/tokens/<команда>/<агент>` и
печатает `{"Authorization":"Bearer …"}` в stdout — и больше ничего и никуда.

Клиент, который подключается к памяти команды сам, берёт адрес из поля `mcpUrl` сайдкара
`~/.vibememory/tokens/<команда>/<агент>.json`. Все поля сайдкара описаны в
[teamSetup.md](teamSetup.md#сайдкар--контракт-для-клиентов).

Прежний токен владельца, выданный до кабинета, кладётся туда же — в
`~/.vibememory/tokens/personal/claude-code`, с правами только владельца (`chmod 600`), — и
регистрируется той же строкой с `mcp-headers personal claude-code`. Движок узнаёт токены по форме
`vmt_…`, а у прежнего формы нет: узнать его в транскрипте движок может только по значению из этого
файла и тогда держит такой файл на машине ([knowledge/design/heldSessions.md](../knowledge/design/heldSessions.md)).

**Токен не показывайте в сессии агента**: транскрипт уезжает в стор, а с ним в зеркало. Движок
держит на машине файл, в котором нашёл токен, но токен, однажды показанный агенту, уже стоит
отозвать. И регистрируйте сервер в `~/.claude.json` (`--scope user`), а не в `settings.json`: копия
`settings.json` синхронизируется, и движок откажется её везти, найдя в ней токен, — `doctor`
назовёт файл.

**Права — из токена:** `reader` только читает; `history_search` доступен токену с `history`;
токен со списком проектов видит и пишет только их; удалённая команда отвечает на запись отказом,
чтение работает, а команда без оплаты пишет в пределах бесплатной квоты. Лимиты команды проверяются до записи: `too_many_entries` — записей в
проекте больше предела, `entry_too_large` — версия больше предела байт, `quota_exceeded` — стор
команды с этой версией превысит квоту тарифа. Забыть запись можно и сверх квоты.

**Локальный сервер в каталоге команды без стора на машине** — не сервер хоста, а его представитель:
каждый запрос он отправляет на `mcpUrl` из сайдкара токена `~/.vibememory/tokens/<команда>/<агент>`
через `curl` и возвращает ответ как есть. Каталог берётся из маршрута `stores.<команда>.cwd`
(`vibememory route add`), проект — по правилам имён движка, и запись без `project` получает его. Агент
видит один сервер `vibememory` в любом каталоге.

**Проект у сервера на хосте не определяется**: каталога клиента он не видит, поэтому
`memory_save`, `memory_update` и `memory_delete` требуют `project`, а `project_resolve` отвечает
`project: null` и списком `projects`, которые вызывающему можно, — клиент с одним сервером на все
окна показывает выбор, а не тупик.

**Хендоффы с хоста не читаются**: хендофф — файл рабочей копии, а хост держит голый репозиторий.
`handoff_list` отвечает там `handoffs: null` и причиной — так же, как `project_resolve` отвечает
`project: null`: пустой список означал бы «ничего не в работе», а это неправда.

Каждый вызов инструмента по HTTPS оставляет в журнале сервиса строку: инструмент, команда и
проект, участник, агент, id токена и исход. Ни секрета, ни текста записи в журнале нет.

## Любой другой клиент MCP

Клиента нет в `mcp-config` — берите фрагмент Cursor: большинство клиентов читает тот же JSON `mcpServers`.
Транспорт — stdio: команда `vibememory-mcp`, аргументы `--agent <имя>`.

**`--agent` у каждого клиента свой**, строчными латинскими буквами, цифрами и дефисом.
Это имя попадает в поле `agent` каждой записи, и памяти оно нужно, чтобы отвечать на вопрос «кто это написал».
Сервер с именем не по правилу не стартует. Без флага сервер подписывается `mcp` — честно, но бесполезно, когда клиентов несколько.

## Инструменты

| Инструмент | Обязательные параметры | Что делает |
|---|---|---|
| `memory_search` | — | Ищет по словам в заголовке, описании, теле и идентификаторе. Фильтры: `project`, `kind`, `status`. Без `project` ищет по всем проектам. Всегда возвращает `status` и `disputed` — есть ли у записи rival-версии. |
| `memory_get` | `id` | Полный текст записи, её ссылки и **версия** — она нужна для `memory_update`. У записи, написанной двумя машинами сразу, — `rivals`: остальные версии целиком. |
| `memory_save` | `id`, `kind`, `description`, `body`; `project` — если сервер не в проекте | Новая запись. Отказывает, если идентификатор занят, и если такого проекта в сторе нет: запись проект не создаёт. |
| `memory_update` | `id`; `project` — если сервер не в проекте | Меняет только переданные поля; остальные остаются. Пишет новую версию с родителем — той, которую вы видели. `merges` — версии из `rivals`, сведённые в этот текст: они перестают показываться; не соперница — отказ. |
| `memory_delete` | `id`; `project` — если сервер не в проекте | Просит забыть запись вместе с её rival-версиями. Версии остаются в журнале, запись перестаёт показываться. |
| `history_search` | `query` | Ищет по словам в прошлых сессиях — Claude Code и тех, что другие агенты отдали `vibememory session put`. Возвращает проект, агента (`claude-code` или имя агента), сессию, время и выдержку — не транскрипты целиком. Новые первыми. Фильтры: `project`, `limit` (20 по умолчанию, 100 максимум). |
| `project_resolve` | `directory` (абсолютный путь) | Называет проект стора для папки по правилам движка. Ответ: `project` и правило (`repo`, `override`, `plainDir`…), или `project: null` с причиной — папка игнорируется или такого проекта в сторе нет (`wouldBe` — имя, которое дали бы правила). Ничего не пишет. На хосте папок клиента не видно: там ответ — `project: null` и `projects`, из которых можно выбрать. |
| `handoff_list` | `project` — необязателен | Открытые хендоффы проекта: файлы `memory/sessions/*.md`, у которых во фронтматтере есть строка `status: open`. На каждый — имя файла, `description`, `status` и `updated` из фронтматтера, размер файла в байтах и тело после фронтматтера. Без `project` берётся проект, в котором запущен сервер; сервер вне проекта читает все проекты, которые вызывающему можно. На хосте — `handoffs: null` с причиной: рабочей копии там нет. |

`kind` — одно из `user`, `feedback`, `project`, `reference`. `status` — `active` или `stale`.
Неизвестное значение отвергается, а не считается значением по умолчанию.

**У каждого инструмента есть заголовок и аннотации** (спека MCP): `readOnlyHint` у тех, что только
читают (`memory_search`, `memory_get`, `history_search`, `project_resolve`, `handoff_list`),
`destructiveHint` у `memory_delete`. Клиент по ним решает, спрашивать ли человека перед вызовом, —
поэтому таблица аннотаций в сервере одна на весь каталог, и тест не даёт новому инструменту
появиться без неё.

**Дисциплина памяти едет вместе с инструментами.** В описаниях `memory_save`, `memory_search` и
`handoff_list` сказано, ради чего они: решение, которое следующая сессия иначе выводила бы заново,
становится записью, а поток, брошенный на середине, — хендоффом. Иначе память остаётся пустой при
живых инструментах, и каждый следующий агент разбирает то же самое заново.
Открытые хендоффы читает `handoff_list`: движок по ним говорит сессии Claude Code, что в работе
(`SessionStart`), а агент без своих хуков спрашивает сам — этим инструментом. Хендофф считается
открытым только по фронтматтеру: строка `status: open` в теле — проза, и такой файл не вернётся.

## Что сервер намеренно не делает

- **Не пишет markdown.** Проекцию делает движок; два писателя в одни файлы — это потерянные
  правки.
- **Не решает конфликты.** Две правки от одной версии остаются обеими, как и везде в этой
  системе.
- **Не ходит в сеть.** Только локальный стор; HTTP с токеном — отдельная задача для агентов без
  локального стора.

## Почему поиск по истории ограничен

Корпус транскриптов на этой машине — 1959 файлов и 1.7 ГиБ. Поиск идёт **новыми сессиями вперёд**
и читает файл только когда до него дошёл: набрав нужное число совпадений, он останавливается и
остальные не открывает. Поэтому `limit` — не украшение, а то, что отделяет полсекунды от минуты;
а `project`, когда он известен, сужает выборку сильнее всего.

Выдержка обрезается: она нужна, чтобы узнать момент, а не чтобы отдать разговор целиком.

## Если поиск ничего не находит

Проверьте, есть ли журналы: `find ~/.vibememory/store/projects -name memory.jsonl`. Пусто —
значит память на этой машине пока живёт только в markdown и записями не стала; почему так и что
с этим делать, разобрано в
[knowledge/design/memoryNeverMetReality.md](../knowledge/design/memoryNeverMetReality.md).
