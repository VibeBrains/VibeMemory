# Спека правил и навыков VibeMemory

> Скопируйте этот файл целиком своей LLM и попросите собрать правило или навык для VibeMemory: всё, что для этого
> нужно, — здесь. Модель — [spec/rulesAndSkills.md](../spec/rulesAndSkills.md).

## 1. Что это

Правило — короткое указание, которое агент держит всегда.
Навык — порядок действий из многих шагов, который агент загружает, когда задача о нём.
VibeMemory хранит правила и навыки в сторе и раскладывает их каждому агенту машины в том виде, который он читает:
Claude Code, DeepSeek Harness, Codex.
Правка в файле любого агента доходит до остальных.

## 2. Уровни

| Уровень | Что | Где лежит в сторе |
|---|---|---|
| `personal` | правила человека: все его проекты, все машины | личный стор, `config/rules/<id>.md`; навыки — `config/skills/<name>/` |
| `team` | правила команды: её проекты, все участники | стор команды, `rules/<id>.md`; навыки — `skills/<name>/` |
| `project` | правила одного проекта | `projects/<проект>/rules/<id>.md`; навыки — `projects/<проект>/skills/<name>/` |

Уровень выше перекрывает правило с тем же `id` ниже: личное → командное → проектное.
Не перекрываются личное правило с `absolute: true` и командное с `enforced: true`.
Командное `enforced` против личного `absolute` с разным текстом — конфликт: в силе оба, движок не выбирает.

Командные правила и навыки пишут владелец и админы команды.
Участник предлагает: предложение ложится в `proposals/rules/<id>.<кто>.md` стора команды, принимает его
владелец или админ командой `vibememory rule accept <id>`.

## 3. Уровень называет человек

| Человек говорит | Уровень |
|---|---|
| «в общие правила», «в глобальные» | `personal` |
| «в правила команды» | `team` |
| «в правило проекта», «для этого проекта» | `project` |
| «сохрани в правило» без уровня | **спросить**: личное, командное или проектное |

Сервер памяти без уровня откажет: `levelRequired`.

## 4. Файл правила

```markdown
---
id: commit-language
title: Коммиты — по-русски
level: personal
absolute: false
enforced: false
paths:
  - "src/**"
---
Subject и body — по-русски.
Префикс `тип(scope):` можно машинным.
```

| Поле | Обязательно | Что |
|---|---|---|
| `id` | да | постоянное имя: строчная латиница и цифры, слова через `-`, до 64 знаков; файл называется `<id>.md` |
| `title` | да | одна строка для списка |
| `level` | да | `personal`, `team` или `project` — тот, где файл лежит |
| `absolute` | нет | только `personal`: ничто выше не перекрывает |
| `enforced` | нет | только `team`: проект и участник не перекрывают |
| `paths` | нет | глобы файлов, о которых правило; пусто — всегда. Claude Code грузит такое правило только при работе с этими файлами |

Текст — после шапки: одна мысль на строку, что делать и почему.
Правило длиннее порога (`rules.longRuleBytes` в `config.json`, по умолчанию 2048 байт) — процедура: вынести в навык,
в правиле оставить строку-указатель.
Токен `vmt_…` в правиле не пропускается: правила уезжают на все машины.
Неизвестные ключи шапки сохраняются как есть.

## 5. Навык

Каталог `<name>/` с файлом `SKILL.md` и, если нужно, `scripts/`, `references/`, `assets/`:

```markdown
---
name: deploy
description: Как выкатить сервис на хост: сборка, проверка, публикация. Использовать, когда просят выложить релиз.
---
# deploy

1. …
```

- `name` — kebab-case, до 64 знаков, совпадает с именем каталога: иначе DSH навык пропустит
- `description` обязателен, до 1024 знаков: по нему агент решает, когда навык нужен
- `SKILL.md` до 64 КБ; длинные справки — рядом, в `references/`
- `disable-model-invocation`, `user-invocable` — `true` или `false`
- поля `allowed-tools`, `hooks`, `context`, `agent`, `model`, `effort`, `arguments`, `argument-hint`, `when_to_use`
  понимает только Claude Code: навык работает и у других агентов, без них

## 6. Где агент их читает

| Агент | Правила | Навыки |
|---|---|---|
| Claude Code | `~/.claude/rules/vm-<id>.md`; в проекте `.claude/rules/vm-<id>.md` | `~/.claude/skills/`; в проекте `.claude/skills/` |
| DeepSeek Harness | `~/.dsh/AGENTS.md` — `CLAUDE.md` и правила с метками; в проекте `AGENTS.local.md` | `~/.agents/skills/`; в проекте `.agents/skills/` |
| Codex | `~/.codex/AGENTS.md` | `~/.codex/skills/` |
| Любой MCP-агент | `instructions` при знакомстве — правила `absolute` и `enforced`; `rules_get`; resources `vibememory://rules/<id>` | `skill_get`; resources `vibememory://skills/<name>`; prompts по имени навыка |

Проектные файлы лежат под `.git/info/exclude` — git проекта их не видит.
Правило в собранном файле обёрнуто метками `<!-- vibememory:rule <id>@<версия> -->` … `<!-- /vibememory:rule -->`:
правка между ними — правка правила, текст вне меток остаётся только в этом файле.

## 7. Команды

```bash
vibememory rule list [каталог]                       # правила в силе: уровень, флаги, что перекрыто
vibememory rule show <id> [каталог]
vibememory rule history <id> [каталог]                # коммиты правила в git стора и его нынешний вид
vibememory rule add --level <уровень> --title "…" [--id <id>] [--absolute] [--enforced] [--path <глоб>] < текст
vibememory rule move <id> --level <откуда> --to <куда> [каталог]
vibememory rule remove <id> --level <уровень> [каталог]
vibememory rule accept <id> [каталог]                 # принять предложение участника команды
vibememory skill list [каталог]
vibememory rules sync [каталог] [--apply] [--mode advise|merge|override]
vibememory rules mode <каталог> advise|merge|override
vibememory rules status [каталог]                     # копии у агентов, правила в силе, командные до показа, навыки
vibememory rules lint
vibememory rules split [--apply] [--skills <id>,…]    # CLAUDE.md — в личные правила по разделам ##
```

`rule add --level team` пишет не в `rules/` команды, а предложение `proposals/rules/<id>.<ник>.md`: правила команды
хост принимает только от владельца и админов, они и принимают предложение `rule accept`.
`rule move` снимает флаг, которого у нового уровня нет (`absolute` — только `personal`, `enforced` — только `team`), и
называет его. Перенос в `team` — предложение: прежнее правило остаётся в силе, пока предложение не примут.

Сервер памяти: инструменты `rules_get`, `rule_save`, `skill_get`, `skill_save` и ресурсы MCP — `vibememory://rules/<id>`
для каждого правила в силе и `vibememory://skills/<name>` для каждого навыка (`resources/list`, `resources/read`).
Каждый навык — ещё и prompt с его именем (`prompts/list`, `prompts/get`) и необязательным аргументом `task`.

Командное правило, пришедшее с пуллом, действует после показа: `SessionStart` в проекте команды или `rules status`
говорят, что пришло и от кого, и правило ложится со следующим запуском движка. Изменённое до показа остаётся в
показанном виде, `enforced` включённый без показа — тоже изменение; убранное командой уходит сразу.

Раздел `rules` в `config.json`:

```json
"rules": { "longRuleBytes": 2048, "agents": ["dsh", "codex"] }
```

`agents` — каким агентам кроме Claude Code раскладывать правила и навыки; нет ключа — всем, что есть на машине.
Агент вне списка получает свой файл обратно: части движка уходят, строки человека остаются.

## 8. Сравнение с файлами проекта

`rules sync` читает собственные файлы правил проекта — `CLAUDE.md`, `AGENTS.md`, `.claude/rules/`, `.vibe/rules/`,
`.cursor/rules/` — и сверяет каждый блок с историей правил в git стора:

| Состояние | Что значит |
|---|---|
| дубль | совпадает с правилом в силе: может уйти, агент получит правило и так |
| устарел | совпадает с прошлой версией правила: заменить |
| свой вариант | изменён руками; изменения правила сливаются поверх, спорные строки — человеку |
| только в проекте | правила такого нет: оставить или поднять `rule add` |

Режим проекта: `advise` (по умолчанию) только говорит; `merge` убирает дубли, обновляет устаревшее и чисто
слившееся; `override` кладёт правило в силе поверх каждого совпавшего блока, версию проекта — в карантин.
Блоки «только в проекте» не трогаются ни в одном режиме.

Ещё `rules sync` называет уроки сессий — воспоминания проекта с `type: feedback`, у которых нет правила с тем же `id`.
Это правила по сути: поднять такое — `rule add --level project --id <id воспоминания>`. Воспоминание остаётся.

## Фикстуры

`fixtures/rules/rulesScenarios.json` — данные теста `crates/vibememory-core/tests/rules_fixtures.rs`. Разделы:

- `rules` — файл правила (`file`) и что из него читается (`expect`: `id`, `title`, `level`, `absolute`, `enforced`,
  `paths`, `body`, `extra` — неизвестные ключи) или подстрока отказа (`error`); прочитанное записывается и читается
  снова — должно совпасть
- `skills` — каталог (`directory`), `SKILL.md` (`file`) и `expect` (`name`, `description`, `claudeOnly`) или `error`
- `layers` — файлы уровней `personal`, `team`, `project` и итог: `inForce` — строки `[id, уровень, [перекрытые]]`,
  `kept` — `[id удержанного, уровень отвергнутого]`, `conflicts` — пары
- `assembly` — база (`base`), правила `[файл, [уровни, которые перекрывает]]`, правки собранного файла `[было,
  стало]` и куски, которые из него читаются (`base`, `rule` с `edited` и `body`, `outside` с `text`), или `error`
- `judge` — файл проекта (`file`, `whole`, `text`), истории правил (`id`, `versions` — `[заголовок, текст]` от
  старой к новой) и решения по блокам (`heading`, `rule`, `guessed`, `state`, для `stale` — `behind`, для `custom` —
  `clean` и `merged`)
- `similar` — заголовок и текст нового правила, известные `[id, заголовок, текст]` и какие `id` найдены
- `shown` — командные правила в сторе (`current`) и показанные на машине (`shown`): что раскладывается (`laid` —
  `[id, текст]`) и что ждёт показа (`unseen` — `[id, new|changed]`)

Новый кейс: добавить в нужный раздел и прогнать `cargo test -p vibememory-core --test rules_fixtures`.
Проверка, что кейс держит: сломать в коде то, что он проверяет, — тест обязан упасть.
