# Промпт: аудит и ужесточение доступа к своему серверу

> Скопируйте этот файл целиком своему агенту в проекте, где есть свой сервер (VPS, хост
> сборки, хост бэкапов, приложение за reverse-proxy или без него). Пересобран 2026-09-16 не по
> общим советам, а по итогам живых проверок: сервер VibeMemory 2026-09-09…13 (ssh, fail2ban,
> сервис за прокси, установка, диск); машина владельца — гигиена облачной папки (2026-09-02…10) и
> замер замены бинаря на macOS (2026-09-10); два разбора VibeSter 2026-07-30…31 (утечка в журнал
> панели, установочные значения в документации и дефолтах скриптов). Каждый пункт — то, что
> оказалось неправдой, когда его проверили.

## Задача агенту

Проверь и ужесточи доступ к серверу проекта. Работай **фактами с сервера**, а не выводом
клиента и не предположениями. Каждый шаг ниже — с проверкой; шаг без проверки не считается
сделанным.

Рецепты ниже проверены на Debian 12 с systemd, journald, nftables и apt; сервис — systemd-юнит за
Caddy или nginx. Это охват, а не пример: на другом стеке команды не переносятся буквально. До
первого шага установи и запиши в отчёт:

1. Есть ли shell на сервере (PaaS, managed hosting — нет). Без shell применимы только шаг 4 и
   внешние проверки 5.1 (`curl`, срок сертификата); остальное — «не применимо: нет shell».
2. Init: `systemctl --version` (systemd) или `rc-service`/`service`. Без systemd `journalctl -u`,
   `systemctl show`, `backend = systemd` и `journalmatch` не работают: журнал sshd и сервиса — в
   файле (`/var/log/auth.log` или `/var/log/secure`), изоляция — средствами своего init.
3. Имя юнита ssh: в командах ниже он назван `ssh`, как на Debian/Ubuntu; на RHEL/Fedora/Arch —
   `sshd` (`systemctl list-units --type=service | grep -E 'sshd?\.service'`).
4. Куда пишет сервис: journald / файл / контейнер (`docker ps`). В контейнере 5.2, 5.3 и 5.5 в
   этой форме не применимы: изоляция и токен-из-файла решаются на уровне контейнера; для 3.4 есть
   контейнерная ветка (журнал контейнера через journald), иначе журнал читается из логов
   контейнера.
5. Firewall: `ls -l /usr/sbin/nft /usr/sbin/iptables` полным путём — без обоих fail2ban
   декоративен (3.2).
6. Пакетный менеджер: `apt-get` ниже — Debian/Ubuntu; на другом — свой.

Неприменимость — по карте, а не молча. Нет reverse-proxy — что проверить вместо, сказано в 3.3 и
5.1; сервис не HTTP или публичный без токена — в 5.1; нет fail2ban — в 3.5; нет git — в шаге 6;
нет своего сервиса (API, вебхук, MCP) — 3.3–3.5, 4.4 и весь шаг 5 не применимы, в отчёте одной
строкой с причиной. Шаг без такой оговорки на другом стеке не пропускается молча: ищется
эквивалент на своём стеке, а если его нет — в отчёте «не применимо: <причина>».

**Предусловие: root без пароля.** Все команды ниже требуют root. Сессия агента идёт без tty, и
sudo с паролем в ней не работает. Первая команда сессии:

```bash
[ "$(id -u)" = 0 ] && echo ROOT_OK || { sudo -n true && echo SUDO_OK; }
```

`ROOT_OK` — префикс `sudo` из команд убирается (на минимальной Debian под root его может не быть
вовсе). `SUDO_OK` — работаем. Ни того ни другого — остановиться и отчитаться: владелец сам, вне
сессии агента, даёт пользователю `NOPASSWD` (`/etc/sudoers.d/<admin>` через `visudo`), после чего
проверка повторяется. Подсказка sudo про `-S` — не инструкция.

## Правило номер один: проверка клиентом ничего не доказывает

Типичная ошибка — «проверить» запрет входа так:

```bash
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no root@<host>
```

и увидеть `Permission denied (publickey,password)`. **Это не доказательство.** Такой же ответ
приходит для любого пользователя, в том числе разрешённого: список методов в этой строке
глобальный и от пользователя не зависит, а пароль в неинтерактивном режиме вообще не
предлагался.

Доказательства всегда на стороне сервера:

```bash
sudo sshd -T -C user=root,host=x,addr=1.2.3.4 | grep -i permitrootlogin   # политика для этого пользователя
sudo journalctl -u ssh --since "1 hour ago" | grep -iE "accepted|failed"  # что случилось на самом деле
```

`sshd -T` — это политика, которую демон прочитает из файлов (с учётом `Match`), а не то, что он
держит в памяти сейчас. Она доказывает содержимое конфига, а факт применения доказывает журнал:
`Received SIGHUP; restarting` после метки времени reload. Порядок всегда такой: журнал подтвердил
reload → `sshd -T` описывает, что именно демон перечитал.

То же правило в других обличьях: служба `active` вместо «делает то, что обещает» (ниже —
fail2ban, который считал нарушителей и не блокировал ничего, и джейл, который был `active` и не
считал ничего); `command -v nft` вместо полного пути (`nft` лежит в `/usr/sbin`, которого нет в
`PATH` неинтерактивной ssh-сессии); зелёный отчёт вместо «операция дошла» (синхронизация сутки
стояла на полном диске при нуле ошибок в диагностике); `ssh <host> 'echo OK'` через мастер-канал
вместо новой аутентификации (`ControlMaster` переиспользует открытое соединение, и ужесточённый
конфиг никто не проверил). Каждый раз проверялся **признак**, а не **следствие**. Спрашивать надо
не «включено ли», а «произошло ли то, ради чего включали».

## Шаг 1. Измерить, а не вообразить

До всяких правок снимите фон — иначе не с чем сравнивать и нечем обосновывать решения.

```bash
sudo journalctl -u ssh --since "1 hour ago" --no-pager > /tmp/a.log
echo "неудачных паролей: $(grep -c 'Failed password' /tmp/a.log)"
echo "  из них по root:  $(grep -c 'Failed password for root' /tmp/a.log)"
echo "уникальных IP:     $(grep -oE 'from [0-9.]+ port' /tmp/a.log | awk '{print $2}' | sort -u | wc -l)"
echo "принято по ключу:  $(grep -c 'Accepted publickey' /tmp/a.log)"
echo "принято паролем:   $(grep -c 'Accepted password' /tmp/a.log)"
df -h /                        # занятость диска
sudo du -sh <каталог данных>   # сколько весит то, что растёт
# ss -t показывает только TCP — на реальном хосте он прятал caddy на UDP *:443 (HTTP/3), публичный порт,
# которого в TCP-выводе нет; VPN (WireGuard 51820/udp), DHCP-клиент (0.0.0.0:68/udp), NTP — тоже только в -u
sudo ss -tulnp                 # каждый порт не на 127.0.0.1 — с ответом, зачем он открыт
```

Ориентир из реального замера на обычном VPS: **615 неудачных попыток пароля и 290 уникальных
адресов за час**, из них 66 по `root`; принято паролем — 0. Это нормальный фон интернета, и
именно поэтому «у нас непопулярное имя пользователя» — не аргумент, а надежда. Ноль принятых
паролей — сегодняшнее состояние, а не гарантия. Диск того же сервера однажды показал 100 %, а
каталог данных вырос с 600 МиБ до 5,5 ГиБ — заметили случайно; запишите «сколько весило при
установке» сейчас, иначе рост не с чем сравнить.

## Шаг 2. Ужесточить ssh порядком, при котором нельзя запереться

Потерять доступ к своему серверу — самая дорогая ошибка в этом списке, поэтому порядок важнее
самих настроек. На реальном VPS до правки `sshd -T` показывал `permitrootlogin yes`,
`passwordauthentication yes`, `maxauthtries 6` — root по паролю был разрешён.

0. **Закрепи ключ на клиенте.** Каждый ключ, который клиент предложил, а сервер отверг, — неудача
   для `MaxAuthTries`; при `MaxAuthTries 3` четвёртый ключ из агента не предлагается вовсе,
   соединение рвётся с `Too many authentication failures`. Поэтому в `~/.ssh/config` блок хоста:
   ```
   Host <host>
       HostName <адрес>
       User <admin>
       IdentityFile ~/.ssh/<key>
       IdentitiesOnly yes
   ```
   Проверка — клиент предлагает ровно один ключ:
   ```bash
   ssh -v -o BatchMode=yes -o ControlPath=none <host> 'echo OK' 2>&1 | grep -E 'Offering public key|^OK$'   # одна строка Offering public key и строка OK
   ```
   `ssh-add -l` для этого не годится: клиент предлагает и дефолтные файлы `~/.ssh/id_*`, которых
   в агенте нет. Ключ, который живёт только в агенте, закрепляется тем же блоком через его `.pub`
   (`IdentityFile ~/.ssh/<key>.pub`) — приватную часть ssh возьмёт из агента. Все проверочные
   соединения ниже — тем же `ssh <host>` через этот блок, с добавкой `-o ControlPath=none`;
   отдельной командной строки с `-i` для проверки не заводить — иначе страховку снимет путь,
   которым потом никто не ходит.
1. **Сначала докажи, что ключ работает, новым соединением, а не сессией из мастер-канала.**
   `ControlMaster auto` / `ControlPersist` в `~/.ssh/config` пускают каждую `ssh <host> cmd`
   через уже открытый мастер без новой аутентификации; отключает разделение только
   `ControlPath=none` (`ControlMaster=no` — умолчание, мастер оно переиспользует).
   ```bash
   ssh -o ControlPath=none -o BatchMode=yes <host> 'echo "$SSH_CONNECTION"'   # второе поле — порт клиента этого соединения
   sudo journalctl -u ssh --since "2 min ago" | grep "Accepted publickey for <admin> from .* port <этот порт>"
   ```
   Строка обязана найтись с этим портом. Просто «есть `Accepted publickey` за последние минуты»
   ничего не доказывает: на хосте с автоматикой (тик, бэкап, CI) такие строки идут постоянно.
   Ключ при этом — тот, что закреплён в п. 0, а не `-i` из командной строки.
2. **Пиши drop-in, а не правь главный конфиг.** Откат тогда — удаление одного файла:
   `/etc/ssh/sshd_config.d/10-<проект>-hardening.conf`. Имя — с префиксом проекта (в одной
   установке — `10-vibememory-hardening.conf`): `10-hardening.conf` — типовое имя, и у
   администратора оно может быть занято своим файлом, который запись перепишет, а страховка при
   откате удалит. Drop-in действует только при двух условиях, и оба проверяются до записи. У sshd
   побеждает **первое** встреченное значение, поэтому `Include` обязан стоять раньше любой
   директивы главного файла. Drop-in'ы читаются в лексическом порядке имён, поэтому имя своего
   файла обязано сортироваться раньше уже лежащих там (Ubuntu через cloud-init кладёт
   `50-cloud-init.conf` с `PasswordAuthentication yes`; `99-hardening.conf` из типовых советов ему
   проиграет). Состояние до записи — в отчёт:
   ```bash
   grep -n '^Include' /etc/ssh/sshd_config                  # где стоит и куда указывает
   grep -nvE '^\s*(#|$)' /etc/ssh/sshd_config | head -3     # первая действующая строка — Include (Debian 12, Ubuntu 24.04: так и есть)
   ls -la /etc/ssh/sshd_config.d/                           # своё имя сортируется раньше всех этих
   sudo test -e /etc/ssh/sshd_config.d/10-<проект>-hardening.conf && { echo "уже есть, не трогаю"; sudo cat /etc/ssh/sshd_config.d/10-<проект>-hardening.conf; exit 1; }   # запись только в отсутствующий файл
   ```
   `set -o noclobber` вместо последней строки не подходит: `sudo tee` и `sudo sh -c '… >'` опцию
   не наследуют. Страховка из п. 4 удаляет `rm -f` только этот файл, отсутствие которого доказано
   до записи; чужой файл под неё попасть не может. Если `Include` ниже директив или его нет —
   drop-in не поможет, и перенос `Include` наверх есть правка главного конфига: делается тем же
   порядком со страховкой (п. 3–7). Итог — не по grep, а
   `sudo sshd -T -C user=root,host=x,addr=1.2.3.4` (без `-C` Match-блоки не применяются): до
   `reload` — что получится, и ещё раз после п. 7 — что drop-in пережил окно страховки.
3. **Проверь синтаксис до применения:** `sudo sshd -t`. Битый конфиг не доедет до демона.
4. **Вооружи страховку транзитным таймером systemd ДО применения.** Он живёт в `system.slice`, а
   не в scope твоей ssh-сессии: nohup-процесс под sudo остаётся в `session-N.scope` и при
   `KillUserProcesses=yes` или `loginctl terminate-session` умирает вместе с соединением — а агент
   закрывает соединение сразу после `reload`. Через 180 секунд таймер снесёт drop-in и
   перезагрузит ssh, если маркер не подтверждён журналом. Маркер — не «файл есть», а «файл
   называет соединение, которое sshd принял ПОСЛЕ вооружения»: старая сессия, чужой
   автоматический вход и мультиплексированный `ssh` этого дать не могут. Маркер лежит в `/run`
   (пишет только root, чистится перезагрузкой), а не в `/tmp` (1777, создаст кто угодно), и
   ставится **только из нового соединения** (новое — это `ssh -o ControlPath=none`, а не
   очередная `ssh <host>` из той же консоли):
   ```bash
   sudo sshd -T | grep -i '^loglevel'                       # INFO или подробнее: ниже строк Accepted нет, и откат сработает всегда
   sudo rm -f /run/ssh-ok                                   # маркер прошлой попытки: журнал его не подтвердит, но лежать он не должен
   sudo systemctl list-timers ssh-guard.timer --no-pager    # «0 timers listed»; иначе висит прошлая попытка — не вооружать
   ARM=$(date +%s); echo "$ARM"                             # метка вооружения — в отчёт: шелл агента переменных между вызовами не хранит
   sudo systemd-run --unit=ssh-guard --collect --on-active=180 --timer-property=AccuracySec=1s \
     sh -c 'M=$(cat /run/ssh-ok 2>/dev/null); [ -n "$M" ] && journalctl -u ssh --since=@'"$ARM"' -q | grep "Accepted " | grep -qF -- "$M" || { rm -f /etc/ssh/sshd_config.d/10-<проект>-hardening.conf; systemctl reload ssh; }; rm -f /run/ssh-ok'
   sudo systemctl list-timers ssh-guard.timer --no-pager    # строка с LEFT — вооружена, виден остаток окна; пусто — не идти дальше
   ```
   `AccuracySec=1s` обязателен: без него таймер срабатывает с опозданием до минуты (дефолт
   `DefaultTimerAccuracySec=1min`). `--collect` обязателен: без него упавший сервис держит имя, и
   следующее вооружение откажет. Повторное вооружение при живом таймере откажет громко («already
   loaded») — это и есть проверка, что прошлая попытка не висит. Откат отменяется, только если
   маркер называет соединение, которое sshd принял после вооружения; файл сам по себе ничего не
   отменяет. `rm -f` в страховке — только свой файл из п. 2.
5. **`reload`, а не `restart`.** Живые соединения переживают перезагрузку конфига; `restart`
   рвёт единственную работающую сессию ровно тогда, когда она нужнее всего. Применение
   подтверждается фактом, не кодом возврата:
   ```bash
   T=$(date +%s); echo "$T"                                 # метка reload — в отчёт
   sudo systemctl reload ssh || echo "reload не прошёл: sshd -t в ExecReload упал, HUP не отправлен"
   sudo journalctl -u ssh --since=@$T --no-pager | grep -E 'Received SIGHUP; restarting|Server listening on'
   ```
   Обязаны быть обе строки: `Received SIGHUP; restarting` — демон получил сигнал и переисполнился,
   `Server listening on` — новый экземпляр поднялся и слушает. Обе — уровень INFO, видны при
   дефолтном `LogLevel`. Нет первой — reload не дошёл (код возврата `systemctl reload` при провале
   `sshd -t` в `ExecReload` ненулевой, HUP не уходит); нет второй — демон упал на переисполнении,
   `systemctl is-active ssh` покажет `failed`.
6. **Проверь новым соединением и им же поставь маркер** — одной командой, через блок хоста из
   п. 0, с запретом мультиплексирования, иначе `ssh` переиспользует старую аутентификацию и
   ничего не проверит:
   ```bash
   ssh -o ControlPath=none -o BatchMode=yes <host> 'set -- $SSH_CONNECTION; printf "from %s port %s " "$1" "$2" | sudo tee /run/ssh-ok; echo'
   sudo journalctl -u ssh --since=@$ARM --no-pager | grep -F "$(sudo cat /run/ssh-ok)" | grep 'Accepted publickey'   # строка с этим портом обязана найтись
   ```
   Соединение не прошло — команда не выполнилась, маркера нет, откат сработает сам. Ставить
   маркер из старой сессии бесполезно: в нём окажется её порт, а её `Accepted` записан до
   вооружения. Нет строки с портом — соединение не новое, и страховка увидит это сама: маркер
   руками не чинить, ждать отката.
7. **Дождись закрытия окна по факту, а не по часам,** и убедись, что drop-in на месте. Иначе
   успех мнимый: откат мог сработать, а проверка — пройти уже по старому конфигу.
   ```bash
   until ! sudo systemctl list-timers ssh-guard.timer --no-pager | grep -q ssh-guard; do sleep 5; done
   ls /etc/ssh/sshd_config.d/                                                              # drop-in на месте
   sudo journalctl -u ssh --since=@$T --no-pager | grep -c 'Received SIGHUP; restarting'   # ровно 1: вторая — страховка сработала и откатила
   sudo sshd -T -C user=root,host=x,addr=1.2.3.4 | grep -iE 'permitrootlogin|maxauthtries|passwordauthentication'   # drop-in пережил окно
   ```
   Если sshd работал с `LogLevel` ниже `INFO`, строк `Accepted` нет и откат сработал всегда — это
   безопасный отказ; уровень поднимается до вооружения (п. 4), а не после.

Разумный минимум настроек:

```
PermitRootLogin prohibit-password
MaxAuthTries 3
```

**Проверь до правки, есть ли у root рабочие ключи** — содержимым файла, а не его размером:
`sudo test -s` здесь врёт. Облачные образы Ubuntu и Debian (cloud-init, `disable_root: true` —
умолчание) кладут root тот же ключ, что и обычному пользователю, но с привязанной командой:
`command="echo 'Please login as the user \"ubuntu\" rather than the user \"root\".';echo;sleep 10;exit 142"`.
Файл непуст, ключ принимается, а оболочки root по нему нет.

```bash
sudo grep -vE '^[[:space:]]*(#|$)' /root/.ssh/authorized_keys | grep -vc 'command='   # строк без command= — столько ключей дают root оболочку
```

`0` — оболочки root по ключу нет, и `prohibit-password` означает «root не зайдёт вообще» — это
обычно и нужно, но знать об этом надо заранее, потому что формулировка звучит мягче последствия.
Строки с `command=` — не вход, а привязанная команда (заглушка cloud-init, `rrsync` бэкапа):
оболочки по ним нет, а сама команда как работала, так и работает — `prohibit-password` запрещает
только пароль. Свой ключ — доказать входом, а не чтением файла:
`ssh -o BatchMode=yes root@<host> 'echo OK'` печатает `OK`; заглушка вместо этого печатает
«Please login as the user…» и выходит с кодом 142.

Про `PasswordAuthentication no`: правильный ответ — выключить. Но если IP администратора меняется
и запасного входа нет, отключение пароля может оставить вас снаружи. Тогда пароль оставляют
осознанно и закрывают дыру следующим шагом — и называют это своим именем: защита неизвестностью.

## Шаг 3. fail2ban — и обязательно проверить, что он что-то делает

Он банит по числу неудач, а не по адресу, поэтому меняющийся IP администратора ему не помеха.

**Цена, которую надо назвать вслух:** бан действует на весь адрес, включая вход по ключу. Пять
промахов паролем — и вы не войдёте с этого адреса ни паролем, ни ключом, пока бан не истечёт.

### 3.1 Джейл для ssh

Сначала — что уже лежит на сервере, в отчёт: `jail.local` у многих есть (свои `ignoreip`, свои
джейлы), и `cat >` снёс бы его.

```bash
ls -la /etc/fail2ban/jail.local /etc/fail2ban/jail.d/ 2>&1
grep -ln '^\[sshd\]' /etc/fail2ban/jail.local /etc/fail2ban/jail.d/*.local 2>/dev/null   # чужая секция [sshd]; Debian-овский jail.d/defaults-debian.conf с одним enabled = true — не в счёт
```

`jail.local` не создавать и не переписывать никогда. Свой файл —
`/etc/fail2ban/jail.d/<проект>-sshd.local`, с той же проверкой `sudo test -e` перед записью, что и
drop-in sshd (шаг 2, п. 2), и с той же переписью только при отличии текста, что у джейла сервиса
в 3.4 и 5.5. Если секция `[sshd]` у администратора уже есть — свой файл не писать: она всё равно
перекрылась бы ключ за ключом. Снять эффективные значения (`sudo fail2ban-client get sshd maxretry`,
`… findtime`, `… bantime`, `… ignoreip`, `… actions`) и предложить владельцу правку его файла, а
не дубль.

```ini
# /etc/fail2ban/jail.d/<проект>-sshd.local
[sshd]
enabled = true
# На Debian 12 нет /var/log/auth.log: журнал только в systemd
backend = systemd
ignoreip = 127.0.0.1/8 ::1
maxretry = 5
findtime = 10m
bantime = 1h
bantime.increment = true
bantime.maxtime = 1w
# Именно normal, не aggressive: aggressive считает нарушением и разрыв до аутентификации
mode = normal
banaction = nftables-multiport
```

В своём файле нет секции `[DEFAULT]`: по man jail.conf(5) `jail.d/*.local` читается после
`jail.local`, и `[DEFAULT]` там перекроет `ignoreip`, `bantime`, `maxretry` администратора для
всех джейлов молча. Все ключи — под `[sshd]`.

В файлах fail2ban `#` — комментарий только с начала строки, инлайн-комментарий — только ` ;`
через пробел. Хвост после ` #` становится частью значения: `backend` превращается в «Unknown
backend», `mode` уезжает в `sshd[mode=normal # …]`, и джейл не создаётся, хотя служба `active`.
То же правило — для любого файла под `/etc/fail2ban` (`jail.d/*.local`, `filter.d/*.conf`): их
читает тот же парсер.

**Свой текущий IP в `ignoreip` вписывать не стоит:** он меняется, а вписанный однажды останется
исключением навсегда — в том числе для того, кому этот адрес достанется после вас. Обычный путь
администратора — ключ, и неудач он не даёт только потому, что закреплён в шаге 2. Каждый
предложенный и отвергнутый ключ сервер считает неудачей; при `MaxAuthTries 3` четвёртый ключ не
предлагается вовсе, сервер пишет `maximum authentication attempts exceeded for <admin> from
<адрес>`, а эту строку fail2ban считает в любом режиме, включая `normal` (одиночные
`Failed publickey` он не считает, превышение — считает). Пять таких соединений за 10 минут —
бан своего адреса на час вместе с живой сессией: правило nftables не делает исключения для
established.

**Бэкенд `systemd` — это python-модуль `systemd.journal` из пакета `python3-systemd`.** В
Debian/Ubuntu он у fail2ban в `Recommends`, а не в `Depends` (Debian 12, fail2ban 1.0.2-2:
`apt-cache show fail2ban`), поэтому `apt-get install --no-install-recommends fail2ban` или образ с
выключенными Recommends оставляют fail2ban без него. Тогда джейл с `backend = systemd` не
поднимается вовсе: в журнале fail2ban —
`Backend 'systemd' failed to initialize due to No module named 'systemd'` и
`Failed to initialize any backend for Jail 'sshd'`. При `systemctl restart` сервер выходит с кодом
255 и юнит становится `failed`; при `fail2ban-client reload` на работающем сервере команда отвечает
`NOK`, служба остаётся `active`, а джейла `sshd` больше не существует. Проверить до включения:

```bash
python3 -c 'import systemd.journal' || sudo apt-get install -y python3-systemd
```

До включения джейла — журнал за сутки со своего адреса: строку превышения `MaxAuthTries` fail2ban
считает как неудачу (см. выше), и если она уже идёт с вашего адреса, джейл с первой минуты считает вас,
а не только ботов:

```bash
me=${SSH_CLIENT%% *}   # свой адрес глазами сервера, не внешнего сервиса
sudo journalctl -u ssh --since "1 day ago" | grep -c "maximum authentication attempts exceeded for <admin> from $me"   # 0
```

Считать без адреса нельзя: боты, перебирающие пароль к имени `<admin>`, пишут ту же строку
каждые три попытки.

Применение проверяется не одним `-t`, а тем, что реально ловит:

```bash
sudo fail2ban-client -t                    # только битый INI; значения не проверяет — на хвосте после # скажет OK
sudo fail2ban-client -d | grep "'add'"     # ['add', 'sshd', 'systemd'] — backend ровно таким уйдёт серверу, хвост будет виден здесь
sudo fail2ban-client reload                # ответ OK, не NOK; если меняли banaction существующего джейла — restart, см. ниже
sudo fail2ban-client status                # в Jail list есть sshd
sudo fail2ban-client status sshd | grep 'Journal matches'   # строка есть; у файлового бэкенда вместо неё File list
for k in maxretry findtime bantime ignoreip actions; do sudo fail2ban-client get sshd $k; done   # эффективные значения: чем перекрылось — видно только так
```

**`reload` после смены действия у существующего джейла — ловушка fail2ban 1.1** (Debian 13): джейл
остаётся работать вовсе без действия. `status` показывает забаненных, в nftables — ноль, а
`fail2ban-client get sshd actions` отвечает `No actions for jail sshd`. Если меняли `banaction` —
`sudo systemctl restart fail2ban`, баны восстановятся из его базы. Проверка одна:

```bash
sudo fail2ban-client get sshd actions      # имя действия, не «No actions»
```

Дальше — проверка 3.2: список джейла против набора nft.

### 3.2 Ловушка, на которой это ломается молча

На минимальном сервере **может не быть ни `iptables`, ни `nft`**. fail2ban при этом
запускается, показывает `active`, честно считает нарушителей и пишет «Currently banned: 2» — а
блокировать ему нечем. Баны существуют только в его собственной базе.

Поэтому проверка обязательна, и не по статусу службы:

```bash
sudo fail2ban-client status sshd                           # что он думает
ls -l /usr/sbin/nft /usr/sbin/iptables                     # полным путём, не command -v
sudo /usr/sbin/nft list tables                             # таблица f2b-table должна существовать
sudo /usr/sbin/nft list set inet f2b-table addr-set-sshd   # адреса должны реально лежать здесь
```

Списки из первой и последней команды обязаны совпадать. Если нет — бан декоративный.

На Debian 12 родное — nftables: поставьте пакет `nftables` и укажите в своём
`jail.d/<проект>-sshd.local` под `[sshd]` `banaction = nftables-multiport` (в форме 3.1 он уже
стоит; джейлу, банящему все порты, — `nftables-allports`). Службу `nftables` включать не нужно:
fail2ban заводит свою таблицу `inet f2b-table`, а включённая служба подгрузила бы
`/etc/nftables.conf` — это уже другая правка, и делать её заодно нельзя.

### 3.3 Джейл для своего сервиса: чей адрес в журнале

Если у вас есть свой сервис с токеном (API, вебхук, MCP), отказы по токену — такой же перебор,
как пароли ssh, и джейл на них ставится так же. Но сначала — адрес.

**За reverse-proxy сервис видит все соединения с `127.0.0.1`.** Если в строке отказа стоит этот
адрес, банить некого — джейл невозможен в принципе, а `ignoreip = 127.0.0.1/8` сделает его ещё
и безвредным. Приложение обязано писать в журнал адрес клиента, и брать его надо из
**последнего** элемента `X-Forwarded-For` — того, который добавил сам прокси. Первый элемент
прислал клиент, и подделывается он одной строкой. Проверка подделкой, а не чтением кода:

```bash
curl -s -o /dev/null -H "X-Forwarded-For: 6.6.6.6" -H "Authorization: Bearer wrong" https://<domain>/<path>
sudo journalctl -u <service> --since "2 min ago" | tail -3   # ваш адрес есть, 6.6.6.6 — нет
```

Сверять адрес с тем, что сервер видит у вашей ssh-сессии (`echo "$SSH_CLIENT"`), а **не** с
внешним сервисом «какой у меня IP»: у машины может быть два выхода, и внешний сервис назвал
другой адрес. Верить хосту.

**Если прокси нет** — заголовку `X-Forwarded-For` доверять нельзя вовсе: его прислал клиент.
Проверка та же: поддельный заголовок в журнал попасть не должен, в строке — адрес пира.

Бан — только на порты сервиса (`port = http,https`), не на ssh: неверный токен ничего не говорит
об ssh. `maxretry` мягче, чем у ssh: клиент, оставшийся со старым токеном после ротации,
перебирает сам, и запереть владельца от собственного сервиса на час вероятнее, чем поймать
злоумышленника. В реальной установке — 10 отказов за 10 минут.

### 3.4 Джейл «active» с нулём счёта

Поставленный джейл показывал `active` и не считал ничего. Причины три, и каждая по отдельности
даёт ноль. Сначала — третья: пока не доказано, что строка отказа вообще видна бэкенду джейла,
чинить флаги и якорь бессмысленно.

- **Строки отказа в journald нет вовсе.** Сервис пишет через свой логгер в файл, под pm2
  (`~/.pm2/logs/<app>-out.log`) или в контейнер с драйвером `json-file`; в journald уходят только
  сообщения мимо логгера — старт и падения. Это бывает и у systemd-юнита с
  `StandardOutput=journal`: юнит пишет в журнал, приложение — в `data/logs/<app>-<дата>.log`.
  Проверка до всяких флагов — один отказ и счёт по тому источнику, который указан в джейле:
  ```bash
  curl -s -o /dev/null -H "Authorization: Bearer wrong" https://<domain>/<path>
  sudo journalctl -u <service> --since "2 min ago" | grep -cF "refused"   # 0 — строка ушла не в журнал
  grep -cF "refused" <файл логов приложения>                                # здесь она и лежит
  ```
  Тогда джейл читает файл, а не журнал: в `jail.d/<jail>.local` — `backend = auto` (перекрывает
  `backend = systemd`, если администратор задал его в `[DEFAULT]`; иначе `logpath` игнорируется)
  и `logpath = <файл>`; файл обязан существовать при старте джейла; замер —
  `sudo fail2ban-regex <файл> /etc/fail2ban/filter.d/<jail>.conf`.
  **Ловушка файловой ветки:** glob в `logpath` fail2ban раскрывает один раз при старте джейла —
  файл с датой в имени (`<app>-2026-09-16.log`) даст джейл, который считает сегодня и молча уходит
  в ноль в полночь, тем же симптомом, что и весь этот раздел. Строка отказа должна лежать в файле
  с постоянным именем (ротация переименованием через logrotate — её fail2ban переживает) либо
  дублироваться в stderr, откуда её заберёт journald, — тогда рецепт ниже применяется без
  изменений. Если файл — JSON-строки, фильтр совпадает внутри обёртки
  (`"msg":"<service>: refused … from <HOST>"`), а не по `$` в конце строки; `datepattern` — под
  поле времени файла; `fail2ban-regex` покажет и совпадения, и ошибки разбора даты.
  **Контейнер:** запускать с `--log-driver=journald` (compose: `logging: {driver: journald}`), в
  фильтре `journalmatch = CONTAINER_NAME=<имя>`, бэкенд — тот же `systemd[journalflags=1]`, что в
  форме ниже; замер — тот же `fail2ban-regex "systemd-journal[journalflags=1]"`. `logpath` на
  `/var/lib/docker/containers/<id>/<id>-json.log` не брать: id меняется при каждом пересоздании, а
  glob читается один раз при старте — снова молчаливый ноль. _Контейнерная ветка собрана по
  документации Docker и fail2ban, на живом хосте не измерялась — замер у себя обязателен._
- **Сервис работает от обычного пользователя** (`User=<user>` в юните), и journald кладёт его
  вывод в `user-<uid>.journal`. Бэкенд `systemd` без `journalflags=1` (`LOCAL_ONLY`)
  пользовательские журналы не читает. Джейл `sshd` этого не покажет: sshd пишет от root.
- **Бэкенд подставляет перед сообщением хост и имя процесса**, поэтому `failregex` с якорем `^`
  не совпадает никогда.

Замер `fail2ban-regex` по настоящему журналу: без флага — 0 строк; с флагом и якорем — 8 строк,
0 совпадений; с флагом без якоря — 2 совпадения, 6 пропущенных. И шесть пропущенных — правильно:
три из них — строки старта сервиса, три — отказы, записанные до того, как в сообщение добавили
адрес. «Строки» здесь — весь вывод сервиса в журнал, а старые отказы без адреса совпасть не могут
и не должны: в них нет `<HOST>`, банить некого. Поэтому критерий — не «совпадений столько же,
сколько отказов». Повторите замер у себя — он и есть проверка фильтра: строк не ноль (иначе не
тот флаг или `journalmatch`), совпадений не ноль (иначе якорь `^` или ни одного отказа в новом
формате — наберите один `curl` с неверным токеном и повторите), а среди пропущенных нет ни одной
строки отказа в текущем формате:

```bash
sudo fail2ban-regex "systemd-journal[journalflags=1]" /etc/fail2ban/filter.d/<jail>.conf --print-all-missed
```

Форма фильтра и джейла, которая считает (имена и текст сообщения — ваши; `<HOST>` — маркер
fail2ban, его не заменять):

```ini
# /etc/fail2ban/filter.d/<jail>.conf
[Definition]
failregex = <текст вашей строки отказа без адреса> <HOST>$
journalmatch = _SYSTEMD_UNIT=<service>.service

# /etc/fail2ban/jail.d/<jail>.local
[<jail>]
enabled   = true
filter    = <jail>
backend   = systemd[journalflags=1]
port      = http,https
maxretry  = 10
findtime  = 10m
banaction = nftables-multiport
```

Текст для `failregex` берётся из вашего журнала, а не из этого примера: вызовите отказ curl'ом из
3.3 и возьмите сообщение из `sudo journalctl -u <service> --since "2 min ago" | tail -1` — без
префикса journald (дата, хост, `процесс[pid]:`) и без адреса в конце; спецсимволы regex (`.`,
`(`, `[`, `?`, `+`) экранировать обратной косой. Пример из одной установки:
`<service>: refused a request without the right token from <HOST>$`. Строка отказа в приложении
обязана быть одной и той же, с адресом последним словом: фильтр совпадает буквально, и правка
сообщения без правки фильтра снова даст ноль.

### 3.5 Живая проверка бана и разбан

Признак — статус джейла; следствие — соединения нет. Проверяется вторым:

```bash
for i in $(seq 1 10); do curl -s -o /dev/null -H "Authorization: Bearer wrong" https://<domain>/<path>; done
sudo fail2ban-client status <jail>                            # ваш адрес в списке
sudo /usr/sbin/nft list set inet f2b-table addr-set-<jail>    # и в наборе
# ожидается 000 и exit=7 (Connection refused): у nftables-multiport по умолчанию blocktype = reject,
# правило reject with icmp port-unreachable, отказ приходит мгновенно; exit=28 (таймаут) — только если
# blocktype = drop или ICMP отфильтрован по пути. Любой HTTP-код, включая 401, — бан не действует
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' https://<domain>/<path>; echo "exit=$?"
sudo fail2ban-client set <jail> unbanip <ваш адрес>
curl -s -o /dev/null -w '%{http_code}\n' https://<domain>/<path>   # снова 401
```

Так и было при реальной проверке: 10 отказов — адрес в джейле и в наборе, соединения нет, после
разбана снова `401`. Делать это с адреса, с которого не страшно на минуту потерять веб-доступ:
ssh бан не трогает. `127.0.0.1` в `ignoreip` уже стоит — если адрес однажды не определится,
всех разом не забанит.

**Если fail2ban на сервере нет** — джейл сервиса не ставится, и установка обязана сказать об
этом вслух («fail2ban не установлен — джейл пропущен»), а не выйти нулём.

## Шаг 4. Секреты: где их не должно быть

### 4.1 Облачная папка

Токены, `.credentials.json`, ключи, `.env` в OneDrive/Dropbox/iCloud — это копия секрета у
третьей стороны плюс история версий. **Удаление файла из облака — половина дела.** Пока не
вычищены **корзина и история версий** (только в веб-интерфейсе провайдера), файл остаётся
доступен. Планируйте этот шаг руками.

### 4.2 История git

Проверьте не только рабочее дерево, но и историю:

```bash
git log --all --full-history --name-only | sort -u | grep -iE "\.env|credential|secret|\.pem|id_rsa|token"
git log --all --diff-filter=A --name-only --format= | sort -u | grep -E '^(<каталог данных>|<каталог рантайма>)/|\.env$'   # пусто
```

Во второй строке подставьте каталоги, которые ваш `.gitignore` держит вне репозитория как
рантайм-состояние: данные, сессии, БД, логи — все, сколько есть. В одной установке это `data/` и
`projects/`. Шаблон, оставленный как есть, не совпадёт ни с чем, и «пусто» пройдёт зелёным, ничего
не проверив.

Нашли ключ, токен или пароль — секрет считается скомпрометированным: сначала отзовите и
перевыпустите, потом чистите историю. Обратный порядок бесполезен. Найденный идентификатор
(адрес, логин, chat_id) — другой случай, см. 4.3.

**Защита должна быть механической, а не дисциплиной:** `.gitignore` + **белый список** того,
что вообще разрешено выпускать наружу, + тест, который падает на попытке добавить остальное.
Чёрный список всегда отстаёт от фантазии.

### 4.3 Документация и дефолты скриптов

Аудит перед первой публикацией репозитория шёл с четырёх углов (рабочее дерево, все коммиты с
недостижимыми блобами, полнота `.gitignore`, документация) и дал ноль блокеров. И при этом
реальные установочные значения нашлись — в базе знаний: идентификатор чата оператора «как пример
серверного конфига», публичный IP сервера в разборе про DNS, полные ssh-координаты боевого
сервера **дефолтами** в скриптах установки. Гигиена секретов строится вокруг конфига и рантайма
(схема, плейсхолдер, тест) и в `docs/` не смотрит; а разбор инцидента пишут по факту, и «пример
из жизни» там — копипаст рабочего файла, «для достоверности».

Правило: установочно-специфичное значение — chat_id, IP, логин, домен, путь на сервере — в тексте
документации маскируется так же, как в конфиге. Достоверность разбору даёт контекст («у сервера в
этом поле **своё** значение»), а не цифра. Дефолты скриптов установки не содержат боевых адресов:
адрес приходит аргументом или переменной окружения.

Проверка — поиском, а не чтением, и по истории, а не только по рабочему дереву:

```bash
git grep -nIiE "<ваш IP>|<домен>|<логин>|<chat_id>" -- docs config infra   # только плейсхолдеры
git log --oneline -S'<значение>' --all          # когда появилось и в скольких коммитах живёт
```

Настоящее значение отличается от синтетического (`<заполнит оператор>`, `123456789`) тем, что
стоит в одном блоке с другими реальными координатами установки.

**Окно бесплатной правки закрывается первым пушем.** Пока коммит не ушёл на удалёнку, значение
убирается `amend`'ом без следа; после пуша оно лежит на серверах хостинга, и `--force` его оттуда
не убирает — приватность репозитория становится единственной защитой. Аудит гоняется **до**
первой публикации.

Идентификатор — chat_id, IP, домен, логин, путь — не ключ: отзывать и перевыпускать нечего, а
переписывать уже отправленную историю ради него нельзя — с серверов хостинга он не исчезнет, а
общая история сломается. Замаскировать в рабочем дереве, а в отчёте назвать, что значение осталось
в истории. Так и было в реальном случае: идентификатор чата, найденный после публикации, оставлен,
история не тронута — репозиторий приватный, а без токена бота идентификатор доступа не даёт.
Менять ли сам идентификатор (другой логин, другой адрес) — решение владельца, не агента:
например, логин при оставленном парольном входе в публичном репозитории. Отзыв и перевыпуск —
только для ключей, токенов и паролей.

### 4.4 Логи запросов

После обычного входа в панель и смены пароля в файле журнала лежали открытым текстом пароль из
тела запроса, токен сессии из `Set-Cookie` и он же в `cookies`, логин, почта, внутренний id
учётки — при дефолтном уровне `info`, без отладочного режима. Две страховки не сработали:
**редакция по имени ключа** ловила `password`, но не `currentPassword` и `newPassword`
(сравнение на полное совпадение); **сериализаторы на дочернем логгере** в изоляции работают, а во
фреймворке нет — строку запроса пишет логгер, который фреймворк создаёт сам под каждый запрос, а
переданный готовый инстанс обходит объект запроса целиком: `cookies`, разобранное тело, `raw`.

Решение — не спорить с внутренностями фреймворка, а забрать логирование запросов себе: выключить
встроенное и в хуке ответа писать только метод, путь **без строки запроса**, код ответа и
длительность. Редакция ловит составные имена по **суффиксу**, а не по подстроке: `newPassword`,
`workerToken`, `taskSecret` режутся, а счётчики `inputTokens` остаются числами — подстрочное
правило испортило бы метрики.

Проверка — живой прогон, а не чтение кода, и ни одно значение не выводится в сессию.
Транскрипт агента — тоже хранилище (4.5): `cat <jar>`, `curl -i`/`-v`/`-D`, `echo "$TOKEN"` здесь
под тем же запретом, что и `cat` токена. Пароли и кука живут только в файлах временного каталога,
в командах — только пути и коды ответа:

```bash
umask 077; d=$(mktemp -d)
gen() { head -c 24 /dev/urandom | od -An -tx1 | tr -d ' \n'; }     # одна строка, без перевода строки
gen > "$d/pw"; gen > "$d/marker"
printf '{"login":"<тест-логин>","password":"%s"}' "$(cat "$d/pw")" > "$d/login.json"
printf '{"currentPassword":"%s","newPassword":"%s"}' "$(cat "$d/pw")" "$(cat "$d/marker")" > "$d/change.json"
# создать учётку <тест-логин> с паролем из "$d/pw" своим API/CLI — тем же способом: тело из файла, не из argv
curl -s -o /dev/null -w '%{http_code}\n' -c "$d/jar" -H 'Content-Type: application/json' --data @"$d/login.json"  https://<domain>/<login>      # 200
curl -s -o /dev/null -w '%{http_code}\n' -b "$d/jar" -c "$d/jar" -H 'Content-Type: application/json' --data @"$d/change.json" https://<domain>/<password>   # 200
awk -F'\t' 'NF==7' "$d/jar" | wc -l                              # ≥1 — кука получена; иначе нули ниже ничего не доказывают
awk -F'\t' 'NF==7 {print $7}' "$d/jar" | grep -cF -f - <лог>     # 0 — токен куки
grep -cF -f "$d/pw" <лог>                                        # 0 — временный пароль
grep -cF -f "$d/marker" <лог>                                    # 0 — маркер
grep -cE '"(body|headers|cookies)"' <лог>                        # 0 — этих ключей в файле быть не должно вовсе
curl -s -o /dev/null -b "$d/jar" -X POST https://<domain>/<logout>; <удалить тестовую учётку своим API/CLI>; rm -rf "$d"
```

Три ловушки, из-за которых проверка врёт, если её упростить:

- jar разбирается только `awk -F'\t' 'NF==7'`: строки-комментарии libcurl дают пустые паттерны, а
  пустой паттерн у `grep -f` совпадает с каждой строкой — счёт станет равен длине лога;
  `grep -v '^#'` не замена — HttpOnly-кука лежит строкой `#HttpOnly_…`, и это как раз сессионная
- файлы-паттерны — ровно одна строка без пустых: пустая строка в конце — снова «совпало всё»
- `grep -f` с пустым файлом молчит (нет вывода, rc=1), поэтому коды `200` и счёт кук идут до
  grep'ов: провалившийся логин иначе выглядит как пройденная проверка

После прогона: сессия закрыта, тестовая учётка удалена, каталог снесён — `shred` не нужен, угроза
здесь транскрипт, а не диск, и на macOS его нет.

Обещание в комментарии («секреты не попадают на диск») не стоит ничего без прогона: тесты были
зелёные, документация утверждала обратное, секреты лежали в файле.

### 4.5 Транскрипты агента

Если вы работаете с сервером через агента, его транскрипт — тоже хранилище. У нас транскрипт
сессии уезжает в git и в зеркало; токен, показанный в сессии однажды, оказался бы в истории git
навсегда. Поэтому **токен никогда не печатается**: скрипт установки создаёт его один раз и не
выводит, а клиенту он передаётся командой, не копированием в чат. `cat <path-to-token>`,
`echo "$TOKEN"`, `curl -v` с заголовком авторизации в сессии агента — под запретом: их вывод и
есть утечка.

Пароль — такой же секрет. `sudo -S`, `echo '<пароль>' | sudo`, `sshpass`, askpass с паролем в
переменной — под запретом: пароль в команде = пароль в транскрипте. Пароль у владельца в сессии не
спрашивать: его сообщение — тоже транскрипт. Прислан в чат — считается скомпрометированным, менять.

```bash
umask 077; head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n' > <path-to-token>   # 256 бит, файл 600
# Один блок: шелл агента не хранит переменные между вызовами. cat — как пользователь входа,
# sudo -n — только если файл принадлежит пользователю сервиса. Пустое значение дальше не идёт.
t=$(ssh -n <host> 'cat <path-to-token> 2>/dev/null || sudo -n cat <path-to-token>') \
  && [ -n "$t" ] || { echo "токен не прочитан" >&2; exit 1; }
<client> --token "$t"                                                  # передача без показа
printf '%s\n' "$t" | grep -rlF -f /dev/stdin <каталог транскриптов>   # проверка: пусто; паттерн не в argv
```

Не проверять формой `ssh … | grep -f /dev/stdin` без сторожа: при отказе ssh список паттернов
пуст, и GNU/BSD grep молча отвечает «чисто», а ugrep (им харнес Claude Code подменяет `grep`) —
«найдено во всех файлах». Оба ответа ложные; паттерн берётся только из проверенной `$t`. Argv
клиента при этом не закрыт: реальный клиент (`claude mcp add --header …`) файл не принимает, и
`"$t"` в его argv остаётся на секунды — это осознанно; у сервиса токен из файла (5.2), у клиента —
из переменной.

Нашёлся в транскрипте или в сторе, куда транскрипты уезжают, — токен скомпрометирован,
перевыпустить.

## Шаг 5. Сервисы: изоляция, токен из файла, атомарная замена, повторяемая установка

### 5.1 Слушать только loopback, наружу — один путь

Сервис слушает `127.0.0.1:<port>`; наружу его выпускает прокси с TLS, и только по одному пути.
Всё остальное — `404`, чтобы наружу не торчало ничего, чего вы не называли. Caddy (nginx — та
же форма: точный `location` на один путь и `return 404` на всё остальное):

```
<domain> {
	handle /<path> {
		reverse_proxy 127.0.0.1:<port>
	}
	handle {
		respond 404
	}
}
```

Проверка — снаружи, каждым кодом по отдельности. Токен в этих командах — только переменной,
заполненной командой (блок чтения со сторожем из 4.5), никогда литералом: транскрипт агента
уезжает в git (шаг 4.5).

```bash
sudo ss -tulnp | grep <port>                 # только 127.0.0.1, не 0.0.0.0 и не [::]
c() { curl -s -o /dev/null -w '%{http_code}\n' "$@"; }
t=$(ssh -n <host> 'cat <path-to-token> 2>/dev/null || sudo -n cat <path-to-token>') && [ -n "$t" ] || exit 1   # токен в переменной, в вывод не попадает; тот же блок, что в 4.5, в том же вызове
c https://<domain>/<path>                                                   # 401 — без токена
c -H "Authorization: Bearer wrong" https://<domain>/<path>                  # 401 — с чужим
c -H "Authorization: Bearer $t" -X POST ...                                 # 200 — со своим, вызовом без побочного эффекта
c -H "Origin: https://evil.example" -H "Authorization: Bearer $t" -X POST ...   # 403 — браузеру здесь делать нечего: отличие от строки 200 только в Origin
c -X GET https://<domain>/<path>                                            # 405 — если сервис только POST
c https://<domain>/anything-else                                            # 404
echo | openssl s_client -connect <domain>:443 2>/dev/null | openssl x509 -noout -dates   # срок сертификата
```

**Тело запроса на `200` — только чтение:** рукопожатие, `health`, поиск. Это единственная строка,
где живой сервис получает настоящий токен, и пишущий вызов оставит тестовую запись в боевых
данных. Так и проверялось: на живом сервере — рукопожатие и поиск; запись — отдельно, в
проекте-пробнике (тестовая сущность, которую не жалко), с удалением после и проверкой, что
удаление дошло на все стороны — именно на этом удалении нашлись два дефекта.

**Если прокси нет** — сервис слушает публичный адрес сам, и тогда TLS и все коды выше — его
обязанность; `ss -tulnp` покажет, что кроме него и ssh наружу ничего не смотрит — ни по TCP, ни
по UDP.

**Если сервис не HTTP** (UDP, VPN, свой протокол) — коды и TLS не проверяются, шаг пропускается
вслух; вместо них проверяется, что в `sudo ss -tulnp` наружу смотрят только он и ssh, а доступ
ограничен ключами протокола, не адресом. Для WireGuard: `sudo wg show <iface> peers` совпадает со
списком выданных вами публичных ключей — лишних peer нет; `sudo wg show <iface> latest-handshakes`
— рукопожатия только от своих пиров.

**Если сервис публичный и без токена** (статика, раздача сборок и обновлений) — `401`, `403` по
`Origin` и `405` на `GET` не проверяются: отдавать их некому, и навешивать авторизацию на
публичную раздачу не нужно. Проверяется другое: наружу отдаётся ровно то, что выкладывали, а по
HTTP нельзя ни перечислить каталог, ни записать в него.

```bash
sudo ss -tulnp                                                     # наружу только 80/443 (и UDP 443 при HTTP/3) и ssh
c https://<domain>/<ожидаемый файл>                                # 200 — только на ожидаемых путях
c https://<domain>/                                                # 200, если корень — страница; иначе 403/404
c https://<domain>/<каталог без индекса>/                          # 403/404 — не HTML-список файлов
curl -s https://<domain>/<каталог без индекса>/ | grep -ci 'index of\|<a href'   # 0
c https://<domain>/anything-else                                   # 404
c -X PUT https://<domain>/probe                                    # 405 — записи по HTTP нет
sudo stat -c '%U %a' <каталог артефактов>                          # владелец — пользователь деплоя, 755
sudo -u <пользователь прокси> touch <каталог артефактов>/probe     # Permission denied — у прокси записи нет
echo | openssl s_client -connect <domain>:443 2>/dev/null | openssl x509 -noout -dates   # срок сертификата
```

Листинг выключен явно: nginx — `autoindex` отсутствует или `autoindex off`; Caddy — `file_server`
без `browse`. Каталог артефактов принадлежит пользователю деплоя; у пользователя прокси (`www-data`
у nginx, `caddy` у Caddy) — только чтение, и проверяется это следствием — отказом на запись от его
имени, а не одним `stat`. Каталог с индексной страницей отдаёт её (`200`), каталог без индекса —
`403`/`404`; HTML-список файлов недопустим в обоих случаях.

### 5.2 Токен — из файла, не из аргументов

Аргументы командной строки видны в списке процессов любому пользователю машины. Токен передаётся
путём к файлу (`--token-file <path>`), файл — `600`, владелец — пользователь сервиса.

```bash
ps -o args= -p "$(systemctl show -p MainPID --value <service>)"   # токена в строке нет
sudo stat -c '%a %U' <path-to-token>                              # 600 <user>
```

### 5.3 systemd-изоляция

Юнит сервиса, который работает от обычного пользователя и пишет только в свой каталог данных;
`ProtectSystem=strict` делает всю файловую систему только для чтения, кроме `ReadWritePaths`:

```ini
[Service]
User=<user>
ExecStart=<bin> --token-file <path-to-token> ...
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ReadWritePaths=<каталог данных>
```

```bash
systemctl show <service> -p User -p ProtectSystem -p NoNewPrivileges -p ReadWritePaths
systemctl is-active <service>
sudo journalctl -u <service> --since "10 min ago" | grep -ciE "read-only|permission denied"   # 0
```

### 5.4 Бинарь заменяется атомарно, а не переписывается

Перезапись работающего бинаря командой `cp` — ошибка на любой системе, но проявляется она
по-разному. Замер сделан на macOS с подписанным Mach-O: файл, скопированный **поверх** уже
запускавшегося, при следующем запуске умирает с кодом **137, SIGKILL**, без единого байта на
stdout и stderr, а `codesign --verify` при этом отвечает `valid on disk`. На Linux этот замер не
воспроизводится, и воспроизводить его на сервере не нужно: `cp` поверх **работающего** бинаря
отвечает `ETXTBSY` («Text file busy») — деплой падает, а не убивает сервис; `cp -f` и `install`
снимают старое имя и создают новый inode, но не дают проверить файл до подмены; поверх **не
запущенного** файла `cp` проходит молча с кодом 0 (проверено на Debian 12: три
`cp … && ./probe --version` подряд — 0, 0, 0). Рвёт процесс на ходу Linux только при записи
поверх подгруженной им библиотеки (`.so`): их ядро не защищает. Правило одно для обеих систем:
новый файл рядом → проверка запуском → `mv`. Иначе на Linux systemd может перезапустить сервис на
полускопированном файле, а на macOS — на файле, который ядро больше не запустит.

Опасно на Linux окно перезапуска (`Restart=on-failure`, `systemctl restart`, падение): в этот
момент процесса нет, `cp` проходит, и недописанный файл — то, что запускает systemd. «Проверять»
`ETXTBSY` командой `cp` на пути сервиса нельзя по той же причине: в окно перезапуска копия
пройдёт. Увидеть его безопасно — во временном месте, не на пути сервиса:

```bash
cp /bin/sleep /tmp/probe && /tmp/probe 60 &   # запущенная копия
sleep 1; cp /bin/sleep /tmp/probe            # cp: cannot create regular file '/tmp/probe': Text file busy
```

Порядок замены — новый файл рядом, проверка запуском, переименование, и только потом перезапуск.
Полускопированный бинарь так никогда не окажется тем, что запускает systemd, а работающий сервис
до переименования держит старый файл:

```bash
scp <bin> <host>:<path>.new
ssh <host> 'chmod 755 <path>.new && <path>.new --version && mv -f <path>.new <path> && <path> --version'
ssh <host> 'sudo systemctl restart <service> && systemctl is-active <service>'
```

### 5.5 Установка идемпотентна и повторяема

Первый прогон реального скрипта установки упал на `apt-get install`: `dpkg` держали
автообновления. Скрипт был идемпотентным — повтор прошёл. Поэтому установка пишется так, чтобы
её можно было запустить второй раз без вреда: токен создаётся один раз
(`[ -s <path-to-token> ] ||`) и никогда не печатается; конфиг прокси, юнит, фильтр и джейл
переписываются **только если текст отличается**, и только тогда делается `reload`; бинарь
заменяется переименованием и проверяется запуском; если компонента нет (fail2ban), шаг
пропускается **вслух**, а не выходит нулём.

Проверка — запустить дважды и сравнить время изменения конфигов:

```bash
sudo stat -c '%Y %n' /etc/systemd/system/<service>.service /etc/fail2ban/jail.d/<jail>.local <конфиг прокси>
./install.sh ...      # второй прогон проходит
sudo stat -c '%Y %n' /etc/systemd/system/<service>.service /etc/fail2ban/jail.d/<jail>.local <конфиг прокси>   # те же числа
```

## Шаг 6. Диск и молчаливые отказы

Диск сервера переполнился, и синхронизация стояла сутки молча: последний push дошёл до хоста в
15:28, к утру на клиенте накопился 291 неотправленный коммит, а клиент показывал
`consecutiveFailures: 0` и зелёную диагностику. Три причины, одна за другой:

1. **Входящие push распаковывались в отдельные объекты.** `transfer.unpackLimit` по умолчанию
   100: push меньше ста объектов ложится отдельными файлами без дельт, и растущий файл до 19 МиБ
   писался целиком каждой версией — 4,75 ГиБ отдельных объектов при 608 МиБ в пакетах.
2. **Порог ради памяти выключил сжатие.** `core.bigFileThreshold=8m`, поставленный при первой
   настройке «для экономии памяти», запрещает дельты для объектов больше 8 МиБ — ровно для тех
   файлов, из которых хранилище состоит. Еженедельный `gc` упал на полном диске, ручной `repack`
   с 2,6 ГиБ свободного места дописал пакет до 1,4 ГиБ и не закончил бы; те же 11 882 объекта с
   порогом по умолчанию упаковались в **135,6 МиБ за 24 секунды**.
3. **Отказ push не считался провалом.** Функция возвращала `bool`; отказ удалённой стороны был
   неотличим от «нечего отправлять» и не попадал в список проблем. Сломанное выглядело
   работающим.

Что изменено, чтобы не повторилось, — и что проверить у себя:

- **Место на диске проверяется автоматически**, а не обзором перед другой задачей: диагностика
  показывает строку `disk` и падает ниже **1 ГиБ или 10 %**; ежедневная проверка оставляет
  предупреждение там, где его увидят. Команда: `df --output=avail,pcent /`.
- **Отказ внешней операции — провал, а не молчание.** Push, `apt-get`, `curl` к чужому API,
  бэкап — каждый возвращает результат, и «удалённая сторона отказала» отличается от «нечего
  делать» по типу, а не по флагу. Найдите в своём коде места, где результат внешней операции
  превращается в `bool` или игнорируется; прогоните с намеренно недоступным адресом и убедитесь,
  что отчёт красный — с сообщением удалённой стороны и back-off, — а не зелёный.
- **Если сервер принимает git push** (бэкапы, стор, зеркало):
  ```bash
  git -C <repo.git> config transfer.unpackLimit    # 1 — входящий push остаётся пакетом с дельтами отправителя
  git -C <repo.git> config core.bigFileThreshold   # пусто: порог выключает дельты для больших файлов
  git -C <repo.git> count-objects -vH              # count (отдельные объекты) — 0 после упаковки
  crontab -l | grep ' gc '                                                 # от владельца репозитория (или sudo crontab -u <user> -l): строка ночной упаковки есть, одна
  ls -lS --time-style=long-iso <repo.git>/objects/pack/*.pack | head -1    # самый большой пакет датирован временем ночной упаковки, не прошлой неделей
  ls <repo.git>/objects/pack/tmp_pack_* 2>/dev/null                        # пусто: недописанных пакетов нет
  git -C <repo.git> count-objects -v | grep -E '^(count|garbage)'          # 0 и 0: garbage — это и есть чужие файлы в objects/pack
  ```
  Не `ls -lt | head`: при `unpackLimit=1` каждый push кладёт свой пакет, и сверху окажутся
  сегодняшние push, а не продукт упаковки. По journal ночная упаковка не проверяется: cron логирует
  только старт команды, а её вывод в нашей строке уходит в `/dev/null`. Если след в journal нужен —
  направить вывод через `2>&1 | logger -t store-gc` и смотреть `journalctl -t store-gc`; без этого
  grep по journal не значит ничего.
  Упаковка — каждую ночь, а не раз в неделю; строка прежнего планировщика заменяется, а не
  остаётся рядом.
- **Если git на сервере нет** — пункт про `unpackLimit` пропускается, но `df` и правило про
  отказ остаются: они про любой растущий каталог и любую внешнюю операцию.

Что дало место, когда его не было: мусор упавших операций (карантины входящих push, недописанные
пакеты), `journalctl --vacuum-size`, `apt-get clean` — около 500 МиБ; пакет с дельтами собран на
другой машине, проверен `git verify-pack`, перенесён `rsync --partial` (`.pack` первым, `.idx`
последним — git не видит пакет без индекса), на хосте `git prune-packed`, итог сверен
`git rev-list --objects --all --missing=print`: ноль недостающих.

Правило шире git: **порог, поставленный ради памяти машины, меняет не только память.**

## Шаг 7. Отчитаться честно

В отчёте о каждом пункте: **что проверено и чем**. Разделяйте «настроено» и «проверено, что
работает» — это разные утверждения, и второе стоит первого. Если проверка невозможна, так и
напишите, вместо того чтобы повышать статус. Пропущенный шаг называется пропущенным, с причиной
(«прокси нет — проверено `ss -tulnp`, что сервис сам слушает только TLS-порт»). Цифры — из вывода
команд, не по памяти. Найденная при перечитке отчёта ошибка исправляется до отправки, а не
оговоркой после.
