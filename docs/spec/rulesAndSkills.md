## 2. Модель: четыре уровня

| Уровень | Чьё | Где канон | Кто видит |
|---|---|---|---|
| **Личные** | человек | личный стор: `rules/`, навыки — `config/skills/` | все его агенты на всех его машинах |
| **Командные** | команда | стор команды: `rules/`, `skills/` | все участники команды |
| **Проектные** | проект | стор, где лежит проект: `projects/<проект>/rules/`, `projects/<проект>/skills/` | все, у кого проект в сторе |
| **Местные** | репозиторий | файлы в репозитории: `CLAUDE.md`, `AGENTS.md`, `.vibe/rules/`, `.cursor/rules/` | все, кто клонировал код |

Местный уровень — не наш: его пишут люди и чужие инструменты, движок его только сравнивает с каноном (раздел 6).

**Правило — запись, а не кусок монолита.** Один файл — одно правило с шапкой:

```markdown
---
id: commit-attribution          # постоянное имя: по нему сравнение, перекрытие и история
title: Атрибуция в коммитах — абсолютный запрет
level: personal                 # personal | team | project
absolute: true                  # нижний уровень не перекрывает
paths: []                       # пусто — всегда; иначе только при работе с этими файлами
---
<текст правила>
```

Версия правила — его история в git стора, а не дата в шапке.
Без постоянного `id` сравнивать можно только файл целиком. Именно так сейчас сходятся копии `CLAUDE.md`: две правки
порознь — конфликт всего файла.
Это пересматривает решение 07.10 «один `CLAUDE.md`, без дробления» — вопрос 1 раздела 12.

**Навык — пакет:** каталог `<name>/` с `SKILL.md`, `scripts/`, `references/`, как сейчас в `config/skills/`.
Уровни те же; личные навыки остаются в `config/skills/`, где уже лежат и синхронизируются.

## 3. Как правила и навыки доходят до агента

Движок раскладывает канон в те места, которые читает каждый агент. Каждая разложенная копия — управляемая: правка в
ней доезжает обратно до канона, правки порознь — конфликт с карантином. Механизм уже есть (`managed::Copy`), меняется
единица: правило, а не файл.

| Агент | Личные + командные | Проектные | Навыки |
|---|---|---|---|
| Claude Code | `~/.claude/rules/vm-<id>.md`, по файлу на правило; `paths` — как есть | `.claude/rules/vm-<id>.md` в проекте, путь в `.git/info/exclude` | `~/.claude/skills` (как сейчас) |
| DSH | `~/.dsh/AGENTS.md` — сборка с метками правил | `AGENTS.local.md` в корне проекта, путь в `.git/info/exclude` | `~/.agents/skills` |
| Codex | `~/.codex/AGENTS.md` — сборка | `AGENTS.override.md`: `AGENTS.md` проекта как база и правила | `~/.codex/skills`; в проекте `.agents/skills` |
| Любой MCP-агент | `instructions` в `initialize`: короткий указатель и правила с `absolute`; `rules_get` | `rules_get` с проектом | resources `vibememory://skills/<name>` |

**Сборка с метками** — для агентов, у которых правила одним файлом. Каждое правило обёрнуто:

```markdown
<!-- vibememory:rule commit-attribution@3f9a2c -->
…текст…
<!-- /vibememory:rule -->
```

По метке правка в собранном файле находит своё правило, и сравнение остаётся построчным для одного правила, а не для
всех ста пятидесяти строк.

Проектные правила кладутся в файлы, которые git проекта не видит: репозиторий не засоряется, а чужие участники без
VibeMemory ничего не получают и ничего не теряют.

Навыки из `synced/` — это то, что Claude сам синхронизирует с claude.ai: другим агентам они не раскладываются.

## 4. Как правило записывается

**Уровень называет человек — словами:**

| Человек говорит | Уровень |
|---|---|
| «в общие правила», «в глобальные» | личные |
| «в правила команды» | командные этой команды |
| «в правило проекта», «для этого проекта» | проектные |
| «сохрани в правило», «запомни как правило» — без уровня | **агент спрашивает:** глобальное, командное или проектное |

**Спрашивать обязан не только текст подсказки, но и сервер.** Инструмент `rule_save(text, level, project?, id?)` без
`level` отвечает отказом `levelRequired` с вариантами. Агент, который забыл спросить, получает отказ, а не молча
записанное правило не того уровня. То же — `skill_save`.

Перед записью сервер ищет **похожие правила** на всех уровнях: одинаковый `id`, близкий заголовок, сильно
пересекающийся текст. Найдено — ответ `similarFound` с кандидатами и вопросом: дополнить существующее, заменить или
завести новое. Так «запомни правило про коммиты» не порождает пятое правило про коммиты.

Новое правило агент формулирует в стиле глобальных правил: одна мысль на строку, что делать и почему.

Те же действия — командами: `vibememory rule add|list|show|history|remove|move|accept`, `vibememory skill list`.
Правка — тот же `rule add` с тем же `id` (он заменяет правило) или правка между метками в файле любого агента.
`move` переносит правило между уровнями, например из проектного в личное, когда оно оказалось общим.

## 5. Порядок и перекрытие

Действующие правила проекта собираются снизу вверх: **личные → командные → проектные → местные**.
Правило с тем же `id` на уровне выше перекрывает нижнее.

Два исключения:
- **`absolute` личного уровня** не перекрывается ничем: атрибуция, секреты
- **`enforced` командного уровня** — правило, которое ставит владелец или админ команды; его не перекрывают проектные и
  местные правила участника

Если `absolute` человека и `enforced` команды противоречат друг другу, движок не выбирает: `doctor` и `rules status`
называют пару, а агент получает обе с пометкой о конфликте. Вопрос 3 раздела 12.

## 6. Сравнение с тем, что уже лежит в проекте

`vibememory rules sync [каталог]` и тот же разбор в `doctor`: движок читает местные правила проекта (`CLAUDE.md`,
`AGENTS.md`, `.claude/rules/`, `.vibe/rules/`, `.cursor/rules/`), режет их на блоки по заголовкам и метками и сравнивает
каждый блок с каноном.

**Как блок находит своё правило:**
- по метке `vibememory:rule` — точно
- без метки — по заголовку и сходству текста; соответствие предлагается человеку один раз и потом записывается

**Состояния и что движок предлагает:**

| Состояние | Как определяется | Предложение |
|---|---|---|
| **Дубль** | текст совпадает с действующей версией правила | убрать из проекта: агент получит его из сервиса |
| **Устарел** | текст совпадает с одной из прошлых версий правила (история в git стора) | заменить на действующую |
| **Свой вариант** | расходится со всеми версиями, но вырос из одной из них | слить: изменения сервиса поверх своего, по-строчно; конфликт строк — вопрос человеку |
| **Только в проекте** | соответствия нет | оставить местным или поднять в сервис — проектным, командным, личным |
| **Только в сервисе** | местного блока нет | ничего: агент получит правило раскладкой |

«Устарел» отличается от «своего варианта» историей: в git стора есть все версии каждого правила, и хеш местного текста
либо есть среди них, либо нет. Догадок о том, что новее, нет. Часы машин не сравниваются — правило движка «никогда не
полагаться на монотонность timestamp».

**Режим проекта** — одна настройка на проект, `rulesMode` в его записи:

| Режим | Что делает движок |
|---|---|
| `advise` — **по умолчанию** | показывает разбор и предлагает действия; ничего не меняет без «да» |
| `merge` | сам убирает дубли и обновляет устаревшее и чисто слившееся; конфликты — человеку |
| `override` | кладёт правило в силе поверх каждого совпавшего блока; версия проекта — в карантин |

Блоки «только в проекте» не трогаются ни в одном режиме. `merge` и `override` включает человек, по проекту: это
его согласие на правку файлов проекта движком; уточнено при реализации 07.10 — первоначальное «override перекрывает
в сборке» не давало проекту единой картины.

Предложения доходят до человека тремя путями:
- `vibememory rules sync` — построчно, с ответом на каждый пункт
- `doctor` — строкой «в проекте N правил: 3 дубля, 1 устарело»
- `SessionStart` — раз в сутки, как сейчас про агентов без регистрации

## 7. Навыки — то же самое

- **Канон:** `skills/<name>/` в личном, командном сторе и сторе проекта
- **Раскладка:** `~/.agents/skills` (DSH и те, кто знает общий корень), `~/.claude/skills`, `~/.codex/skills`; проектные
  — `.agents/skills` проекта под `.git/info/exclude`
- **Запись:** `skill_save` с обязательным уровнем; «сохрани как навык» без уровня — вопрос
- **Проверка формата при записи:** имя в kebab-case, `description` обязателен, размер `SKILL.md`. Навык, который DSH
  отбросит с предупреждением, не записывается — вместо этого называется причина
- **Сравнение:** по имени навыка и хешу всего пакета; состояния те же, что у правил. Слияние — по файлам пакета
- **Совместимость полей:** поля, которые понимает только Claude (`allowed-tools`, `hooks`, `context`), остаются в файле;
  `rules status` говорит, какие агенты их проигнорируют

## 8. Безопасность

Правило — это инструкция, которую агент исполняет. Командные правила — способ одному участнику управлять агентами
всех остальных.

- **Писать командные правила и навыки** могут владелец и админы команды. Это проверяет хост на приёме push, по
  снимку прав, как сейчас проверяются пути. Участник предлагает правило, админ принимает
- **Новое командное правило на машине** раскладывается после первого показа: `SessionStart` и `rules status` называют,
  что пришло и от кого. `enforced` без показа не действует
- **Токены и секреты** в правиле и навыке не уезжают с машины: та же проверка, что у управляемых копий
- **Скрипты навыков** (`scripts/`) от команды помечаются отдельно: исполняемый код — не текст

## 9. Бюджет: правила короткие, процедуры — навыки

Правило всегда в контексте, навык — по запросу. Сейчас глобальный `CLAUDE.md` весит 51,5 КБ, и в нём есть процедуры:
как собирать `.dmg`, как поднимать start0. Это навыки.

- `rules lint` называет правила длиннее порога (по умолчанию 2 КБ) и предлагает вынести процедуру в навык, оставив в
  правиле одну строку-указатель
- `paths` у правила — загрузка только при работе с этими файлами там, где агент это умеет (Claude Code); остальным
  правило идёт всегда
- Сборка для агента считает свой бюджет: для DSH — по `agent-instructions`, и превышение называется в `doctor` до того,
  как DSH молча выбросит глобальный файл

## 10. Переход

1. **Глобальный `CLAUDE.md` режется на правила** по разделам `##`. Движок предлагает разрезку, владелец смотрит и
   принимает; `id` — из заголовка. Сам `~/.claude/CLAUDE.md` после этого — короткий файл владельца без раскладываемого
   содержимого, а правила лежат в `~/.claude/rules/`
2. **Процедуры** из раздела 9 предлагаются в навыки
3. **Проекты с ручными копиями**, например `.vibe/rules/` VibeSnipe, получают разбор раздела 6
4. **Воспоминания типа `feedback`** в памяти проектов — это правила, выученные на поправках. `rules sync` показывает их
   отдельным списком и предлагает поднять в правила проекта. Сами записи памяти остаются

## 11. Что из современного здесь использовано

- **`AGENTS.md`** — общий стандарт файла инструкций, его читают DSH, Codex и Claude Code
- **Agent Skills, `SKILL.md`** — один формат навыка на всех агентов, с прогрессивным раскрытием: в контексте только
  каталог, тело — по запросу
- **Общий корень `~/.agents/`** для агентов, которые его знают
- **Правила с областью действия** (`paths`) — грузятся только там, где нужны
- **MCP:** `instructions` при знакомстве, инструменты записи с проверкой на сервере, resources для навыков — для агентов
  без своих файлов правил
- **Правила как код:** каждое правило — файл с историей в git, сравнение по версиям, а не по датам, и линтер

## 13. План реализации

Одним выпуском, по шагам; каждый шаг — свой коммит с тестами.

**Переходное:** пока глобальный `CLAUDE.md` не разрезан, сборка для DSH и Codex начинается с его текста как с базового
блока — иначе 0.9.0 оставил бы DSH без правил, которые 0.8.0 уже дал. Блок остаётся и после разрезки: это короткий
файл владельца.

1. **Ядро:** формат правила и навыка, разбор и проверка; сборка действующих правил по уровням; сборка с метками и
   обратный разбор; состояния сравнения по истории версий; поиск похожих — чистая логика с фикстурами реального формата
2. **Стор:** `rules/` и `skills/` в личном, командном сторе и сторе проекта; проверка прав записи на хосте
3. **Раскладка:** правило как управляемая копия; файлы и сборки с метками для Claude Code, DSH, Codex; проектные файлы
   под `.git/info/exclude`
4. **Сервер памяти:** `rule_save`, `rule_get`, `rules_get`, `skill_save`, `skill_get` с обязательным уровнем и поиском
   похожих; `instructions`; resources навыков
5. **CLI:** `rule …`, `skill …`, `rules sync`, `rules status`, `rules lint`; разбор в `doctor` и `SessionStart`
6. **Переход:** разрезка глобального `CLAUDE.md`, перенос процедур в навыки, разбор VibeSnipe
7. **Стенд:** проверки `selfHostLab.sh check` на правила и навыки — команда, участник, второй агент
8. **Документы:** спека формата правила и навыка для модели в `docs/manuals/`, мануал «правила и навыки», каталог
   возможностей, knowledge
