## 1. Решения владельца

> **Тариф выбран 2026-09-20:** 2 vCPU, 4 ГБ RAM, 50 ГБ NVMe, 650 ₽/мес. План требовал «≥ 4 ГБ и ≥ 80 ГБ»;
> память совпадает, диск взят меньше осознанно. Посчитано по хосту: система и своп ≈ 4 ГБ, стор 1,11 ГиБ,
> свободными остаются ≈ 45 ГБ. Рост стора по трём ночам подряд (835 → 873 → 884 МиБ в пакетах) — около
> 25 МиБ в сутки при 200–400 коммитах в день: одному владельцу это ≈ 9 ГБ в год, втроём ≈ 27 ГБ.
> Значит диск — первый ресурс, который кончится, и следит за ним порог в `doctor`, отказ ночной упаковки
> без места и письмо владельцу. Следующая ступень (4 vCPU / 8 ГБ / 80 ГБ, 1100 ₽) берётся по этому письму,
> а не заранее.

   (в) Railway для кабинета и Postgres — отвергнуто: «данные на своём хосте», GitHub App только через UI, оплата из РФ без ИП не проверена, снимок прав пришлось бы возить по сети

    **Решение владельца 2026-09-20: (б) — новый VPS ≥ 4 ГБ / ≥ 80 ГБ, перенос имени, пользователя и пути стора.** Перенос входит в фазу 0 отдельным днём: старый репозиторий на время `rsync` переводится на чтение через `pre-receive`, `known_hosts` на машинах владельца обновляется руками, `connect --refresh` у участников появится только в фазе 3 — на момент переноса их ещё нет.

## 2. Целевая схема

### 2.1. Сущности кабинета (Prisma, Postgres)

Поверх моделей пака `User`, `Session`, `Account`, `Verification`; демо `Idea` удаляется
Секреты — только отпечатками, наружу — только короткие публичные id
**Правила имён исполняет только бинарь:** каждая мутация, меняющая снимок (проект, слаг команды, `handle`, `machine`/`storeName`, членство, токен, ключ, грант), внутри своей транзакции рендерит кандидат-снимок во временный файл и вызывает `vibememory-mcp access check` (2.4); код выхода ≠ 0 — транзакция откатывается, форма показывает код причины из первой строки stdout (`NamingError::code`); в TypeScript правил имён нет — дубликат разошёлся бы молча; сторож реконсилера (2.4) пользовательским вводом не запирается

- **User** — better-auth, вход **email + пароль** (`emailAndPassword`); Google остаётся плейсхолдером `__XXX__`, magic link не включается — почта участникам не нужна; `role: admin` только у владельца (вертикаль `adminPlugin` пака); регистрация закрыта: аккаунт создаётся погашением `AccessCode`, принятием приглашения или импортом снимка (владелец, см. 2.4); **`handle`** — слаг участника `[a-z0-9-]`, уникален на площадке, задаётся при первом входе, неизменяем (переименование молча переписало бы авторство); email в стор не попадает никогда
- **Organization / Member / Invitation** — плагин `organization` better-auth (в 1.6.28 есть, проверено по `node_modules` VibeSter), роли `owner | admin | member` — дефолтные; `slug` команды = имя каталога `teams/<slug>.git`; `owner` ровно один, снять его нельзя; ссылка приглашения показывается пригласившему, письмо не шлётся (решение 17); **удаление команды — мягкое:** `deletedAt`, строка и уникальный индекс по `slug` остаются навсегда — слаг не переиспользуется (3.2); **у `adopted`-организации (`personal`) ровно одно членство — владелец:** приглашение и добавление в неё отказывают («личный стор не делится — в нём транскрипты владельца»), расширение Prisma держит это ниже кода, `access check` отказывает снимку с двумя членами у `adopted`
- **Team** (расширение организации) — `mode: memory | sync`, `state: active | readOnly` (вычисляется из грантов), `limits {seats, maxRecords, maxRecordBytes, quotaBytes}`, `adopted` (стор существовал до кабинета — `personal`), `repoPath` только у `adopted`, **`projects: string[]`** — только у `memory`-команд: список ведёт кабинет (добавить / архивировать; имя — `StoreName::parse` ядра, уникальность в команде по `StoreName::key`: два имени, равные по NFC и регистру, на APFS и NTFS один каталог; исполнитель — `access check` на кандидат-снимке, выше) — в `memory` репозиторий пуст, и правило «запись не создаёт проект» иначе не выполнимо; у `sync` и `adopted` проекты приходят из `host.json`; **`restoredAt`, `restoreReason`** — только действием «принять сиротский каталог» (2.4)
- **AgentToken** — `id` (`tk_<tokenId>`, публичный), `memberId`, `agent` (слаг из списка + свой), `label`, `secretSha256`, `role: reader | writer`, `history: bool`, `projects: string[] | null` (null = все), `expiresAt`, `revokedAt`, `legacy: bool` (ровно одна строка на площадке, только `personal`)
  Порядок прав задан явно: `reader | writer` не зависит от ранга членства — `member` может держать `writer`; `history: true` — только у членств `owner | admin`; право `git-upload-pack` (экспорт) **в режиме `memory`** — только у членств `owner | admin`, в `sync` оно есть у каждого членства (участник обязан клонировать); расширение Prisma отказывает в создании токена с `history` у `member` и снимает `history` при понижении
- **MachineKey** — `id` (`mk_…`), `userId` (машина принадлежит человеку, команды выводятся из членств), `machine` (метка `[a-z0-9-]`), **`storeName`** = `<handle>-<machine>` — имя каталога `machines/<storeName>/` и префикс версий; **уникален на всей площадке** (индекс), а не только у человека: склейка через `-` неоднозначна (`a-b`+`c` = `a`+`b-c`), и без индекса два участника писали бы в один каталог; занятое имя — отказ «имя занято» при выпуске ключа; `publicKey`, `fingerprint`, `revokedAt`
- **ClaimCode** — `userId`, `purpose: key | token`, `teamId`, `agent | machine`, `codeSha256`, `expiresAt` (10 мин), `usedAt`; точка `POST /api/agent/claim` без сессии; все отказы неотличимы
- **AccessCode** (этап A) — `codeSha256`, `months`, `activations`, `seats`, `expiresAt`, `disabledAt`, `note`; правило заметки: без имён, сумм и дат переводов — «команда на троих, сентябрь», не «донат от N.» (подсказка в форме; `monetization.md` VibeSter запрещает связывать перевод и код); жжёт единственная redeem-транзакция
- **Grant** — `teamId`, `until` (месяц календарный, ≥ 30 дней, считается при активации), `seats`, `source: code | manual`, `reason` (обязательна), `createdBy`; `personal` вне квот безусловно
- **SnapshotPublication** — `hash`, `publishedAt`, **`teamCount`** (строк `Organization` в базе на момент публикации, с `deletedAt` и без; не строк снимка: удалённая команда уходит из снимка вместе с каталогом `.deleted-*`, а из базы — никогда) — **пишется и в сам `access.json`**, потому что сторож (2.4) читает его с хоста: после восстановления дампа таблица публикаций тоже из дампа, и база совпала бы сама с собой; `hostAck` из `host.json`
- **Release** — не сущность базы: страница «Скачать» читает `/srv/vibememory/releases/index.json` (пишет `hostRelease.sh`: `{"<версия>": {"<target>": {"archive", "sha256", "files": ["vibememory", "vibememory-mcp"]}}}` — состав архива перечислен, страница и `teamSetup.md` печатают его), кабинет к каталогу релизов только читает

Связи: `User 1—n Member n—1 Organization`; `Member 1—n AgentToken`; `User 1—n MachineKey`; `Organization 1—n Grant`

### 2.3. Токены и ключи

**HTTPS-токен per участник × агент** — `vmt_<tokenId>_<секрет>`: `tokenId` 8 символов base32 (публичный), секрет 32 байта CSPRNG; **`id` токена в снимке, аудите и имени версии — `tk_<tokenId>`** (`tk_7q2m9x4a`), легаси-строка — `tk_legacy`; префикс версии — `host-<id>`: `host-tk_7q2m9x4a`, `host-tk_legacy` — одна форма везде, `memoryRecordsSpec.md` называет её
- Кабинет хранит `sha256(секрет)`; сервер ищет грант по `tokenId` за O(1), сравнивает отпечаток за постоянное время (`same_secret` остаётся); отпечаток — `vibememory_cli::sha256::digest`, новых крейтов нет
- Значение без префикса `vmt_` — легаси: сервер сверяет `sha256` всей строки с единственной строкой `legacy: true` снимка тем же `same_secret`; `access check` отказывает снимку с двумя легаси-строками; снятие строки — фаза 4
- Агент, участник, команда, роль, `history`, область проектов, срок — в гранте; заголовок `VibeMemory-Agent` и `DEFAULT_AGENT = "http"` из HTTP-режима удаляются: **по HTTPS источник и личности, и агента — только токен**
- Одна точка `/mcp`, команда выводится из токена — ни слага в пути, ни 404-оракула; неизвестный, отозванный и просроченный токен отвечают одинаково `401` + `WWW-Authenticate`; строка журнала для неизвестного — прежняя (джейл fail2ban не меняется), для просроченного — другая, которую джейл не считает (знакомый клиент — не атака)
- Отзыв = отсутствие в снимке; ротация = новый токен и отзыв старого одной транзакцией кабинета и одной публикацией; рестарта нет: сервер перечитывает снимок по `(mtime, size, inode)` одним `stat` на запрос
- Кабинет лёг — действует последний снимок: новых прав не появится, отозванные не вернутся; снимка нет при старте — сервер не стартует; пропал на ходу — отказ всем и громкая строка (fail closed)
- **Выдача только claim-кодом:** мастер «Подключить агента» в кабинете выпускает `XXXX-XXXX-XXXX` (Crockford base32, 60 бит, 10 минут, одно погашение, в базе отпечаток) и показывает команду `vibememory connect --code … --cabinet https://vibememory.ru --agent claude-code`; **адрес кабинета — только из флага `--cabinet`** (в коде ни одного адреса, `roadmap.md:502-503`), `connect` записывает его в сайдкар `~/.vibememory/tokens/<team>/<agent>.json` (`{cabinet, team, tokenId, agent}`) — для токенов, и в `stores.<id>.cabinet` конфига — для ключей (2.7); оттуда его читают `doctor`, `disconnect`, `connect --refresh`; токен — `~/.vibememory/tokens/<team>/<agent>` (0600) и фрагмент конфигурации клиента рядом (0600), печатаются только пути и команда регистрации с `$(cat …)`; литерала нет ни в stdout, ни в чате, ни в UI; код в транскрипте безвреден — он сгорел

- Приватный ключ — `~/.vibememory/keys/<store-id>` (0600 / `icacls`), рядом `.pub` и `<store-id>.known_hosts` из ответа claim (решение 20); в `~/.ssh/config` `connect` пишет свой блок между маркерами `# vibememory <store-id> begin/end`: `Host vibememory-<store-id>`, `HostName vibememory.ru` (из ответа claim, не из кода), `User vmgit`, `IdentityFile <путь>`, `IdentitiesOnly yes`, `UserKnownHostsFile <путь>.known_hosts`, `StrictHostKeyChecking yes`, `BatchMode yes`; повторный `connect` перезаписывает только свой блок; алиас владельца `vibememory` из `seedKey.sh` не трогается; remote стора — `vibememory-<store-id>:teams/<slug>.git`

- Валидация материала до рендера: ровно одна строка, тип только `ssh-ed25519`, base64 декодируется в 32 байта, ни одного управляющего символа — иначе ключ пропускается с журналом, строка без `restrict` появиться не может

- `shell` выставляет `VIBEMEMORY_KEY=mk_<id>` для `pre-receive`

**Имя версии, `member` и счётчик** — `member` и префикс `uuid` называют **путь записи**, а не команду: любая запись по HTTPS — в `teams/*` и в `personal` одинаково — несёт префикс `host-<id токена>` (`host-tk_7q2m9x4a`, `host-tk_legacy`) и `member` из гранта (в `personal` это слаг владельца, решение 13); ssh-`mcp` — префикс `<storeName>`, `member` из ключа; движок и stdio-сервер участника в `sync`-сторе — `<storeName>` и `member` из `stores.<id>` конфига (не `machineId`: он у двух участников может совпасть); **без `member` остаются только движок владельца и его stdio по ssh (`--git-store`)** — префикс `machineId`, как сегодня; `written` стартует с `pid << 32` и общий на процесс — закрыты и коллизия двух ssh-процессов одной машины в одну секунду, и коллизия двух сторов в одном процессе

- **Порядок на хосте:** `hostCabinet.sh` выполняет миграции и `access:import` **до** `systemctl enable --now vibememory-cabinet`; юнит несёт `ExecStartPre=bun run access:seeded` (выход ≠ 0, если в базе нет владельца) — служба на пустой базе не стартует, а не публикует пустой снимок

- **Слаги, занятые каталогом на хосте:** обычное создание команды со слагом из `deleted[]` или `orphans[]` кабинет отвергает («слаг занят каталогом на хосте»); для `deleted[]` пути нет (2.1); для `orphans[]` — **действие владельца «принять сиротский каталог»**: только `role: admin`, слаг из `orphans[]`, режим предвыбран по признаку `machines`, `owner` — существующий пользователь (пропал с дампом — создаётся заново кодом-подарком), причина обязательна; создаёт `Organization`/`Team` с `restoredAt`, `restoreReason` и строкой журнала `team adopted <slug> by <handle>: <причина>`; следующая публикация ставит слаг в снимок без маркера, `access-apply` реаттачит каталог по правилу «слаг в снимке и каталог есть» (2.5); членств, токенов и ключей после дампа нет — участники приглашаются заново и делают `connect`, старые токены отвечают `401`

### 2.5. Изоляция команд

- Один голый репозиторий на команду `/srv/vibememory/teams/<slug>.git`, 2770 `vmgit:vibememory`, настройки из `infra/storeInit.sh <путь> [--adopted]` (единый источник для `hostBootstrap.sh` и `access-apply`; общая часть — `init --bare`, `autocrlf=false`, `filemode=false`, `gc.auto=0`, `transfer.unpackLimit=1`, `core.sharedRepository=group`, `pack.windowMemory`/`pack.threads=1` под RAM; без флага сверх неё — `receive.denyNonFastForwards`, `receive.denyDeletes`, `receive.maxInputSize=1g` и хук `pre-receive`; `--adopted` для `store.git` их не ставит: хук без правила для владельца отверг бы его push, а `maxInputSize` встретил бы тик владельца раньше порционного push фазы 5; коммитов скрипт не делает)
- **Первый коммит делает хост при создании репозитория:** `access-apply` после `storeInit.sh` кладёт единственный файл `.gitattributes` с текстом `install::GITATTRIBUTES` (байт в байт как в клоне) plumbing-командами `hash-object -w` → `mktree` → `commit-tree` без родителя → `update-ref refs/heads/main` — `pre-receive` при `update-ref` не запускается; без этого `append_once` не запишет ни одной записи, а тик участника без `origin/main` считает `ahead = 0` навсегда; `connect` для `sync` клонирует непустой репозиторий, первый push участника — обычный
- **Эволюция `.gitattributes` — тоже хост:** при каждом применении `access-apply` сверяет `.gitattributes` в `main` каждой команды из снимка без маркера (`cat-file` по `ls-tree`; `adopted` и сирот не трогает) с константой и при расхождении коммитит новый текст тем же plumbing-путём с родителем (`commit-tree -p`, `update-ref` со старым значением — compare-and-swap как у `append_once`); участники получают его fetch'ем; больше файл менять некому — `pre-receive` не пускает, `install` не переписывает (`install.rs:693-705`); фикстура: старый текст → после применения `main` несёт новый, история цела
- **Правила `access-apply` для каталога `teams/<slug>.git`:** слаг в снимке без маркера и каталог есть → настройки и хук применяются идемпотентно (так же реаттачится команда, принятая из `orphans[]`, 2.4); слаг в снимке, каталога нет и нет `teams/<slug>.deleted-*.git` → создать по правилу выше; есть `.deleted-*` того же слага → ничего не создавать, `problems[]: slug_retired`; маркер `deleted: <дата>` и каталог `teams/<slug>.git` → переименовать в `teams/<slug>.deleted-<дата>.git` (дата из снимка — повтор идемпотентен); слага нет в снимке → каталог не трогается, попадает в `orphans[]`; файлы не удаляются никогда
- **`pre-receive` — только `refs/heads/main`, остальное отказ:** хук читает все строки stdin; любая ссылка кроме `refs/heads/main` — ветка, тег, заметка — отвечает `ref_denied`, и push отвергается целиком (иначе ветки и теги прошли бы мимо путей и квоты в бандл); `denyDeletes`/`denyNonFastForwards` — вторая линия; для `main` хук сравнивает **изменённые пути** (`diff-tree --name-only old new`), не дерево — незатронутый `.gitattributes` проходит; корневой `.gitattributes` неизменяем: правка или удаление — `path_denied`; фикстура `fixtures/access/preReceiveUpdates.json` — `old new ref` и пути → код
- Режим `memory`: `pre-receive` отвергает любой push; память только через сервер; `history_search` пуст; сессии участников в личных сторах; **сети нет — памяти нет**: это сказано в `functional.md`, в тексте политики при создании команды и в `teamSetup.md`, офлайн даёт только `sync`
- Режим `sync`: push только в `projects/**` и `machines/<storeName>/**` своего ключа; `config/**` запрещён (общий `settings.json` с хуками = выполнение команд на машинах участников); квота команды и резерв свободного места хоста проверяются здесь же
- **Отказы `pre-receive` — кодами, тик их читает:** первая строка `vibememory: <код>`, дальше пути, если код про пути; коды `read_only` (грант истёк), `not_a_member`, `team_gone`, `quota`, `disk_reserve`, `path_denied`, `config_denied`, `ref_denied`; тик по коду переводит стор в `paused: {code, since, paths}` в `tick-state.json` **этого стора** (2.7): при `read_only` fetch идёт, push не пробуется; при `not_a_member` и `team_gone` стор не трогается; **при `path_denied` и `config_denied`** — fetch идёт, push не пробуется, `doctor` называет пути и `vibememory store reclone <store-id>` (2.7): движок историю не переписывает, и отвергнутый коммит остался бы в ней навсегда; `doctor` показывает код, человеческую строку и адрес кабинета из `stores.<id>.cabinet`; выход из паузы — `status` с `writable: true` и членством раз в час (`guard::PAUSE_RECHECK`) или `vibememory connect`; `quota`/`disk_reserve` — обычный провал цикла с сообщением хоста, `consecutive_failures` только этого стора
- **Порционный push тика:** при `ahead > 300` тик пушит `sha:refs/heads/main` порциями по 300 (как `connectStore.sh`); отказ по `receive.maxInputSize` (`remote: fatal: pack exceeds maximum allowed size`) — порция делится пополам до одного коммита; коммит больше лимита невозможен (файлы ≥ 45 МиБ не коммитятся, лимит 1g); фикстура отказа, тест деления
- Правило «запись не создаёт проект» на хосте: `memory` — только проекты из `projects` снимка; `sync` и `adopted` — только `ls-tree` репозитория; ошибка называет причину и адрес кабинета
- Область проектов, роль и `history` — у токена и ssh-`mcp`, фильтрует сервер (`scope()`, `project_of`); git-ключ `sync`-команды видит весь репозиторий — сказано в кабинете рядом с выдачей ключа
- Лимиты `maxRecords` (на проект) и `maxRecordBytes` проверяются сервером до `append`, ошибки названы как у Anthropic: `too_many_entries`, `entry_too_large`
- `writable: false` (истёк грант): чтение и экспорт живут, запись по HTTPS и ssh-`mcp` отвечает ошибкой с адресом кабинета, push — кодом `read_only`
- Движок на машине участника (`sync`): раздел `stores` в `config.json`, проект принадлежит ровно одному стору, выбор по cwd тем же glob-диалектом, что `ignoreCwd`; **outbox per вид стора** — в командный стор тик пишет только `machines/<storeName>/{live,tails,links,forgotten}.json`, писатели `history.jsonl`, `tasks/`, `desktop/` для него выключены (`Outbox::Team`), белый список экспорта из `~/.claude/` для команды — только `projects/**`; **`vibememory forget <sid>` в `sync`-команде работает:** стор находится по `live.json`/пути транскрипта среди сторов конфига, надгробие ложится в его `machines/<storeName>/forgotten.json` (`forget.rs:55`), `pre-receive` его пускает, `apply_tombstones` каждого участника (`tick.rs:451-470`) снимает транскрипт локально; исключённый участник надгробие не получит — часть текста о необратимости (решение 7); **входящее направление закрыто так же:** для командного стора тик не вызывает `managed::reconcile` (`tick.rs:226`), не стажирует `config/` (`tick.rs:929-932`) и не ставит `SkillsLink` — подложенный в клон `config/` на машину не попадает по построению; и то и другое — тесты на фикстурах
- Запись памяти получает `member: Option<String>` (3.1); движок владельца на Mac обновляется до выкладки фазы 1, на GPD ставится впервые в фазе W

### 2.7. Движок на машине участника

- **Бинари** — архив с `vibememory` и `vibememory-mcp` из `/dl/` тремя строками (`curl`, проверка суммы per ОС, `tar xzf` в один каталог — решение 16), их печатают страница «Скачать» и `teamSetup.md`; потом `./vibememory install` из этого каталога — шаг `McpBinary` берёт сервер рядом (`install.rs:996-1001`); **при разделе `stores` шаг `McpBinary` обязателен:** `named_binary_state` без источника отвечает `Satisfied` (`install.rs:1009-1015`), а локальный stdio-сервер в cwd команды без `bin/vibememory-mcp` невозможен — `doctor` даёт `missing` с подсказкой «распакуйте архив целиком и повторите `install`»; `install` без `signingIdentity` подпись не делает, ad-hoc подписи линкера macOS достаточно
- **Личный стор не переезжает:** `~/.vibememory/store` и `Layout::store()` остаются, его состояние — `~/.vibememory/` (миграции нет); **командный стор — клон `~/.vibememory/stores/<store-id>/store`, каталог состояния — `~/.vibememory/stores/<store-id>/`** (свои `tick-state.json`, `quarantine/`, отложенные заметки); `engine_dir_of(store) = store.parent()` (`tick.rs:1265`) верен для обоих — оба клона лежат в `<состояние>/store`, состояние тика, back-off и пауза **per стор по построению**, `guard.rs` не меняется; `Layout::team_store(id)` отдаёт пару «клон, каталог состояния»; `hook::session_start` и `doctor` обходят каталоги состояния всех сторов; тест: `quota` командного стора не увеличивает `consecutive_failures` личного; хуки и ссылки существующих машин не меняются — гейт фазы 5 сравнивает их байт в байт
- **Раздел `stores` конфига** — `stores.<id>: {remote, cabinet, member, storeName, cwd: [glob]}`; `cabinet` пишет `connect` из флага `--cabinet` — это адрес для `connect --refresh`, `disconnect` и строки `doctor` о паузе стора у машины с одним ключом без токена (сайдкар `tokens/<team>/<agent>.json` есть только у токенов); образец в `configSpec.md`; стор сессии и записи выбирается по проекту: SessionStart и локальный stdio-сервер — по cwd среди `stores.<id>.cwd`, потом личный; Stop — по клону, содержащему канонический путь транскрипта (реестр мест — 3.1)
- **Личный стор участника без своего хоста:** `vibememory install` без `remote` даёт локальный личный стор — так задумано по коду (`config.rs:52`): тик его не трогает (`tick.rs:589` — `Ok(false)`), `doctor` печатает `remote: none (local store)` без тревоги, зеркало и диск хоста не спрашиваются (`probe(None)`, `probe_disk(None)`); `teamSetup.md` описывает путь как штатный для `sync`-участника: движок — ради командного стора, свой хост для личного — по желанию и `hostSetup.md`
- **Scaffolding командного клона** — только `machines/<storeName>/.keep`; `.gitattributes` в нём уже есть от хоста (2.5), и **для командного стора `install` шаг `Gitattributes` не планирует, а `doctor` с константой его не сравнивает** — истина у хоста, клон получает её fetch'ем, версии бинаря участника и хоста могут различаться; отсутствие файла — `missing` («хост не сделал первый коммит»); `config/{CLAUDE.md,settings.json}` в командный клон не кладутся — иначе первый же push упёрся бы в `config_denied`
- **Настройки git и драйверы слияния командного клона:** `install::plan` ставит `GIT_SETTINGS` и `MERGE_DRIVERS` только на `layout.store()` (`install.rs:316-320`), а без `merge.vibememory-jsonl.driver` в `.git/config` клона параллельные дописи `memory.jsonl` двух участников — конфликт и `merge --abort` каждый тик (`tick.rs:340-347`); поэтому `install::plan` планирует `Step::GitSetting` **per стор** (`push_git_settings` уже принимает путь стора) — для личного и каждого `stores.<id>`, `connect` для `sync` после клона применяет план этого стора тем же `install::apply`, `doctor` показывает `missing`/`conflict` по клону как по личному; строка драйвера одна на все сторы, а каталог состояния (`quarantine/`, заметки `merge_report`) драйвер берёт как `engine_dir_of(cwd)` — git запускает драйвер из корня рабочего дерева (факт раунда 4), тот же инвариант, что у тика; тест на `fixtures/merge/mergeScenarios.json`: два клона с параллельными дописями — до `install::apply` на клоне `merge --abort`, после — слияние драйвером
- **В режиме `memory`** движок участнику не нужен вовсе: только `connect` и фрагмент конфигурации; личный стор у него может отсутствовать — `connect` работает без `install`
- **`doctor` без движка:** `report` без `config.json` завершается кодом 2 (`main.rs:101`); теперь у `doctor`/`status` два раздела — «движок» (нет `config.json` → строка `engine: not installed` и код 0: отсутствие движка — не поломка) и «учётные данные» (токены и сайдкары, ключи, `known_hosts` против точки `hostkeys`, блоки `~/.ssh/config`, `curl`, паузы сторов)
- **Перенос проекта в `sync`-команду** — `vibememory project move <cwd> --to <store-id>`: копирует `projects/<name>/**` (транскрипты и `memory.jsonl`, версии как есть) в клон команды, перелинковывает `~/.claude/projects/<enc>` на новый стор, в личном сторе оставляет каталог как архив с `moved.json {to: <store-id>, at}` (движок файлы не удаляет; хуки по `moved.json` его больше не линкуют); допустим только без живого sid этого `enc` в `live.json` всех машин — то же правило, что у `relink`; **обратно — `--to personal` только для проекта с `moved.json` этого личного стора, и назад едет только своё:** транскрипты сессий с sid из `machines/<handle>-*/tails.json` командного стора (все машины участника), и версии `memory.jsonl` с `member` = свой `handle` — union кладёт их поверх архива; чужие транскрипты и версии в личный стор не копируются (решение 10: оттуда они уехали бы на его remote и зеркало), проект, родившийся в команде, — отказ «проект принадлежит команде»; `history_search` на машине ищет по всем сторам конфига, на хосте — только по команде
- **Восстановление клона после `path_denied`/`config_denied`** — `vibememory store reclone <store-id>`: старый клон переносится в `~/.vibememory/stores/<id>/store.rejected-<дата>/` (движок не удаляет), репозиторий клонируется заново в `stores/<id>/store`, из старого рабочего дерева в новый клон копируются только пути белого списка (`projects/**`, своё `machines/<storeName>/`) и коммитятся, ссылки `~/.claude/projects/*` перенацеливаются, пауза снимается; запрещённые файлы остаются в отложенном каталоге, легитимные не теряются, история не переписывается
- **Снятие одной командой** — `vibememory disconnect <store-id>`: `project move --to personal` для каждого проекта с `moved.json` этого личного стора (правило выше — только своё), у остальных проектов ссылки `~/.claude/projects/<enc>` снимаются; клон и состояние переносятся в `~/.vibememory/stores/<id>.disconnected-<дата>/` (по образцу `store.rejected-*`: движок не удаляет, чужие транскрипты остаются локальным архивом вне сторов, `doctor` называет каталог); удаляются ключ, `known_hosts`, блок `~/.ssh/config`, токены `~/.vibememory/tokens/<team>/` с сайдкарами и фрагменты конфигурации, раздел `stores.<id>`; печатает адрес кабинета (из `stores.<id>.cabinet`, а для токенов — из сайдкара) для отзыва ключа и токенов на сервере; для `memory`-команды без клона — только токены, сайдкары и фрагменты
- Windows участника — полноценная цель: фаза 4 гоняет `connect`, `icacls` и запись на GPD, фаза 5 — тик из Планировщика в командный стор

## 5. Риски

- **Диск и RAM хоста** — стор растёт ~ГБ/нед, Postgres на полном диске умирает молча → расширение и замер роста в фазе 0, резерв и квота в `pre-receive`, `status` раз в час с письмом, порог `doctor`
- **Пустой командный репозиторий** — без первого коммита `append_once` и push тика не работают → первый коммит `.gitattributes` делает `access-apply`, гейт фазы 2 обоими путями
- **Смена текста `.gitattributes`** — в командах файл менять некому → обновляет `access-apply` локальным коммитом, гейт фазы 2; клон с константой не сравнивается
- **Удаление команды по отсутствию в снимке** — дамп или пустая база переименовали бы живые репозитории → удаление только маркером, отсутствие = «не трогать», сторож — строки базы против `teamCount` из `host.json` (дамп хост не переписывает), `ExecStartPre`, гейт дампа в фазе 3
- **Команда, созданная после дампа, теряет доступ** — обычное создание с её слагом отказывает → «принять сиротский каталог» с причиной, реаттач по существующему правилу, гейт фазы 3
- **`shell` — граница безопасности** — ошибка разбора `SSH_ORIGINAL_COMMAND` = чужой репозиторий, но не sudo → ключи только под `vmgit`, `restrict`, фикстуры инъекций, `status` по области ключа, адверсарный прогон до первого ключа
- **Чужие ссылки в push** — `refs/heads/x` и теги прошли бы мимо путей и квоты в бандл → `ref_denied` на всё кроме `refs/heads/main`, гейт фазы 2 с `for-each-ref`
- **Рендер ключей** — ключ с переводом строки дал бы строку без `restrict` → строгая валидация в Rust, дефектный ключ пропускается с журналом
- **Групповые права на `store.git` и `/home/vm`** — `sharedRepository=group` не трогает существующие файлы, `git -C` под `vmgit` упирается в «dubious ownership» → рекурсивные `chgrp`/`chmod`/setgid, `--git-dir` в коде и `safe.directory` для мануалов, гейт фазы 0 обоими способами и gc после
- **Личный стор владельца открыт участникам** — `admin`-членство в `adopted` дало бы клон транскриптов → у `adopted` одно членство по расширению Prisma, `access check` отказывает, гейты фаз 1 и 3
- **`Match` в drop-in sshd** — без `Match all` остаток `sshd_config` уходит в блок и запирает хост → `Match all`, `sshd -t` и `-T` до `reload`, окно страховки
- **Ключ хоста у участника** — `BatchMode` без `known_hosts` = отказ без вопроса → ключи хоста в ответе claim, `UserKnownHostsFile` per стор, `doctor` против точки `hostkeys`, `connect --refresh` (решение 20)
- **Гейты пака opt-in** — открытая регистрация VibeSter → deny-by-default на `root`, гейт в `databaseHooks`, `curl` анонимом на проде, адверсарная проверка
- **Секреты в логах кабинета** — прецедент `requestLoggingLeak.md` → своё логирование без тела, тест с маркером
- **Токен в транскрипте или в сторе** → путь выдачи один (claim-код → файл 0600 / `icacls`), `connect` ничего не печатает, регистрация только в `~/.claude.json`, управляемая копия `settings.json` с `vmt_` не копируется
- **Расхождение снимка и базы** — «правило без исполнителя» → полная перезапись на каждое изменение, реконсилер раз в 5 минут под сторожем, `hostAck` у владельца, `access check` на кандидат-снимке в каждой мутации и в int-тесте, первая публикация сверяется с рукописным снимком
- **Два писателя `host.json`** → пишет только `status`, `access-apply` кладёт своё в `applied.json`; гейт фазы 2 — `diff` пуст
- **Плагин `organization` и адаптер Prisma 7** — совместимость не подтверждена → спайк в фазе 0; иначе свои `Team`/`Membership` той же формы, снимок не меняется
- **`bunx 1gr14 update` из подкаталога** — не проверен → спайк в фазе 0; ломается — обновления диффом вручную
- **Транскрипты `sync`-команд** — секреты вывода инструментов видны каждому ключу, у исключённого остаётся клон без надгробий → `memory` по умолчанию, предупреждение с необратимостью, §11 `architecture.md`; `disconnect` и `project move --to personal` возвращают в личный стор только своё, чужое остаётся в `.disconnected-*`
- **Правовой** — сумма или автоматика «перевод → код» выводит из рамки A → UI проверяется на это при каждом выпуске; заметка кода без имён и сумм
- **`bun install --production`** выкидывает devDeps миграций → гейт фазы 3 на хосте, миграции только из `dependencies`
- **Один процесс на все команды** — паника в потоке отравляет мьютекс команды → `into_inner` с громкой строкой, состояние в репозитории консистентно; падение процесса — `Restart=on-failure`
- **Один стор в коде движка** — состояние тика, драйверы слияния и хуки знали только `layout.store()`: `quota` команды гасил бы личный стор на 15 циклов, параллельные дописи `memory.jsonl` = `merge --abort`, транскрипт команды уехал бы в личный → каталог состояния и `install::plan` per стор, маршрутизация по проекту (3.1); гейт фазы 5: два `tick-state.json`, слияние драйвером, коммит в командный клон
- **Старый движок на машине владельца** переписывает проекцию без `member` → обновление на Mac — гейт фазы 1, на GPD движок ставится в фазе W; round-trip фикстура; старая версия остаётся (keep-both)
- **Старый движок участника пишет запрещённый путь** → `path_denied` = пауза с путями, `store reclone` без переписывания истории; гейт фазы 5
- **Бинари у чужого человека без подписи** — скачанный браузером macOS остановит, одиночный `vibememory` оставил бы `sync`-участника без stdio-сервера → архив с обоими бинарями, `curl` с проверкой суммы per ОС, `install` из каталога архива, `McpBinary` в `doctor`; Developer ID не меняет канал; `curl` на старом Windows нет — `doctor` и `install` называют шаг `Curl`, Git for Windows несёт свой
- **Windows вживую** — движка на GPD нет → фаза W ставит его и закрывает этап 4; при 19(б) — только `memory`-участник, сказано в roadmap
- **Единственная копия `memory`-сторов и базы** — ночной бэкап с восстановлением на Mac в гейтах фаз 2 и 3; `sync`-стор — копией из клона участника, гейт фазы 5; возраст бэкапа в письме
- **Утечка установочных значений через доки** → маскировать как в конфиге, окно правки закрывается первым пушем
